# 에이전트 하네스 — 팀원용 안내

리포에 `.claude/`와 `CLAUDE.md`가 생겼습니다. 이게 뭐고, **당신 기계에서
무엇이 달라지는지**를 설명합니다.

세 줄 요약.

- Claude Code를 **안 쓴다면** 아무 영향 없습니다. 1절 끝만 보고 덮으셔도 됩니다.
- **쓴다면** pull 하는 순간 훅 하나가 켜지고 명령 18개가 자동 승인됩니다.
- 끄는 법은 4절에 있습니다. 끈다고 눈치 주지 않습니다.

---

## 1. pull 하면 무엇이 달라지나

**커밋된 설정이라 pull 하면 당신에게도 적용됩니다.** 이게 이 문서를 쓴
이유입니다. 모르고 있다가 발견하는 게 제일 나쁩니다.

### Claude Code를 쓰는 경우

**① `src/`나 `tests/`의 `.py`를 고치면 테스트가 자동으로 돕니다.**

Claude가 파일을 고칠 때마다 `pytest -q -x`가 붙습니다. 약 5초. 통과하면
아무 표시도 없고, 실패하면 실패 내역이 Claude에게 되돌아가 고치게 합니다.

문서만 고칠 때는 안 돕니다(0.3초 만에 건너뜁니다).

가상환경(`.venv/`)이 없으면 조용히 넘어갑니다. 그러니 아직 환경을 안 만든
사람에게는 아무 일도 일어나지 않습니다.

**② 명령 18개가 물어보지 않고 실행됩니다.**

`pytest`, 파이프라인 단계 실행, `tools/`·`benchmark/` 스크립트, 그리고
읽기 전용 git(`status` `log` `diff` `show` `branch` `ls-files`)입니다.

전부 이 리포 안에서 도는 것이거나 아무것도 바꾸지 않는 것입니다. 파일을
지우거나 커밋하거나 푸시하는 명령은 넣지 않았습니다. 그건 여전히 물어봅니다.

**③ Claude가 이 프로젝트의 규칙을 미리 압니다.**

`CLAUDE.md`가 매번 자동으로 읽힙니다. 스키마가 동결됐다는 것, `ref`는
`refs.py`를 경유해야 한다는 것, 커밋 메시지 형식 같은 것들입니다. 매번
설명하지 않아도 됩니다.

### Claude Code를 안 쓰는 경우

**아무 영향 없습니다.** 훅은 Claude Code 안에서만 돕니다. `git`, 편집기,
`pytest`를 직접 쓰는 것은 전과 똑같습니다.

`.claude/` 폴더가 하나 늘어난 것뿐입니다. 지우지만 말아주세요.

---

## 2. 하네스가 뭔가

**모델을 둘러싼 환경 전부**를 가리킵니다. 도구, 파일 배치, 실행 명령,
검증 루프, 권한, 문서.

발상은 단순합니다. **에이전트가 자주 틀리면 더 잘 부탁하지 말고, 틀릴 수
없는 환경을 만든다.**

| 문제 | 부탁하는 해법 | 하네스 해법 |
|---|---|---|
| 자꾸 잘못된 파이썬을 부른다 | 매번 설명한다 | CLAUDE.md에 한 줄 박는다 |
| 테스트를 안 돌린다 | "테스트 돌려줘"라고 한다 | 훅으로 강제한다 |
| 같은 절차를 매번 설명한다 | 매번 설명한다 | 스킬로 만든다 |

부탁은 세션이 끝나면 사라지고, 하네스는 리포에 남습니다. 그 차이입니다.

---

## 3. `.claude/`에 뭐가 있나

```
CLAUDE.md                          Claude가 매 세션 읽는 기준 문서
.claude/
├── settings.json                  팀 공용 — 권한과 훅 (커밋됨)
├── settings.local.json            개인용 — 당신 승인 기록 (커밋 안 됨)
├── hooks/
│   └── pytest-on-source-change.sh 훅이 실제로 실행하는 스크립트
└── skills/
    └── add-parser/SKILL.md        04단계 파서 추가 절차
```

### `CLAUDE.md`

**사람용 명세가 아닙니다.** Claude에게 주는 지시서입니다. 설계를 알고
싶으면 `work-guide.md`를 보세요.

여기에는 "매 세션 반복되는 것"만 넣습니다 — 실행 명령, 환경 함정, 어느
문서가 어느 주제의 권위인지. 매 세션 실리는 비용이라 100줄 안쪽으로 묶어 뒀습니다.

**여기에 설계 근거나 스키마 필드를 복사하지 마세요.** 진실이 두 개가
되면 갈라지는 순간 어느 쪽이 맞는지 알 수 없게 됩니다.

### `settings.json` vs `settings.local.json`

| | 무엇 | git |
|---|---|---|
| `settings.json` | 팀 전체에 해당하는 권한·훅 | 커밋 |
| `settings.local.json` | 당신이 개인적으로 승인한 것 | 제외 |

Claude Code에서 "항상 허용"을 누르면 `settings.local.json`에 쌓입니다.
그건 당신 기계 사정이니 커밋되지 않습니다.

팀 전체에 해당하는 것만 `settings.json`에 넣습니다. 판단이 서지 않으면
그냥 두세요. 어차피 local에 쌓입니다.

### `skills/`

작업 종류별 절차서입니다. **관련 있는 작업일 때만** 불려 옵니다.

CLAUDE.md와 나눈 기준은 분량입니다. CLAUDE.md는 매 세션 비용이라 짧아야
하고, 스킬은 그때만 실리므로 길어도 됩니다. "새 파서 추가" 같은 160줄 넘는
절차가 스킬로 간 이유입니다.

## 4. 끄는 법

### 훅만 끄기

`.claude/settings.local.json`에 넣으면 당신 기계에서만 꺼집니다.

```json
{ "disableAllHooks": true }
```

### 팀 전체에서 끄기

`.claude/settings.json`의 `hooks` 블록을 지웁니다. 스크립트는 남겨둬도
아무 일도 하지 않습니다.

### 권한을 되돌리기

`settings.local.json`의 `deny`에 넣으면 당신 기계에서만 다시 물어봅니다.

```json
{ "permissions": { "deny": ["Bash(git log*)"] } }
```

**성가시면 끄세요.** 하네스는 일을 편하게 하려고 있는 것이지 지키라고
있는 규칙이 아닙니다. 끄는 사람이 많으면 그건 하네스가 잘못 만들어진
것이지 사람이 잘못한 게 아닙니다.

## 5. 언제 손대나

**작업 전에 하네스를 손보지 않습니다.** 그러면 하네스 만들다가 프로젝트를
못 합니다.

### 스킬을 만드는 시점

기준은 대략 **세 번째**입니다.

| | 할 일 |
|---|---|
| 1번째 | 그냥 합니다. 절차를 모르니 쓸 것도 없습니다 |
| 2번째 | "저번에도 이랬는데" 알아차립니다. 아직 안 씁니다 |
| 3번째 | 이제 씁니다. 두 번의 실제 사례가 근거가 됩니다 |

두 번으로는 무엇이 매번 같고 무엇이 케이스마다 다른지 구분이 안 됩니다.
그 상태로 쓰면 특정 케이스를 일반 규칙으로 착각한 문서가 나옵니다.

`add-parser`가 정당한 이유는 **이미 네 번 했기** 때문입니다 — `$MFT`,
`$UsnJrnl`, `evtx`, `registry`.

### 고치는 시점

**틀렸다는 게 드러났을 때만**입니다. 절차대로 했는데 안 되면 그 자리에서
고치고 같은 커밋에 넣습니다. 테스트가 잘못됐을 때 테스트를 고치는 것과
같습니다.

잘 됐으면 아무것도 안 합니다.

---

## 6. 과해졌다는 신호

이런 게 보이면 줄이는 게 맞습니다.

- 스킬이 열 개가 넘는데 대부분 안 불려 온다
- 작업보다 하네스 고치는 시간이 길다
- 스킬 내용이 틀려서 Claude가 무시하고 진행한다
- 팀원 대부분이 훅을 꺼 놨다

관리 대상이 하나 늘어나는 선택이라는 점을 잊지 않는 게 좋습니다. 이
리포는 이미 문서 여덟 개가 낡아 있던 적이 있습니다.
