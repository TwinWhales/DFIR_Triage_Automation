# 온디스크 구조 조사 메모

파싱하면서 확인한 사실과, **기존 도구와 어긋난 지점과 그 원인**을 쌓는
문서입니다. 진행 중 누적됩니다.

여기 쌓인 내용이 팀의 학습 성과물이자, 발표에서 "직접 구현했다"를
뒷받침하는 근거입니다. 스펙 문서를 옮겨 적는 곳이 아니라 **실제 데이터에서
겪은 것**을 적는 곳입니다.

---

## 대조 기록

`work-guide.md` 3.2가 필수로 정한 절차입니다. 파서를 고칠 때마다 돌리고
결과를 여기 남깁니다.

```bash
MFTECmd.exe -f "<evidence>\$MFT" --csv out --csvf mft.csv
.venv/Scripts/python.exe tools/compare_mft.py --ours cases/<id>/04_parsed/mft.jsonl --mftecmd out/mft.csv --full
```

`--full`은 범위 없이 돌린 출력에 씁니다. 선별 범위만 낸 결과에는 붙이지
마십시오 — MFTECmd에만 있는 레코드가 전부 오류로 잡힙니다.

### 대조 조건 — 두 산출물의 출력 단위가 다르다

| | 출력 단위 |
|---|---|
| MFTECmd CSV | **스트림마다 한 행.** `Sysmon.exe`와 `Sysmon.exe:Zone.Identifier`가 같은 `EntryNumber`의 두 행이다 |
| 우리 파서 | **레코드당 한 건.** 이름 없는 `$DATA`만 본다(`parsers/mft.py`의 `_data_size`) — ADS는 범위 밖(`work-guide.md` 3.3) |

그래서 `compare_mft.py`는 **`IsAds = True` 행을 제외하고** 대조하며, 제외
건수를 요약에 적습니다. **조건이 빠진 기록은 재현되지 않습니다** — 같은
CSV로 다른 숫자가 나옵니다.

**이것은 건수로 드러나지 않는 문제였습니다.** 대조기는 `EntryNumber`를
키로 짝을 맞추므로 ADS 행이 레코드 수를 늘리지 않습니다. 나중 행이 앞 행을
**덮어쓸** 뿐입니다. 그러면 경로가 `Sysmon.exe:Zone.Identifier`로 바뀌어
ADS를 가진 파일 수만큼 경로 불일치가 나오고, 타임스탬프도 본체가 아닌 행과
대조하게 됩니다. 2026-09-02 이전 대조는 이 상태였습니다 — 아래 기록들이
어긋나지 않은 것은 대조가 옳아서가 아니라 **그 이미지들에 콜론이 든 이름이
드물었기 때문**입니다(`$UsnJrnl` 355,850레코드 조사에서 콜론이 든 ADS
이름 0건). 지금까지의 `$MFT` 판정은 이 조건으로 다시 돌려 봐야 합니다.

`IsAds` 열이 없거나 모르는 값이면 **멈춥니다.** `FileName`의 콜론으로도
가려낼 수 있지만(NTFS 파일 이름에 콜론은 못 들어간다) 그것은 표기에
기대는 판정이라, 맞았는지 아무도 확인하지 않게 됩니다. ADS를 걸러 낸 뒤에도
`EntryNumber`가 중복이면 역시 멈춥니다 — 덮어쓰면 어느 행과 대조했는지
알 수 없습니다.

**아직 대조하지 않는 것: `fn_*` 타임스탬프.** `COMPARED_TIMESTAMPS`가
`si_*` 넷뿐이라 `$FN` 시각은 읽어만 두고 비교하지 않습니다. 넣으려면
**"생략"의 뜻이 양쪽에서 반대라는 것**을 먼저 처리해야 합니다 — MFTECmd는
`0x30` 값이 `$SI`와 같으면 열을 비우고, 우리 파서는 FILETIME이 0일 때 키를
뺍니다. 그대로 비교하면 "우리 값 있음 + 저쪽 공란"이 전부 불일치가 됩니다.
`theirs`가 없을 때 우리 `fn_x == si_x`인지 보는 처리가 필요합니다.

### 기록 형식

`compare_mft.py`의 요약을 그대로 붙이고, **원인**을 덧붙입니다.
수치만 남기면 나중에 같은 실수를 반복합니다. **대조 조건 줄을 빼지
마십시오** — 무엇을 제외한 대조인지가 수치의 일부입니다.

```markdown
- 판정: 통과

**원인 / 조치**

```

#### 2026-08-19 · evtx · python-evtx 어댑터 (최초)

**이 프로젝트 최초의 진짜 외부 도구 대조입니다.** `$MFT`·`$UsnJrnl`은
자체 정답지로 대신했지만, evtx는 `wevtutil`이 모든 Windows에 들어 있어
준비물이 없습니다. 마이크로소프트 자신의 파서라 **공통 오해가 생기지
않습니다** — 같은 사람이 짠 두 구현을 비교하던 한계가 여기서는 없습니다.

```bash
wevtutil epl Application <사본>.evtx          # 라이브 로그는 잠겨 있어 사본을 뜬다
wevtutil qe <사본>.evtx /lf:true /f:xml       # 정답지
```

대조 대상 8,257레코드(Application 로그, 7.4MB, 103청크).

| 항목 | 결과 |
|---|---|
| 레코드 수 | 8,257 / 8,257 **일치** |
| EventRecordID 집합 | 차이 **0건** |
| `event_id` | 불일치 **0건** |
| `computer` | 불일치 **0건** |
| 타임스탬프(초까지) | 불일치 **0건** |
| 타임스탬프(100ns 자리) | 8,257건 전부 0~+9 차이 — 아래 참조 |

`offset`도 따로 확인했습니다. 200건을 뽑아 그 위치의 원본 바이트를 읽으니
**200/200이 레코드 매직(`2A 2A 00 00`)** 이었습니다. 근거 추적이 이 필드에
달려 있으므로 값이 그럴듯한 것만으로는 부족합니다.

**원인 / 조치**

- 처음에는 `record.timestamp()`를 그대로 썼습니다. 그랬더니 7,938건이
  **−1.6 µs ~ +2.8 µs** 어긋났고, 오차가 **양방향**이라 100ns 절삭으로는
  설명되지 않았습니다. python-evtx가 float로 변환하기 때문입니다.

  ```python
  # Evtx/BinaryParser.py — parse_filetime
  datetime.fromtimestamp(float(qword) * 1e-7 - 11644473600, timezone.utc)
  ```

  아래 "밟은 함정"에 이미 적혀 있는 문제를 **vendored 라이브러리가 다시
  들여온 것**입니다. 우리 `filetime_to_datetime`은 정수 연산만 씁니다.
  원시 FILETIME qword(레코드 오프셋 `0x10`)를 직접 읽어 그 함수로 넘기니
  차이가 **0~+9로 균일**해졌습니다. 이제 남는 것은 `datetime`이 마이크로초
  까지만 담아 생기는 100ns 절삭뿐이고, `$MFT`·`$UsnJrnl`과 같은 규약입니다.

## 확인한 구조

구조 정의는 `src/stage04_parse/structs/`에 있습니다. **그 파일의 오프셋 표는
스펙 대조 전 상태**이므로, 대조하면서 확인했거나 고친 것을 여기 적습니다.

### $MFT

#### timestamp_mismatch 판정은 **생성 시각만** 봐야 한다

가장 중요한 발견입니다. 초기 룰은 `$SI`가 `$FN`보다 이른 쌍이 **하나라도**
있으면 플래그를 붙였습니다. 방향(이르다)만 따지면 맞는 줄 알았습니다.

실제 이미지에서 측정한 결과:

| 비교 | 걸린 레코드 |
|---|---|
| `si_btime < fn_btime` (생성) | **0건** |
| `si_ctime < fn_ctime` | 91건 (59%) |
| `si_mtime < fn_mtime` | 91건 (59%) |
| 초기 룰 (셋 중 하나라도) | **91건 (59%)** |

**91건 전부 오탐이었습니다.** 154건 중 59%가 걸리면 필터로 쓸 수 없습니다.

원인은 파일 복사입니다. 복사하면 `$SI`의 ctime·mtime은 원본 값이 보존되고,
`$FN`은 새 디렉터리 항목이 만들어진 시각으로 설정됩니다. 실제 값:

```
si_btime = 2026-07-24T00:28:07.476   fn_btime = 2026-07-24T00:28:07.476  (같음)
si_ctime = 2026-07-23T08:51:16.954   fn_ctime = 2026-07-24T00:28:07.476  (다름)
```

"파일이 자기 이름 항목보다 먼저 존재할 수 없다"는 논리는 **생성 시각에만**
적용됩니다. ctime·mtime은 그 논리가 성립하지 않습니다.

→ `flagging.MISMATCH_PAIRS`를 `(("si_btime", "fn_btime"),)`로 좁혔습니다.
   같은 이미지에서 0건이 나옵니다(이 이미지에는 조작이 없으므로 맞는
   결과). 오탐 패턴은 `tests/test_flagging.py`에 회귀 테스트로 고정했습니다.

**교훈**: 추론으로 만든 룰은 실제 데이터에서 확인하기 전까지 믿을 수
없습니다. 이 룰은 합성 테스트를 전부 통과했습니다.

#### …그런데 시스템 볼륨에서는 좁힌 룰도 81%가 걸린다 (미해결)

**위 수정으로 끝난 줄 알았는데 아니었습니다.** 같은 룰을 실제 시스템
볼륨(`evidence/[root]`, Windows 7)에 돌리니 이렇게 나옵니다.

| 볼륨 | 대상 | `timestamp_mismatch` |
|---|---|---|
| `evidence/test` (데이터 볼륨) | 154 | **0건** |
| `evidence/[root]` (시스템 볼륨) | 2,034 (실행파일류) | **1,651건 (81%)** |

원인은 **OS 설치**입니다. 측정하면 바로 드러납니다.

- 걸린 것들의 `fn_btime`은 **서로 다른 "분"이 14개뿐**입니다.
  675건이 `2019-01-10T02:48`, 464건이 `02:47` — 설치 시각입니다.
- 같은 것들의 `si_btime`은 **167개 분에 흩어져** 2009~2010년입니다.
  `2009-07-13`(Windows 7 RTM), `2010-11-21`(SP1) 빌드 시각입니다.
- 표본: `C:\Windows\System32\msinfo32.exe`, `iexplore.exe`, `ielowutil.exe`
  — 전부 OS 기본 바이너리입니다.

즉 **Windows Setup이 `$SI`는 설치 미디어의 빌드 시각으로 보존하고
`$FN`은 디렉터리 항목을 만든 설치 시각으로 씁니다.** 그래서
`si_btime < fn_btime`이 OS 파일 전체에서 정상적으로 성립합니다.

앞의 복사 사례를 피하려고 btime으로 좁혔는데, **설치는 바로 그 btime을
보존합니다.** 좁힌 방향이 이 경우엔 효과가 없습니다.

**시도해 봤으나 검증되지 않은 판별자 둘** — 이 볼륨엔 실제 조작이 없어
참양성으로 확인할 수 없었습니다. 근거 없이 채택하면 안 됩니다.

- `si_btime` 소수부가 0인가 → 걸린 것의 **30.5%(503건)가 이미 0**입니다.
  MSI·ZIP처럼 초 단위만 보존하는 설치 경로가 많아 판별력이 약합니다.
- `fn_btime` 클러스터 바깥인가 → 1,651 → 9건으로 줄지만, 그 9건도 전부
  정상 소프트웨어 설치(VS Launcher, .NET SetupCache, VMware)였습니다.

**영향** — `$MFT`의 `timestamp_mismatch`가 시스템 볼륨에서는 필터 구실을
못 합니다. `record_filter.DEFAULT_LIMIT`이 60이므로 1,651건 중 60건만
05단계로 갑니다. `limitations.md` 4-2가 `$UsnJrnl`에 대해 적은 것과
**같은 문제이며, 이제 `$MFT`에도 해당합니다.**

#### 미사용 슬롯

256슬롯 중 154개만 유효했습니다. 나머지는 0으로 채워져 있어 시그니처

### $UsnJrnl

`evidence/$J`(33MiB, 355,850레코드)에서 확인한 것들입니다.

**저널 블록은 4096바이트입니다.** `[LIBFSNTFS]`가 열어 둔 질문
(*"seems to be 4096 bytes, but could this be defined by the index entry
size?"*)에 대한 실측 답입니다.

- 0 구간 7,616개가 **전부** 4096 경계에서 끝남 (`끝 % 4096 == 0`이 7,616/7,616)
- 4096 경계를 넘는 레코드 **0건** / 355,850건

즉 레코드는 블록을 가로지르지 않고, 블록 끝 자투리는 0으로 채웁니다.
0바이트 총 823,376(파일의 2.4%)이 전부 이 패딩입니다. 파서는 블록
크기에 의존하지 않고 0을 만나면 건너뛰는 방식이라 이 값이 달라져도
동작합니다 — 의존하지 않는 편이 낫다는 근거이기도 합니다.

**USN 값과 파일 오프셋이 어긋납니다.** 첫 레코드의 USN이 159,383,552인데
파일 오프셋은 0입니다. 추출본이 **스트림 앞부분이 잘려 나간 뒷도막**이기
때문입니다(저널이 최대 크기에 닿아 앞쪽이 스파스로 회수된 상태).

- 파일 안에서는 USN 증가분 = 오프셋 증가분 (34,164,232로 동일)
- 그래서 `record_num`(=USN)과 `offset`(=파일 위치)을 따로 기록합니다.
  둘의 차이가 곧 "잘려 나간 앞부분의 크기"입니다.

**이름** — 최장 154자(`...presentationframework-systemdata_...cdf-ms`),
한글 이름 정상 복원(`오픈소스_스튜디오`), 콜론이 든 ADS 이름은 없었습니다.
255자 상한에 한참 못 미쳐 `MAX_RECORD_SIZE = 4096` 여유는 충분합니다.

### EVTX

python-evtx를 씁니다. 직접 구현하지 않는 이유는 바이너리 XML + 청크
압축이라 난이도가 차원이 다르기 때문입니다(`work-guide.md` 3.1).

레코드마다 `absolute_offset`을 주는 것을 확인했으므로, 근거 추적 구조는
라이브러리를 써도 성립합니다.

Application 로그 8,257건에서 확인한 것들입니다.

#### `<EventData>`의 모양은 하나가 아니다

`<Data Name="X">`만 있을 거라고 가정하면 대부분을 놓칩니다.

| 모양 | 건수 | 비율 |
|---|---|---|
| 이름 없는 `<Data>` | 7,503 | **91%** |
| `<Data Name="X">` | 374 | 4.5% |
| `<EventData>` 없이 `<UserData>`만 | 266 | 3.2% |
| `<EventData>`가 빔 | 109 | 1.3% |
| `<Data>`와 `<Binary>` 혼재 | 5 | 0.1% |

**이름 없는 `<Data>`가 예외가 아니라 다수입니다.** Security 로그는 이름을
붙이는 이벤트가 많지만, 카탈로그에 채널을 더하면 이쪽이 늘어납니다.
그래서 `Data[0]`, `Data[1]`로 자리를 남깁니다 — USN의
`unknown_0x########`와 같은 이유로, 조용히 버리면 아무도 모릅니다.

`<UserData>` 하위는 **제공자 고유 네임스페이스**를 씁니다(실측:
`http://manifests.microsoft.com/win/2006/windows/WMI`). 기본 네임스페이스
하나로 못 박으면 이쪽이 통째로 안 읽힙니다.

#### chunk_count를 믿으면 꼬리를 잃는다

`FileHeader.chunks()`는 헤더가 선언한 `chunk_count`까지만 냅니다. 실측
파일은 물리 슬롯 113개 중 103개만 선언돼 있었고, 나머지 10개는 빈 공간이라
체크섬에서 걸러졌습니다.

문제는 **로그가 깨끗하게 닫히지 않은 경우**입니다. 그때 선언값이 실제보다
작으면 가장 최근 이벤트가 담긴 꼬리 청크가 조용히 빠지는데, 사고 대응에서
제일 보고 싶은 구간이 그쪽입니다. 그래서 `include_inactive=True`로 물리
슬롯을 전부 훑고 `verify()`로 거른 뒤, 선언 밖에서 살아난 청크를
`recovered_chunks`로 셉니다.

#### 라이브러리가 청크를 조용히 끊는다

`ChunkHeader.records()`는 레코드 하나가 깨지면 `InvalidRecordException`을
잡아 그냥 `return`합니다. **그 청크의 나머지가 통째로 사라지는데 아무 소리도
나지 않습니다.**

그래서 `Evtx.records()`를 쓰지 않고 청크를 직접 걸으며, 마지막 레코드의 끝이
청크가 선언한 `next_record_offset` 경계에 못 미치면 `parse_errors`로 셉니다.
정상 청크에서는 둘이 정확히 일치하는 것을 확인했습니다(`last_end == boundary`).

### 프리패치

온디스크 구조와 `MAM` 압축 해제 둘 다 자체 구현입니다. 파이썬에 이 압축을
푸는 표준 라이브러리가 없고, `ctypes`로 `RtlDecompressBufferEx`를 부르면
**Windows에서만 읽히는 아티팩트**가 되기 때문입니다 —
플랫폼에 따라 볼 수 있는 증거가 달라지면 "봤는데 없었다"와 "볼 줄 몰라
못 봤다"의 구분이 실행 환경에 좌우됩니다.

#### 버전마다 움직이는 것은 둘뿐이다

구조 전체가 버전마다 바뀌는 것처럼 보이지만 실제로 움직이는 것은 실행
시각·실행 횟수의 자리와 배열 원소 크기뿐입니다. **파일 정보 블록 앞머리
9개 dword(0x00~0x23)는 모든 버전에서 같은 자리**라, 적재 파일 목록과
볼륨 정보는 버전과 무관하게 한 경로로 읽힙니다.

그래서 `FILE_INFORMATION` 표를 **(버전, 블록 크기)**로 찾습니다. 블록
크기는 표에서 가져오지 않고 **파일이 말하는 값**(메트릭 배열 오프셋 -
헤더 84)을 씁니다. 버전 30은 Windows 10 빌드에 따라 이 값이 달라
버전 번호만으로는 자리를 정할 수 없습니다.

| 버전 | Windows | 블록 | 실행 시각 | 볼륨 원소 | 확인 |
|---|---|---|---|---|---|
| 17 | XP/2003 | 68 | 1개 | 40 | 명세 |
| 23 | 7 | 156 | 1개 | **104** | **실측 73건** |
| 26 | 8.1 | 224 | 8개 | 104 | 명세 |
| 30 | 10 | 224 / 216 | 8개 | 96 | 명세 |
| 31 | 11 | 224 | 8개 | 96 | 명세 |

표에 없는 조합은 **추측하지 않고 그 파일만 건너뜁니다**(`UnknownLayout`).
실행 횟수 자리를 잘못 잡으면 예외도 경고도 없이 그럴듯한 숫자가 나오고,
그것이 보고서에 "3회 실행됨"으로 실립니다.

명세를 잘못 옮겼을 때를 대비해 값의 앞뒤도 봅니다 — 실행 횟수가 100만을
넘거나 실행 시각이 1995년보다 이르면 레코드를 내지 않습니다. 자리가
어긋나면 FILETIME 여덟 개가 전부 그럴듯하게 나올 확률이 낮다는 것에
기댄 검사입니다.

#### 경로는 드라이브 문자가 아니라 장치 이름이다

.pf 안의 경로는 `\DEVICE\HARDDISKVOLUME2\WINDOWS\SYSTEM32\CMD.EXE`
형태입니다. 03단계의 `path_prefix`는 `C:\...` 형태라 **그대로는 절대
매칭되지 않습니다.**

섀도 카피가 아닌 `HARDDISKVOLUME<n>`이 **정확히 하나일 때만** 드라이브
문자로 바꿉니다. 한 실행은 한 볼륨이므로 그 하나가 곧 분석 중인 볼륨입니다.
둘 이상이면 어느 쪽인지 알 방법이 없어 바꾸지 않습니다.

실측 73건 중 **17건이 섀도 카피를 함께 참조**했습니다
(`HARDDISKVOLUMESHADOWCOPY1~3`). 섀도 카피 안의 파일은 살아 있는 볼륨의
그 경로가 아니므로 바꾸지 않습니다. 원본 경로는 `fields.loaded_files`에
손대지 않은 채로 남고, 바꾼 값은 `path` 하나뿐입니다.

##### 장치 이름의 형태가 하나가 아니었다 (2026-08-26 대조)

`\DEVICE\HARDDISKVOLUME<n>` 만 살아 있는 볼륨으로 보고 있었습니다.
**`win10_sysmon_testimage.001` 의 프리패치 127건 전부가 다른 형태**를
씁니다 — 마운트 관리자의 영구 볼륨 이름입니다.

```
\VOLUME{01d8e7bd02796420-a202ae01}\WINDOWS\SYSTEM32\SVCHOST.EXE
        ^^^^^^^^^^^^^^^^ ^^^^^^^^
        볼륨 생성 시각    일련번호
```

한 형태만 보던 탓에 `device_prefixes()` 가 `None` 을 돌려주고,
`_to_drive()` 가 주석대로 경로를 **그대로 뒀습니다.** 조용히 틀리는 쪽은
아니지만(값이 그대로 남을 뿐입니다) 그 결과가 06단계에서 **정상 문장의
기각**으로 나타납니다 — 모델은 `C:\...` 로 정규화해 씁니다.

**대조 방법과 결과.** 127건의 `(device_path, serial_number)` 쌍을 전부
뽑아 봤습니다.

| | |
|---|---|
| 형태 | 127건 전부 `\VOLUME{01d8e7bd02796420-a202ae01}` |
| 레코드당 볼륨 개수 | 127건 전부 **1개** |
| 뒤 8자리 vs `serial_number` | `a202ae01` ↔ `A202AE01` — **일치**(대소문자 무시) |
| 섀도 카피 | **0건** |

뒤 8자리가 일련번호와 같다는 것은 확인했지만 **대조하지는 않습니다.**
어긋날 때 변환을 포기하면 경로가 조용히 안 바뀌는데, 그것이 지금 고치는
증상 그대로이기 때문입니다.

조치 후 127건 중 **115건**이 `C:\` 로 바뀝니다. 나머지 12건은
`path_unresolved` 로, 실행 파일 이름을 적재 목록에서 못 찾은 별개
사안입니다(조치 전후 같은 수 — 위 "29자에서 잘린다" 참조).

**`SHADOWCOPY` 는 여전히 걸리지 않습니다.** 첫 형태는 숫자만, 둘째는
16진수만 받으므로 `HARDDISKVOLUMESHADOWCOPY1` 은 양쪽 다 어긋납니다.
`tests/test_prefetch_parser.py` 가 거부해야 할 형태 다섯을 함께 봅니다.

**남은 것** — `fields.loaded_files` 는 여전히 장치 이름 그대로입니다.
위에 적은 대로 의도된 것이지만, 모델이 적재 파일을 인용하면서 `C:\` 로
정규화하면 그 문장은 기각됩니다. `path` 와 같은 부류의 문제이고 아직
실측된 적은 없습니다 — `docs/limitations.md`.

#### 실행 파일 이름은 29자에서 잘린다

헤더의 이름 자리는 60바이트(UTF-16LE 29자 + 널)입니다. 전체 경로는 적재
파일 목록 안에 있으므로 이름이 맞는 항목을 찾는데, **정확 일치를 먼저 보고
없을 때만 접두어로 내려가야 합니다.** 둘을 한 목록에 섞으면 이름이 29자인
실행 파일이 자기 `.config`까지 후보로 끌고 와 "후보가 둘이라 모르겠다"가
됩니다. 실측에서 그런 파일이 둘 있었습니다.

## 밟은 함정

구현하면서 놓쳤거나 헤맨 지점. **다음 사람이 같은 데서 막히지 않게**
적습니다.

### fixup(업데이트 시퀀스)을 되돌리지 않으면

NTFS는 각 섹터의 마지막 2바이트를 USN으로 덮어씁니다. 되돌리지 않으면
512바이트마다 2바이트가 엉뚱한 값인데, **레코드 대부분은 멀쩡해서 원인을
찾기 어렵습니다.** 경로 문자열이 중간에 깨지거나 타임스탬프가 이상해집니다.

→ `structs/mft_record.py`의 `apply_fixups()`로 처리. 속성을 읽기 **전에**
   반드시 부릅니다.

### $FILE_NAME의 부모 참조는 하위 48비트만

상위 16비트는 시퀀스 번호입니다. 마스킹을 빼먹으면 부모를 못 찾아 경로가
끊깁니다.

### 8.3 단축 이름을 고르면 경로가 이상해짐

한 파일이 `$FN`을 여러 개 가질 수 있습니다. DOS 이름공간을 고르면
`PROGRA~1` 같은 값이 나옵니다. `WIN32` 또는 `WIN32_AND_DOS`를 우선합니다.

### FILETIME 변환에 float를 쓰면 정밀도가 깨짐

`timedelta.total_seconds()`는 float를 돌려줍니다. 유효숫자가 15~16자리인데
FILETIME은 18자리라 **마이크로초가 조용히 틀어집니다.** 정수 연산만 쓰십시오.

(테스트 헬퍼를 짜다가 실제로 밟은 건입니다. 값이 2 마이크로초 어긋났고,
허용 오차 1초 안이라 파이프라인에서는 안 걸렸을 겁니다.)

### USN 이름 크기는 문자 수가 아니라 바이트 수

`$FILE_NAME`은 문자 수(`name_length`)인데 `USN_RECORD_V2`는 바이트
수입니다. `$MFT` 파서 코드를 옮겨 오면 반드시 밟습니다. 한글 이름에서만
깨지므로 ASCII 테스트만으로는 안 잡힙니다 —
`test_name_size_is_bytes_not_characters`로 고정해 두었습니다.

### USN 신호 플래그는 $MFT보다 훨씬 많이 걸린다 (미해결)

`evidence/$J` 355,850건 전량 측정:

| 플래그 | 건수 | 비율 |
|---|---|---|
| `deleted` | 131,139 | 37% |
| `file_created` | 81,266 | 23% |

확장자를 `.exe/.dll/.aspx`로 좁히고 20분 시간창을 걸어도 2,042건 중
**1,281건(63%)이 신호**로 남습니다. `record_filter.DEFAULT_LIMIT`이
60이므로 필터가 사실상 임의로 60건을 고르는 상태입니다.

**원인은 룰이 틀려서가 아닙니다.** 플래그는 정확합니다. 같은 이름이지만
카디널리티가 다릅니다.

- `$MFT`의 `deleted` = **상태**("지금 미할당"). 볼륨 크기에 묶여 있음
- `$UsnJrnl`의 `deleted` = **사건**("지워졌다"). 시간에 비례해 무한정 쌓임

개발 장비의 npm 설치·삭제 같은 정상 churn만으로 수만 건이 나옵니다.
(첫 레코드가 `README.md`, `unpipe`인 것이 그 증거입니다.)

**아직 고치지 않았습니다.** 좁힐 수 있는 가장 강한 축은 경로인데 USN
레코드에는 경로가 없어(`parsers/usnjrnl.py` "범위 필터의 한계" 참조)
현재로선 적용할 수단이 없습니다. `$MFT`의 `MISMATCH_PAIRS`처럼 물리적
근거가 있는 판별자를 찾은 뒤에 좁혀야 하며, 근거 없이 임계값만 만지면
증거를 놓칩니다.

### 2026-08-24 · 프리패치 버전 30 / 220바이트 레이아웃 (실측)

키오스크 사고 이미지(`evidence/0824test.001`, 60GB VMware 물리 디스크,
볼륨 1)를 04단계로 돌렸더니 **프리패치가 137건 전부 `UnknownLayout`으로
빠졌습니다.** `docs/limitations.md`가 예고한 "새 빌드가 블록 크기를 바꾸면
그 시스템의 프리패치가 통째로 0건"이 실제로 일어난 것입니다. 조용하지는
않았습니다 — `parse_errors`와 로그에 `(버전 30, 파일 정보 220바이트)`가
그대로 찍혔습니다.

**이 이미지는 137건 전부가 `(30, 220)` 하나입니다.** 표에 있던
`(30, 216)`(1903 이상)도 `(30, 224)`(1809 이하)도 아닙니다.

#### 자리를 어떻게 정했나 — 추측이 아니라 대조

블록 크기는 파일이 말합니다(`메트릭 오프셋 - 헤더 84`). 나머지 자리는
137건을 훑어 **값의 성질로** 확정했습니다.

| 자리 | 값 | 무엇으로 확인했나 |
|---|---|---|
| `run_time_offset` | `0x2C` | 그 자리의 QWORD 8개가 FILETIME으로 그럴듯한 유일한 위치 |
| `run_count_offset` | `0x7C` | **유효 시각 개수와 정확히 일치** (아래) |
| `metrics_entry_size` | 32 | `트레이스오프셋 - 메트릭오프셋 = 1232-304 = 928 = 29 × 32` |
| `volume_entry_size` | 96 | v30·v31 공통값. 독립 스캐너 대조가 뒤를 받침 |

`run_count`가 결정적입니다. 유효한 실행 시각이 8개 미만인 파일에서
`0x7C`의 값이 **그 개수와 한 건도 빠짐없이 같았습니다**
(`IPCONFIG` 4/8→4, `BACKGROUNDTASKHOST` 3/8→3, `AUDIODG` 2/8→2 …).
8개가 다 찬 파일에서는 `0x7C`가 10·12·13으로 8을 넘습니다 — 시각 슬롯은
최근 8회만 남는 링버퍼이고 횟수는 계속 센다는 동작과 맞습니다.
후보였던 `0x80`은 개수와 무관하게 흩어졌고, `(30,216)`이 쓰는 `0x74`는
`0` 아니면 `1200000000`이라 둘 다 탈락했습니다.

#### 대조 결과 (`tools/scan_prefetch.py`)

이미지에서 `.pf` 137건을 뽑아 **파서와 다른 길**(메트릭 배열을 걷지 않고
문자열 블록을 널로 쪼개는 경로)로 읽어 맞췄습니다.

```
읽은 파일 137건 / 건너뛴 0건
버전 분포: 30=137
적재 파일 경로 총 10,195건
파일명 해시 불일치 0건 / 헤더 크기 불일치 0건
파서 출력 대조: 불일치 0건
```

#### 곁가지 — 스캐너의 헤더 크기 대조가 늘 틀렸다

처음 돌렸을 때 **헤더 크기 불일치가 137/137**로 나왔습니다. 파서 문제가
아니라 `scan_prefetch.py`가 헤더의 크기(압축을 푼 `.pf`의 크기)를
`path.stat().st_size`(온디스크 **압축** 크기)와 비교했기 때문입니다.
Win10 이후 `.pf`는 전부 `MAM` 압축이라 **이 검사는 구조적으로 항상
실패**했고, 그래서 진짜 크기 어긋남을 가리고 있었습니다. 해제된 바이트

`$UsnJrnl`의 0바이트 껍데기와 같은 부류입니다 — 검사가 돌고, 답이 나오고,

### 2026-08-24 · evtx 채널 확장 (Firewall / BITS / NetworkProfile)

키오스크 사고 이미지에서 "외부 서버로 데이터를 보냈는가"에 답할 수 없다는
것이 드러나 카탈로그를 늘렸습니다. **파서는 새로 만들지 않았습니다** —
채널만 다르고 온디스크 형식이 같아 `EvtxParser`를 그대로 씁니다.

#### 대조 — 범위 없이 읽은 히스토그램과 04단계 산출물

같은 파일을 두 번 읽습니다. 한 번은 `Scope()`(제한 없음)로 전량을 읽어
EventID 히스토그램을 만들고, 한 번은 03단계가 준 `event_ids` 범위로
파이프라인을 돌립니다. **범위 밖을 빼먹거나 더 넣으면 두 수가 갈립니다.**

| 아티팩트 | 전량 | 요청 ID 합계 | 04단계 산출물 | 일치 |
|---|---|---|---|---|
| `evtx:Firewall` | 394 | 381 | 381 | ✓ |
| `evtx:BITS` | 118 | 92 | 92 | ✓ |
| `evtx:NetworkProfile` | 30 | — | (Tier 2, 미요청) | — |

함께 확인한 것: 산출물에 **요청 밖 EventID가 한 건도 섞이지 않음**,
`ref` 접두어가 아티팩트별로 일관(`EVTX-FW#` / `EVTX-BITS#`), `ref` 유일.
마지막 둘은 인스턴스를 공유했을 때 깨지는 성질입니다 — 공유하면 한 채널의
레코드가 다른 접두어로 나가고 06단계가 그것을 환각으로 셉니다.

전량 히스토그램 상위:

```
Firewall : 2004=368  2006=8  2010=8  2002=5  2003=5
BITS     : 59=30  3=18  61=16  60=14  4=14  209=8
```

#### 값이 실제로 담기는지

`evtx:BITS` 이벤트 59의 `fields`에 **`url`이 그대로 들어옵니다.**

```
{"transferId": "{da68c0bd-...}", "name": "Font Download",
 "url": "https://fs.microsoft.com/fs/windows/config.json", ...}
```

"어디로 갔는가"가 남는 몇 안 되는 자리이고, 이것이 이 채널을 넣은 이유입니다.

#### EventID는 채널을 가려야 한다

`_flags.yaml`의 새 룰 셋은 기존 evtx 룰과 달리 `evtx:*`가 아니라 **정확한
아티팩트 이름**으로 겁니다. 실제로 겹치기 때문입니다 — NetworkProfile의
`10000`(네트워크 연결)은 `T1200` 매핑이 `evtx:System`에 요청하는 Kernel-PnP
`10000`과 번호가 같습니다. `evtx:*`로 걸면 장치 구성 이벤트에
`network_state_changed`가 붙습니다. `T1200.yaml`에도 같은 이유로 주석을
남기고 NetworkProfile을 Tier 2로 따로 적었습니다.

#### 등록 지점이 넷이 아니라 다섯이었다

`add-parser` 스킬은 등록 지점을 넷으로 적고 있는데, evtx는 하나 더
있습니다 — `parsers/evtx.py`의 `CHANNEL_FALLBACK`입니다.
`EvtxParser.__init__`이 여기 없는 아티팩트를 거부하므로 카탈로그·등록소만
고치면 **import 시점에 죽습니다.** 조용하지는 않지만 어디를 고쳐야 하는지가
드러나지 않아 스킬과 파일 주석 양쪽에 적었습니다.

사고 시간창(06:55:09~06:57:38) 안: 방화벽 **0건**, BITS **0건**.
다만 `$MFT`에서 BITS 작업 큐 파일 넷(`qmgr.db`·`edb.log`·`edb.chk`·
`qmgr.jfm`)이 **그 창 안에서 수정**됐습니다. 큐는 만져졌는데 전송 작업

## 2026-08-25 · $SI 서브초 0 정렬의 오탐률 (실측)

`timestamp_truncated` 플래그를 넣기 전에 실물 두 이미지의 `$MFT` 전체를

잡힙니다.

**룰이 아니라 픽스처를 고쳤습니다.** 실물에 그런 파일이 없다는 것이 위

```bash
import sys; sys.path.insert(0, '.')

    fr = [x for x in fr if x]
    if fr and all(set(x) == {"0"} for x in fr):

print(f"{aligned}/{n}")
EOF
```

| `Root\InventoryApplicationFile\{hash}` | 29 | `LowerCaseLongPath`·`FileId`·`ProgramId`·`Size`·`BinFileVersion`·`BinaryType`·`LongPathHash` |

work.md 는 "이 이미지의 레이아웃은 `Root\File` 이고
`InventoryApplicationFile` 이 아니다"라고 적어 두었는데, **둘이 함께
있었습니다.** 그래서 한쪽을 다른 쪽의 정답지로 쓸 수 있습니다.

### 대조 방법과 결과

증거: `evidence/0824test.001` 볼륨 1 (Windows 10 Pro, 빌드 15063).
`registry:Amcache` 392건.

`101` 을 `FileId` 로 보고 두 집합을 **1:1 로 조인**했습니다. 29건 전부가
맞물렸고(즉 `101` = `FileId` 가 그 자체로 확인됨), 맞물린 29건에서:

```
15  == LowerCaseLongPath   29 / 29   (대소문자 무시)
6   == Size (16진수 → 정수) 29 / 29
100 == ProgramId           28 / 29
```

- 판정: **통과** (`15`·`6`·`101`), **부분 통과** (`100`)

**원인 / 조치**

- `100` 의 한 건은 두 저장소가 같은 파일을 다른 `ProgramId` 에
  귀속시킨 것으로 보이나 **확인하지 못했습니다.** 28/29 를 근거로
  매핑에 넣었고, 이 한 건은 아는 오차로 남깁니다.
- **`17`·`b`·`10`·`16` 은 매핑하지 않았습니다.** 이 이미지 안에 대조할
  상대가 없습니다. 공개 자료에 대응표가 있으나 그것으로 채우면 틀렸을 때
  조용히 틀립니다. `17` 은 FILETIME 이고 360건 전부에 있어 값이 커
  보이는데, **$MFT 의 같은 경로 타임스탬프와 대조하면 이 이미지 안에서
  확정할 수 있습니다** — 아직 하지 않았습니다.
- 키 이름은 `LongPathHash` 가 **아닙니다** (0/29). 조인 키로 쓰지
  마십시오.
- `10` 은 `BinaryType` 이 아닙니다 (0/29). `10` 은 정수 `9` 이고
  `BinaryType` 은 `"PE64_AMD64"` 문자열입니다.

### 곁가지 — 대소문자가 두 레이아웃에서 다르다

`InventoryApplicationFile` 의 `LowerCaseLongPath` 는 이름 그대로 전부
소문자인데, `Root\File` 의 `15` 는 **대소문자가 살아 있습니다**
(`C:\Program Files\VMware\...`). 위 29/29 는 대소문자를 무시한 비교입니다.
그래도 04단계는 `15` 를 `LowerCaseLongPath` 로 내보냅니다 — 근거는
`parsers/registry.AMCACHE_FILE_VALUE_NAMES` 에 있습니다.

### 곁가지 — 이 대조가 06단계의 구멍을 하나 더 드러냈다

`PATH_FIELDS` 에 `lowercaselongpath` 가 없었습니다. 즉 **이름이 원래부터
있던 `InventoryApplicationFile` 29건도** 경로 필드로 인식되지 않아, 소문자
저장값과 모델이 쓰는 `C:\Program Files\...` 가 정확 문자열 비교로 갈렸습니다.
V36 이 가리키던 것은 `Root\File` 하나였지만 구멍은 Amcache 전체였습니다.

## 2026-08-27 · SRUM(`SRUDB.dat`) · dissect.esedb 어댑터 (최초)

증거: `evidence/0824test.001` 볼륨 1 (Windows 10 Pro, 빌드 15063).
`Windows\System32\sru\SRUDB.dat` 640KB.

- 공급자 테이블 3종 423건 (NetworkUsage 76 / AppResourceUsage 341 /
  NetworkConnectivity 6)
- 스키마 위반 0건
- 판정: **통과**

**외부 도구 대조는 하지 않았습니다.** 아래 셋은 그 대신 **파일 자신이
들고 있는 값**과 맞춰 본 것입니다 — 프리패치에서 헤더 해시와 .pf 파일명을
맞춰 본 것과 같은 방식입니다.

### 대조 1 — 시각 인코딩이 서로를 지지한다

`TimeStamp` 는 FILETIME 이 **아닙니다.** ESE 의 `JET_coltyp.DateTime`,
즉 OLE Automation date 입니다. FILETIME 으로 읽으면 `OverflowError` 입니다.

같은 DB 의 `ConnectStartTime` 은 **진짜 FILETIME** 입니다. 둘은 인코딩이
독립인데 같은 시각대를 가리킵니다:

```
TimeStamp        4676398138920708779  →(OLE)      2022-10-24 15:30:00.000000+00:00
ConnectStartTime  133110989883930110  →(FILETIME) 2022-10-24 15:29:48.393011+00:00
                                                          차이 12초
```

우리 해석이 틀렸다면 두 값이 같은 12초 안에 떨어질 이유가 없습니다.

**밟은 함정** — `dissect.esedb` 는 `DateTime` 컬럼을 **원시 int64 로**
돌려줍니다. `float(값)` 을 씌우면 같은 크기의 실수가 될 뿐이고, 그
8바이트를 **IEEE 754 double 로 다시 읽어야** 44858.6458... 이 나옵니다.
처음에 이것을 놓쳐 **76건 전부가 `timestamp` 없이** 나갔습니다. 조용한
실패였습니다 — 파싱은 성공했다고 보고되는데 레코드가 타임라인에 못 놓입니다.

### 대조 2 — 페이지 → 파일 오프셋 공식

라이브러리를 써도 `offset` 을 포기하지 않았습니다(`parsers/base.py` 의
세 가지 중 둘째). ESE 의 논리 페이지 `n` 은 파일의 `(n + 1) * page_size`
에 있습니다 — 앞의 두 페이지가 DB 헤더와 그 그림자이기 때문입니다.

**추측하지 않고 확인했습니다.** 76건 전부에서 그 위치의 파일 바이트가
라이브러리가 들고 있는 페이지 버퍼와 정확히 일치했고, 보정 없는
`n * page_size` 는 어긋났습니다.

```
(page.num + 1) * page_size 가 실제 바이트와 일치: 76 / 불일치 0
대조군 page.num * page_size 일치?               False
```

**페이지 단위입니다.** ESE 레코드는 페이지 안에서 태그로 가리켜지고
압축된 키 접두어를 공유해서, 레코드 하나의 시작 바이트를 파일 좌표로
말하는 것이 evtx 만큼 깔끔하지 않습니다. 페이지 위치까지가 정직하게
말할 수 있는 범위이고, 4KB 페이지와 `AutoIncId` 가 있으면 되짚어집니다.

### 대조 3 — `AppId` 풀기

사용량 테이블의 `AppId`·`UserId` 는 정수이고 문자열은 `SruDbIdMapTable`
에 있습니다. 실측 `IdType` 분포는 0=실행 파일 경로 또는 의사 이름(126),
1=서비스 이름(18), 2=패키지·서비스 식별자(114), 3=사용자 SID(107)였고,
`IdIndex` 는 타입과 무관하게 유일했습니다(겹침 0건).

NetworkUsage 76건 중 **73건이 풀렸습니다.** 남은 3건은 우리 실패가
아닙니다 — `IdIndex` 1(앱)과 2(사용자)의 `IdBlob` 이 **DB 안에서 이미
`None`** 입니다. 파서는 정수를 남기고 `unresolved_app_id` 로 셉니다.

`IdType` 3 은 UTF-16 문자열이 아니라 **바이너리 SID** 입니다. 문자열로
읽으면 깨진 글자가 보고서에 실립니다. `S-1-5-18`(SYSTEM)이 정상적으로
나오는 것을 확인했습니다.

### 클린 셧다운이 아니어도 열린다

곁에 `SRU.log`·`SRUDB.jfm` 이 있었습니다 — 로그가 반영되지 않은 상태
입니다. `dissect.esedb` 가 그대로 열었고 423건이 나왔습니다. 로그를
재생하지 않으므로 **가장 최근 기록 일부가 빠져 있을 수 있습니다**
(`docs/limitations.md`).

### 곁가지 — 앱 경로가 장치 이름이다

`IdType` 0 의 값은 `\Device\HarddiskVolume4\Windows\System32\smss.exe`
형태입니다. 프리패치와 같은 부류인데 **바꿀 근거가 없습니다** — SRUM 에는
볼륨 표가 없어 `HarddiskVolume4` 가 분석 중인 볼륨인지 알 수 없습니다.
그대로 둡니다(프리패치 파서와 같은 판단). 대가는 06단계입니다.

## 2026-08-27 · Amcache 숫자 값 이름 — 공개 출처 둘로 마저 채웠다

앞 절에서 이미지 안의 조인으로 넷(`15`·`6`·`100`·`101`)만 확정하고
나머지를 숫자로 남겼습니다. 그러면 **360건 전부에 있는 타임스탬프(`17`)를
못 씁니다.** 공개 출처를 찾아 채웠습니다.

### 출처 둘 — 계보가 다르다

| 출처 | 형태 | 자리 |
|---|---|---|
| AmcacheParser (Eric Zimmerman, MIT, C#) | 소스 | `Amcache/AmcacheOld.cs` 의 `private const int` 목록 |
| Plaso / log2timeline (Python) | 소스 | `plaso/parsers/winreg_plugins/amcache.py` |

**겹치는 항목에서 둘이 어긋나는 곳이 하나도 없었습니다.** 그리고 우리가
이미지 안에서 독립적으로 확인한 넷이 양쪽과 전부 일치합니다 — 서로를
지지하는 세 번째 축입니다.

값 이름은 **16진수**입니다(`int.Parse(name, NumberStyles.HexNumber)`).
`a`·`b`·`f` 가 그래서 나옵니다.

### `17` 을 `$MFT` 로 확인했다

공개 출처만 믿지 않고 이미지 안에서 한 번 더 걸렀습니다. `15`(전체 경로)로
`$MFT` 레코드와 짝을 짓고, `17` 을 FILETIME 으로 읽어 타임스탬프 넷과
비교했습니다.

```
경로로 짝지은 것 335 / 360

  17 이 si_mtime 과 2초 이내   329 / 335  (98%)
  17 이 si_btime 과 2초 이내   328 / 335  (98%)
  17 이 si_ctime 과 2초 이내   154 / 335  (46%)
  17 이 fn_mtime 과 2초 이내   154 / 335  (46%)

표본:
  ...vmware vgauth\ssleay32.dll  17=2020-03-30 06:28:34  si_mtime=2020-03-30T06:28:34
```

- 판정: **`17` 은 파일의 타임스탬프다** (레지스트리 쪽 시각이 아니다)

### 왜 뒤집었나 — 비교가 목록에서만 성립하지 않았다

`win10_sysmon_testimage.001` (볼륨 1), 프리패치 127건 · 적재 경로

### 규칙은 새로 만들지 않았다

`_to_drive()` 를 목록에도 거는 것이 전부입니다. 그 함수는 이미 조건부라

정확히 하나일 때만 바꾸고(`device_prefixes()`), 접두어가 안 맞는 것은
그대로 둡니다.

바뀐 항목 수는 `stats["loaded_paths_converted"]` 로 셉니다. 레코드는
나오는데 이 수가 0이면 접두어를 못 알아본 것이고, 위의 100% 가 정확히
그 증상이었습니다.

### 대조 — 다른 길로 읽은 것과 맞췄다


(`_strip_volume`) — 이 대조가 보려는 것은 접두어가 아니라 개수와
내용이고, 접두어를 맞추라고 하면 파서가 정상일 때도 전량이 불일치로
나와 진짜 어긋남을 가립니다. 뗄 때 쓰는 정규식은 파서 것을 빌리지 않고
따로 씁니다.

### 섀도 카피는 실물로 못 봤다

2026-08-25 절과 같은 이유).

### `$MFT` 는 업데이트 시퀀스가 가장 강한 증거였다

번호 대조만으로는 부족합니다 — 엉뚱한 자리의 4바이트가 우연히 그 번호일
수 있습니다. NTFS 는 **각 섹터의 마지막 2바이트를 같은 USN 으로 덮어
쓰므로**, 오프셋이 한 섹터라도 밀려 있으면 그 값들이 서로 달라집니다.
40건 전부에서 섹터 2개(섹터 크기 512)의 끝 2바이트가 같았습니다.

**되돌리지 않고 확인만 합니다.** 덤프는 fixup 전의 디스크 원본이어야
합니다. 되돌린 바이트를 보여 주면 그것은 이미 우리가 손댄 값입니다.

### `$UsnJrnl` — 오프셋과 USN 이 전건 같았다

`usnjrnl.py` 는 *"추출 도구가 스파스 구간을 잘라냈다면 `record_num` 과
어긋나는데, 그 차이 자체가 이 파일은 원본 스트림이 아니다라는 신호"* 라고
적어 두었습니다. **이 이미지에서는 40건 전부 `offset == record_num`
입니다** — 볼륨에서 직접 읽었으니 당연하지만, 그 당연함이 처음으로
확인됐습니다. 추출본으로 돌렸을 때 이 값이 갈리면 그것이 진단입니다.

### 프리패치 127건이 전부 MAM 압축본이었다

Win10 이라 예상대로입니다. `offset` 이 항상 `0x0` 이고 헤더가 압축돼
있어, 되짚기는 **파일명 뒤 8자리 = `record_num`** 으로만 성립합니다.
그 값도 Windows 가 쓴 것이라 독립적인 대조입니다.

### SRUM — 페이지 크기를 추측하지 않는다

`srum:*` 의 `offset` 은 레코드가 아니라 **레코드가 실린 ESE 페이지**입니다
(`parsers/srum.py` 의 `_file_offset`). 대조도 페이지까지만 성립하고, 도구가
그 한계를 출력에 싣습니다.

**그 안에서는 조였습니다.** 처음에는 "4096의 배수인가"만 봤는데 그것은
대조가 아니라 장식입니다 — 페이지가 8KB 인 DB 에서는 엉뚱한 오프셋의
절반이 그대로 통과합니다. 지금은 **ESE 데이터베이스 헤더가 말하는 값**을
씁니다.

| 헤더 자리 | 실측값 (`SRUDB.dat`, win10_sysmon_testimage) |
|---|---|
| `0x04` 매직 | `0x89ABCDEF` |
| `0xEC` `cbDbPage` | 4096 — `dissect.esedb` 의 `db.page_size` 와 같은 값 |

여기에 **앞의 두 페이지(DB 헤더와 그 그림자)에는 레코드가 있을 수 없다**는
것과 페이지가 파일 안에 있다는 것을 더해 넷을 봅니다.
`parsers/srum.py` 의 `PAGE_NUMBER_BIAS = 1` 을 반대쪽에서 확인하는 셈입니다.

`SRUM-CONN` 3건은 오프셋이 셋 다 `0x60000` 입니다 — 같은 페이지에 실렸다는
뜻이고, 그것이 페이지 단위 대조의 한계를 그대로 보여 줍니다. 그 안에서
레코드를 가르는 것은 `AutoIncId` 입니다.

**이 대조는 하마터면 못 할 뻔했습니다.** `dissect.esedb` 가

`ParseError` 로 멈췄습니다. 설치 후 2.1초에 238건이 나왔습니다.

## 2026-09-02 · SQLite 엔진 × `sqlite3` — 이미지 둘의 실물 64개 전수 대조

SQLite 파서를 만들기로 하고(`work.md` 2-3), 페이지·셀을 직접 걷는 엔진을

했는데 여기서는 `sqlite3` 가 그 자리를 그대로 맡습니다.

`tools/scan_sqlite.py` 가 같은 파일을 양쪽으로 읽어 테이블·컬럼 이름·행을
rowid 로 맞춰 봅니다. `immutable=1` 로 열어 **WAL 을 읽지 않게** 합니다 —
우리 엔진도 본 DB 만 보므로 같은 조건이어야 합니다(증거에 쓰지 않는다는
뜻이기도 합니다).

### 대조 대상을 먼저 셌다

이름이 아니라 **헤더 매직**으로 판정했습니다. 브라우저 `History` 처럼
확장자가 없는 것이 많아 이름으로 찾으면 놓칩니다.

|---|---|---|---|
| `0824test.001` (Win10) | 113,523 | **22** | 브라우저 History·`ActivitiesCache.db` 는 없다 |
| `windows7_testimage.001` | 78,546 | **42** | 전부 HP 프린터 `.vdf` (DriverStore/winsxs 사본) |

Win10 쪽에서 나온 것 — `wpndatabase.db`(알림), `StateRepository-*.srd`(앱·
패키지 상태), OneDrive 동기화 DB 14개, `configuration.sqlite`(utf-16le),
Photos `MediaDb.v1.sqlite`.

### 결과 — 전수 일치

```

페이지 크기 512 / 1024 / 4096 / 32768   인코딩 utf-8 / utf-16-le
```

같은 파일을 다른 구현으로 읽어 값이 전부 같으므로, 넘침 계산·serial type
크기·`INTEGER PRIMARY KEY` 채워 넣기·컬럼 이름 추출이 **동시에** 지지됩니다.

### 실물이 잡아 준 것 넷 — 전부 조용히 틀리는 부류였다

합성 픽스처는 통과하는데 실물에서 드러난 것들입니다.

1. **`GENERATED ALWAYS AS (...) VIRTUAL` 컬럼은 레코드에 저장되지 않는다.**
   세면 그 뒤 컬럼 이름이 **전부 한 칸씩 밀립니다** — 값은 멀쩡하고 이름만
   남의 것이 붙으므로 눈으로는 안 걸립니다. `STORED` 는 저장되므로 셉니다.
   (`Microsoft.LocalContent.db` 의 `WatchedRootFolders.FullPath`)
2. **키워드와 대괄호 사이에 공백이 없는 SQL 을 Windows 가 쓴다** —
   `CONSTRAINT[] PRIMARY KEY([Key])`, `UNIQUE([Id])`. 공백으로 잘라 첫
   토큰을 보면 걸러지지 않아 제약이 컬럼으로 둔갑합니다.
   (`wpndatabase.db` 의 테이블 6개 전부)
3. **`CREATE TABLE` 안에 `--` 주석이 있다.** 주석 한 줄이 이름 없는 컬럼이
   되고, 같은 조각에 붙어 있던 `PRIMARY KEY(...)` 가 제약으로 인식되지
   않습니다. (`Microsoft.LocalContent.db` 의 `PathPeriodicRetry`)
4. **헤더의 페이지 수가 0인 파일이 실재한다.** Win7 의 `.vdf` 42건이
   그렇습니다. 변경 카운터(`0x18`)와 `0x5C` 가 다르면 헤더 값이 낡은
   것이므로 파일 크기로 셉니다.

대조 도구 자신도 한 번 틀렸습니다 — `text_factory=bytes` 로 받으면 텍스트와
BLOB 의 구별이 사라져 BLOB 을 UTF-8 로 풀어 놓고 "값이 다르다"고 말했습니다.
기본값을 그대로 쓰면 `str`/`bytes` 가 우리 엔진의 표현과 그대로 맞습니다.

### 양쪽이 다르게 보는 자리 하나 — 어느 쪽도 틀린 게 아니다

`ALTER TABLE ADD COLUMN` 으로 컬럼이 늘기 **전에** 쓰인 레코드는 뒤 컬럼이
디스크에 아예 없습니다. `sqlite3` 는 그 자리를 컬럼 기본값으로 채워 주고,
우리 엔진은 디스크에 있는 것만 냅니다. 대조에서는 `PRAGMA table_info` 의
`dflt_value` 로 채워 비교합니다 — 기본값이 `NULL` 이라고 가정하면 안 됩니다
(`SyncEngineDatabase.db` 에 기본값이 `''` 인 컬럼이 있었습니다).

### 되짚는 방법 — 시그니처가 없는 아티팩트다

어긋나도 varint 해석이 통째로 달라져 우연히 맞기 어렵습니다.

### 시각 인코딩을 실물로 정했다

| 아티팩트 | 컬럼 | 인코딩 | 실측 |
|---|---|---|---|
| StateRepository | `PackageUser.InstallTime` | FILETIME | 152/152행 채워짐 |
| StateRepository | `Package._Created`·`_Modified` | — | **전부 0. 쓰지 않는다** |
| Notifications | `Notification.ArrivalTime` | FILETIME | 15/15행 |
| Notifications | `NotificationHandler.CreatedTime` | 텍스트 | `'2022-10-24 15:32:53'` |

**한 DB 안에서 인코딩이 갈립니다.** 프로파일이 필요한 이유가 이것입니다.

`Package._Created` 는 컬럼이 있는데 값이 0 입니다. 있다고 믿고 적으면
1601년이 타임라인에 실립니다 — 컬럼의 존재가 아니라 **값을 봐야** 합니다.

### 텍스트 시각이 UTC 라는 근거 — 두 인코딩이 서로를 지지한다

`NotificationHandler.CreatedTime` 은 시간대 표기가 없습니다. 같은 DB 의
`Notification.ArrivalTime` 은 FILETIME 이라 정의상 UTC 인데, 실측에서
텍스트가 `15:32:53`, 이웃한 FILETIME 이 `15:34:00` 이었습니다. **1분
차이**입니다 — 텍스트가 현지 시각(KST)이었다면 9시간이 어긋납니다.
SRUM 의 OLE/FILETIME 대조와 같은 논리입니다.

### 참조를 풀지 않으면 한 줄로는 쓸모가 없다

`PackageUser` 가 설치 시각을 들고 있고 무엇이 설치됐는지는 `Package` 에
있습니다. **05단계는 레코드를 한 건씩 모델에 보내므로 조인을 그때 할 수
없습니다.** SRUM 이 `AppId` 를 `SruDbIdMapTable` 로 풀었던 것과 같은
처리를 넣었습니다.

```
풀기 전: PackageUser.Package = 182, InstallTime = 133110991735785285
풀은 뒤: Microsoft.AAD.BrokerPlugin_1000.15063.0.0_neutral_neutral_cw5n1h2txyewy
         2022-10-24T15:32:53Z
```

알림도 같습니다 — `Notification.HandlerId` 를 풀면
`microsoft.windowscommunicationsapps...!microsoft.windowslive.mail` 이
`2022-10-24T15:34:00Z` 에 알림을 띄웠다가 한 줄로 읽힙니다.

실물에서 **1,004건 전부 `name` 이 채워졌습니다**(풀지 못한 참조 0건).

### 사용자 프로필 경로 — `relative_paths` 로는 표현할 수 없었다

`wpndatabase.db` 는 `Users/<사용자>/AppData/...` 에 있습니다. 고정 문자열
경로로는 못 잡아 `ArtifactLocation.user_paths` 를 넣었습니다.

**프로필이 여럿이면 하나를 고르고 나머지는 `alternates` 로 매니페스트에
남깁니다.** 전부 읽지 않는 이유는 `ref` 입니다 — 레코드 번호가 셀의 파일 내
오프셋이라 파일이 둘이면 같은 번호가 두 번 나옵니다. 프리패치는 헤더의

있었지만, SQLite 에는 그런 값이 없습니다.

스스로 적어 둔 규칙이 정확히 여기서 깨져 있었습니다. 이런 오탐은 조용히
틀리는 것보다 나쁩니다 — **멀쩡한 파서를 고치러 가게 만듭니다.**
