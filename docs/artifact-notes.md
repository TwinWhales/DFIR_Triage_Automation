# 온디스크 구조 조사 메모

파싱하면서 확인한 사실과, **기존 도구와 어긋난 지점과 그 원인**을 쌓는
문서입니다. 진행 중 누적됩니다.

여기 쌓인 내용이 팀의 학습 성과물이자, 발표에서 "직접 구현했다"를
뒷받침하는 근거입니다. 스펙 문서를 옮겨 적는 곳이 아니라 **실제 데이터에서
겪은 것**을 적는 곳입니다.

---

## 대조 기록

`work-guide.md` 3.2가 필수로 정한 절차입니다. 파서를 고칠 때마다 돌리고
결과를 여기 남깁니다.

```bash
MFTECmd.exe -f "<evidence>\$MFT" --csv out --csvf mft.csv
.venv/Scripts/python.exe tools/compare_mft.py --ours cases/<id>/04_parsed/mft.jsonl --mftecmd out/mft.csv --full
```

`--full`은 범위 없이 돌린 출력에 씁니다. 선별 범위만 낸 결과에는 붙이지
마십시오 — MFTECmd에만 있는 레코드가 전부 오류로 잡힙니다.

### 기록 형식

`compare_mft.py`의 요약을 그대로 붙이고, **원인**을 덧붙입니다.
수치만 남기면 나중에 같은 실수를 반복합니다.

```markdown
### 2026-08-__ · $MFT · <파서 버전이나 커밋>

- 우리 레코드 0건 / MFTECmd 0건
- 값 불일치 0건
- 판정: 통과

**원인 / 조치**

```

#### 2026-08-19 · evtx · python-evtx 어댑터 (최초)

**이 프로젝트 최초의 진짜 외부 도구 대조입니다.** `$MFT`·`$UsnJrnl`은
자체 정답지로 대신했지만, evtx는 `wevtutil`이 모든 Windows에 들어 있어
준비물이 없습니다. 마이크로소프트 자신의 파서라 **공통 오해가 생기지
않습니다** — 같은 사람이 짠 두 구현을 비교하던 한계가 여기서는 없습니다.

```bash
wevtutil epl Application <사본>.evtx          # 라이브 로그는 잠겨 있어 사본을 뜬다
wevtutil qe <사본>.evtx /lf:true /f:xml       # 정답지
```

대조 대상 8,257레코드(Application 로그, 7.4MB, 103청크).

| 항목 | 결과 |
|---|---|
| 레코드 수 | 8,257 / 8,257 **일치** |
| EventRecordID 집합 | 차이 **0건** |
| `event_id` | 불일치 **0건** |
| `computer` | 불일치 **0건** |
| 타임스탬프(초까지) | 불일치 **0건** |
| 타임스탬프(100ns 자리) | 8,257건 전부 0~+9 차이 — 아래 참조 |

`offset`도 따로 확인했습니다. 200건을 뽑아 그 위치의 원본 바이트를 읽으니
**200/200이 레코드 매직(`2A 2A 00 00`)** 이었습니다. 근거 추적이 이 필드에
달려 있으므로 값이 그럴듯한 것만으로는 부족합니다.

**원인 / 조치**

- 처음에는 `record.timestamp()`를 그대로 썼습니다. 그랬더니 7,938건이
  **−1.6 µs ~ +2.8 µs** 어긋났고, 오차가 **양방향**이라 100ns 절삭으로는
  설명되지 않았습니다. python-evtx가 float로 변환하기 때문입니다.

  ```python
  # Evtx/BinaryParser.py — parse_filetime
  datetime.fromtimestamp(float(qword) * 1e-7 - 11644473600, timezone.utc)
  ```

  아래 "밟은 함정"에 이미 적혀 있는 문제를 **vendored 라이브러리가 다시
  들여온 것**입니다. 우리 `filetime_to_datetime`은 정수 연산만 씁니다.
  원시 FILETIME qword(레코드 오프셋 `0x10`)를 직접 읽어 그 함수로 넘기니
  차이가 **0~+9로 균일**해졌습니다. 이제 남는 것은 `datetime`이 마이크로초
  까지만 담아 생기는 100ns 절삭뿐이고, `$MFT`·`$UsnJrnl`과 같은 규약입니다.

  → **다른 사람이 wevtutil이나 EvtxECmd와 대조하면 마지막 자리가 다릅니다.
    파서 버그가 아닙니다.** 허용 오차가 초 단위라 판정에는 영향이 없습니다.

- `FileHeader.verify()`로 파일을 게이팅하려다 뺐습니다. **정상 로그에서도
  False가 납니다** — `wevtutil epl`로 갓 내보낸 로그(103청크,
  `is_dirty=False`)에서 확인했습니다. 이걸로 거부하면 멀쩡한 증거를 통째로
  버립니다. 파일 수준에서는 매직만 보고, 엄격한 판정은 청크 단위로 내린 뒤
  셉니다.

#### 2026-08-21 · prefetch · 자체 구현 (최초)

`evidence/[root]/Windows/Prefetch` 105개 항목 중 **.pf 82건(유효 73건 +

**원인 / 조치**
- 볼륨 정보 원소 크기를 96바이트로 잡았다가 **104바이트**로 고쳤습니다.
  단일 볼륨 파일에서는 첫 원소만 읽으므로 **73건 중 56건이 멀쩡히
  통과했고**, 섀도 카피를 함께 참조하는 17건에서만 두 번째 원소부터
  자리가 밀렸습니다. 그마저도 예외가 아니라 "볼륨 하나를 읽지 못했다"는
  경고로만 나타났습니다. 카운트 대조(`볼륨 개수 == 읽은 개수`)를 넣지
  않았으면 그대로 갔을 종류입니다.

## 확인한 구조

구조 정의는 `src/stage04_parse/structs/`에 있습니다. **그 파일의 오프셋 표는
스펙 대조 전 상태**이므로, 대조하면서 확인했거나 고친 것을 여기 적습니다.

### $MFT

#### timestamp_mismatch 판정은 **생성 시각만** 봐야 한다

가장 중요한 발견입니다. 초기 룰은 `$SI`가 `$FN`보다 이른 쌍이 **하나라도**
있으면 플래그를 붙였습니다. 방향(이르다)만 따지면 맞는 줄 알았습니다.

실제 이미지에서 측정한 결과:

| 비교 | 걸린 레코드 |
|---|---|
| `si_btime < fn_btime` (생성) | **0건** |
| `si_ctime < fn_ctime` | 91건 (59%) |
| `si_mtime < fn_mtime` | 91건 (59%) |
| 초기 룰 (셋 중 하나라도) | **91건 (59%)** |

**91건 전부 오탐이었습니다.** 154건 중 59%가 걸리면 필터로 쓸 수 없습니다.

원인은 파일 복사입니다. 복사하면 `$SI`의 ctime·mtime은 원본 값이 보존되고,
`$FN`은 새 디렉터리 항목이 만들어진 시각으로 설정됩니다. 실제 값:

```
si_btime = 2026-07-24T00:28:07.476   fn_btime = 2026-07-24T00:28:07.476  (같음)
si_ctime = 2026-07-23T08:51:16.954   fn_ctime = 2026-07-24T00:28:07.476  (다름)
```

"파일이 자기 이름 항목보다 먼저 존재할 수 없다"는 논리는 **생성 시각에만**
적용됩니다. ctime·mtime은 그 논리가 성립하지 않습니다.

→ `flagging.MISMATCH_PAIRS`를 `(("si_btime", "fn_btime"),)`로 좁혔습니다.
   같은 이미지에서 0건이 나옵니다(이 이미지에는 조작이 없으므로 맞는
   결과). 오탐 패턴은 `tests/test_flagging.py`에 회귀 테스트로 고정했습니다.

**교훈**: 추론으로 만든 룰은 실제 데이터에서 확인하기 전까지 믿을 수
없습니다. 이 룰은 합성 테스트를 전부 통과했습니다.

#### …그런데 시스템 볼륨에서는 좁힌 룰도 81%가 걸린다 (미해결)

**위 수정으로 끝난 줄 알았는데 아니었습니다.** 같은 룰을 실제 시스템
볼륨(`evidence/[root]`, Windows 7)에 돌리니 이렇게 나옵니다.

| 볼륨 | 대상 | `timestamp_mismatch` |
|---|---|---|
| `evidence/test` (데이터 볼륨) | 154 | **0건** |
| `evidence/[root]` (시스템 볼륨) | 2,034 (실행파일류) | **1,651건 (81%)** |

원인은 **OS 설치**입니다. 측정하면 바로 드러납니다.

- 걸린 것들의 `fn_btime`은 **서로 다른 "분"이 14개뿐**입니다.
  675건이 `2019-01-10T02:48`, 464건이 `02:47` — 설치 시각입니다.
- 같은 것들의 `si_btime`은 **167개 분에 흩어져** 2009~2010년입니다.
  `2009-07-13`(Windows 7 RTM), `2010-11-21`(SP1) 빌드 시각입니다.
- 표본: `C:\Windows\System32\msinfo32.exe`, `iexplore.exe`, `ielowutil.exe`
  — 전부 OS 기본 바이너리입니다.

즉 **Windows Setup이 `$SI`는 설치 미디어의 빌드 시각으로 보존하고
`$FN`은 디렉터리 항목을 만든 설치 시각으로 씁니다.** 그래서
`si_btime < fn_btime`이 OS 파일 전체에서 정상적으로 성립합니다.

앞의 복사 사례를 피하려고 btime으로 좁혔는데, **설치는 바로 그 btime을
보존합니다.** 좁힌 방향이 이 경우엔 효과가 없습니다.

**시도해 봤으나 검증되지 않은 판별자 둘** — 이 볼륨엔 실제 조작이 없어
참양성으로 확인할 수 없었습니다. 근거 없이 채택하면 안 됩니다.

- `si_btime` 소수부가 0인가 → 걸린 것의 **30.5%(503건)가 이미 0**입니다.
  MSI·ZIP처럼 초 단위만 보존하는 설치 경로가 많아 판별력이 약합니다.
- `fn_btime` 클러스터 바깥인가 → 1,651 → 9건으로 줄지만, 그 9건도 전부
  정상 소프트웨어 설치(VS Launcher, .NET SetupCache, VMware)였습니다.

**영향** — `$MFT`의 `timestamp_mismatch`가 시스템 볼륨에서는 필터 구실을
못 합니다. `record_filter.DEFAULT_LIMIT`이 60이므로 1,651건 중 60건만
05단계로 갑니다. `limitations.md` 4-2가 `$UsnJrnl`에 대해 적은 것과
**같은 문제이며, 이제 `$MFT`에도 해당합니다.**

#### `$FN`의 real_size는 파일 크기가 아니다

이름이 만들어진 시점의 크기라 나중에 쓰인 파일은 대부분 0입니다.
실제 크기는 `$DATA`에 있습니다(상주면 content_length, 비상주면 real_size).

#### 미사용 슬롯

256슬롯 중 154개만 유효했습니다. 나머지는 0으로 채워져 있어 시그니처
검사(`FILE`/`BAAD`)로 걸러집니다.

### $UsnJrnl

`evidence/$J`(33MiB, 355,850레코드)에서 확인한 것들입니다.

**저널 블록은 4096바이트입니다.** `[LIBFSNTFS]`가 열어 둔 질문
(*"seems to be 4096 bytes, but could this be defined by the index entry
size?"*)에 대한 실측 답입니다.

- 0 구간 7,616개가 **전부** 4096 경계에서 끝남 (`끝 % 4096 == 0`이 7,616/7,616)
- 4096 경계를 넘는 레코드 **0건** / 355,850건

즉 레코드는 블록을 가로지르지 않고, 블록 끝 자투리는 0으로 채웁니다.
0바이트 총 823,376(파일의 2.4%)이 전부 이 패딩입니다. 파서는 블록
크기에 의존하지 않고 0을 만나면 건너뛰는 방식이라 이 값이 달라져도
동작합니다 — 의존하지 않는 편이 낫다는 근거이기도 합니다.

**USN 값과 파일 오프셋이 어긋납니다.** 첫 레코드의 USN이 159,383,552인데
파일 오프셋은 0입니다. 추출본이 **스트림 앞부분이 잘려 나간 뒷도막**이기
때문입니다(저널이 최대 크기에 닿아 앞쪽이 스파스로 회수된 상태).

- 파일 안에서는 USN 증가분 = 오프셋 증가분 (34,164,232로 동일)
- 그래서 `record_num`(=USN)과 `offset`(=파일 위치)을 따로 기록합니다.
  둘의 차이가 곧 "잘려 나간 앞부분의 크기"입니다.

**이름** — 최장 154자(`...presentationframework-systemdata_...cdf-ms`),
한글 이름 정상 복원(`오픈소스_스튜디오`), 콜론이 든 ADS 이름은 없었습니다.
255자 상한에 한참 못 미쳐 `MAX_RECORD_SIZE = 4096` 여유는 충분합니다.

### EVTX

python-evtx를 씁니다. 직접 구현하지 않는 이유는 바이너리 XML + 청크
압축이라 난이도가 차원이 다르기 때문입니다(`work-guide.md` 3.1).

레코드마다 `absolute_offset`을 주는 것을 확인했으므로, 근거 추적 구조는
라이브러리를 써도 성립합니다.

Application 로그 8,257건에서 확인한 것들입니다.

#### `<EventData>`의 모양은 하나가 아니다

`<Data Name="X">`만 있을 거라고 가정하면 대부분을 놓칩니다.

| 모양 | 건수 | 비율 |
|---|---|---|
| 이름 없는 `<Data>` | 7,503 | **91%** |
| `<Data Name="X">` | 374 | 4.5% |
| `<EventData>` 없이 `<UserData>`만 | 266 | 3.2% |
| `<EventData>`가 빔 | 109 | 1.3% |
| `<Data>`와 `<Binary>` 혼재 | 5 | 0.1% |

**이름 없는 `<Data>`가 예외가 아니라 다수입니다.** Security 로그는 이름을
붙이는 이벤트가 많지만, 카탈로그에 채널을 더하면 이쪽이 늘어납니다.
그래서 `Data[0]`, `Data[1]`로 자리를 남깁니다 — USN의
`unknown_0x########`와 같은 이유로, 조용히 버리면 아무도 모릅니다.

`<UserData>` 하위는 **제공자 고유 네임스페이스**를 씁니다(실측:
`http://manifests.microsoft.com/win/2006/windows/WMI`). 기본 네임스페이스
하나로 못 박으면 이쪽이 통째로 안 읽힙니다.

#### chunk_count를 믿으면 꼬리를 잃는다

`FileHeader.chunks()`는 헤더가 선언한 `chunk_count`까지만 냅니다. 실측
파일은 물리 슬롯 113개 중 103개만 선언돼 있었고, 나머지 10개는 빈 공간이라
체크섬에서 걸러졌습니다.

문제는 **로그가 깨끗하게 닫히지 않은 경우**입니다. 그때 선언값이 실제보다
작으면 가장 최근 이벤트가 담긴 꼬리 청크가 조용히 빠지는데, 사고 대응에서
제일 보고 싶은 구간이 그쪽입니다. 그래서 `include_inactive=True`로 물리
슬롯을 전부 훑고 `verify()`로 거른 뒤, 선언 밖에서 살아난 청크를
`recovered_chunks`로 셉니다.

#### 라이브러리가 청크를 조용히 끊는다

`ChunkHeader.records()`는 레코드 하나가 깨지면 `InvalidRecordException`을
잡아 그냥 `return`합니다. **그 청크의 나머지가 통째로 사라지는데 아무 소리도
나지 않습니다.**

그래서 `Evtx.records()`를 쓰지 않고 청크를 직접 걸으며, 마지막 레코드의 끝이
청크가 선언한 `next_record_offset` 경계에 못 미치면 `parse_errors`로 셉니다.
정상 청크에서는 둘이 정확히 일치하는 것을 확인했습니다(`last_end == boundary`).

### 프리패치

온디스크 구조와 `MAM` 압축 해제 둘 다 자체 구현입니다. 파이썬에 이 압축을
푸는 표준 라이브러리가 없고, `ctypes`로 `RtlDecompressBufferEx`를 부르면
**Windows에서만 읽히는 아티팩트**가 되기 때문입니다 —
플랫폼에 따라 볼 수 있는 증거가 달라지면 "봤는데 없었다"와 "볼 줄 몰라
못 봤다"의 구분이 실행 환경에 좌우됩니다.

#### 버전마다 움직이는 것은 둘뿐이다

구조 전체가 버전마다 바뀌는 것처럼 보이지만 실제로 움직이는 것은 실행
시각·실행 횟수의 자리와 배열 원소 크기뿐입니다. **파일 정보 블록 앞머리
9개 dword(0x00~0x23)는 모든 버전에서 같은 자리**라, 적재 파일 목록과
볼륨 정보는 버전과 무관하게 한 경로로 읽힙니다.

그래서 `FILE_INFORMATION` 표를 **(버전, 블록 크기)**로 찾습니다. 블록
크기는 표에서 가져오지 않고 **파일이 말하는 값**(메트릭 배열 오프셋 -
헤더 84)을 씁니다. 버전 30은 Windows 10 빌드에 따라 이 값이 달라
버전 번호만으로는 자리를 정할 수 없습니다.

| 버전 | Windows | 블록 | 실행 시각 | 볼륨 원소 | 확인 |
|---|---|---|---|---|---|
| 17 | XP/2003 | 68 | 1개 | 40 | 명세 |
| 23 | 7 | 156 | 1개 | **104** | **실측 73건** |
| 26 | 8.1 | 224 | 8개 | 104 | 명세 |
| 30 | 10 | 224 / 216 | 8개 | 96 | 명세 |
| 31 | 11 | 224 | 8개 | 96 | 명세 |

표에 없는 조합은 **추측하지 않고 그 파일만 건너뜁니다**(`UnknownLayout`).
실행 횟수 자리를 잘못 잡으면 예외도 경고도 없이 그럴듯한 숫자가 나오고,
그것이 보고서에 "3회 실행됨"으로 실립니다.

명세를 잘못 옮겼을 때를 대비해 값의 앞뒤도 봅니다 — 실행 횟수가 100만을
넘거나 실행 시각이 1995년보다 이르면 레코드를 내지 않습니다. 자리가
어긋나면 FILETIME 여덟 개가 전부 그럴듯하게 나올 확률이 낮다는 것에
기댄 검사입니다.

#### 경로는 드라이브 문자가 아니라 장치 이름이다

.pf 안의 경로는 `\DEVICE\HARDDISKVOLUME2\WINDOWS\SYSTEM32\CMD.EXE`
형태입니다. 03단계의 `path_prefix`는 `C:\...` 형태라 **그대로는 절대
매칭되지 않습니다.**

섀도 카피가 아닌 `HARDDISKVOLUME<n>`이 **정확히 하나일 때만** 드라이브
문자로 바꿉니다. 한 실행은 한 볼륨이므로 그 하나가 곧 분석 중인 볼륨입니다.
둘 이상이면 어느 쪽인지 알 방법이 없어 바꾸지 않습니다.

실측 73건 중 **17건이 섀도 카피를 함께 참조**했습니다
(`HARDDISKVOLUMESHADOWCOPY1~3`). 섀도 카피 안의 파일은 살아 있는 볼륨의
그 경로가 아니므로 바꾸지 않습니다. 원본 경로는 `fields.loaded_files`에
손대지 않은 채로 남고, 바꾼 값은 `path` 하나뿐입니다.

#### 실행 파일 이름은 29자에서 잘린다

헤더의 이름 자리는 60바이트(UTF-16LE 29자 + 널)입니다. 전체 경로는 적재
파일 목록 안에 있으므로 이름이 맞는 항목을 찾는데, **정확 일치를 먼저 보고
없을 때만 접두어로 내려가야 합니다.** 둘을 한 목록에 섞으면 이름이 29자인
실행 파일이 자기 `.config`까지 후보로 끌고 와 "후보가 둘이라 모르겠다"가
됩니다. 실측에서 그런 파일이 둘 있었습니다.

## 밟은 함정

구현하면서 놓쳤거나 헤맨 지점. **다음 사람이 같은 데서 막히지 않게**
적습니다.

### fixup(업데이트 시퀀스)을 되돌리지 않으면

NTFS는 각 섹터의 마지막 2바이트를 USN으로 덮어씁니다. 되돌리지 않으면
512바이트마다 2바이트가 엉뚱한 값인데, **레코드 대부분은 멀쩡해서 원인을
찾기 어렵습니다.** 경로 문자열이 중간에 깨지거나 타임스탬프가 이상해집니다.

→ `structs/mft_record.py`의 `apply_fixups()`로 처리. 속성을 읽기 **전에**
   반드시 부릅니다.

### $FILE_NAME의 부모 참조는 하위 48비트만

상위 16비트는 시퀀스 번호입니다. 마스킹을 빼먹으면 부모를 못 찾아 경로가
끊깁니다.

### 8.3 단축 이름을 고르면 경로가 이상해짐

한 파일이 `$FN`을 여러 개 가질 수 있습니다. DOS 이름공간을 고르면
`PROGRA~1` 같은 값이 나옵니다. `WIN32` 또는 `WIN32_AND_DOS`를 우선합니다.

### FILETIME 변환에 float를 쓰면 정밀도가 깨짐

`timedelta.total_seconds()`는 float를 돌려줍니다. 유효숫자가 15~16자리인데
FILETIME은 18자리라 **마이크로초가 조용히 틀어집니다.** 정수 연산만 쓰십시오.

(테스트 헬퍼를 짜다가 실제로 밟은 건입니다. 값이 2 마이크로초 어긋났고,
허용 오차 1초 안이라 파이프라인에서는 안 걸렸을 겁니다.)

### USN 이름 크기는 문자 수가 아니라 바이트 수

`$FILE_NAME`은 문자 수(`name_length`)인데 `USN_RECORD_V2`는 바이트
수입니다. `$MFT` 파서 코드를 옮겨 오면 반드시 밟습니다. 한글 이름에서만
깨지므로 ASCII 테스트만으로는 안 잡힙니다 —
`test_name_size_is_bytes_not_characters`로 고정해 두었습니다.

### USN 신호 플래그는 $MFT보다 훨씬 많이 걸린다 (미해결)

`evidence/$J` 355,850건 전량 측정:

| 플래그 | 건수 | 비율 |
|---|---|---|
| `deleted` | 131,139 | 37% |
| `file_created` | 81,266 | 23% |

확장자를 `.exe/.dll/.aspx`로 좁히고 20분 시간창을 걸어도 2,042건 중
**1,281건(63%)이 신호**로 남습니다. `record_filter.DEFAULT_LIMIT`이
60이므로 필터가 사실상 임의로 60건을 고르는 상태입니다.

**원인은 룰이 틀려서가 아닙니다.** 플래그는 정확합니다. 같은 이름이지만
카디널리티가 다릅니다.

- `$MFT`의 `deleted` = **상태**("지금 미할당"). 볼륨 크기에 묶여 있음
- `$UsnJrnl`의 `deleted` = **사건**("지워졌다"). 시간에 비례해 무한정 쌓임

개발 장비의 npm 설치·삭제 같은 정상 churn만으로 수만 건이 나옵니다.
(첫 레코드가 `README.md`, `unpipe`인 것이 그 증거입니다.)

**아직 고치지 않았습니다.** 좁힐 수 있는 가장 강한 축은 경로인데 USN
레코드에는 경로가 없어(`parsers/usnjrnl.py` "범위 필터의 한계" 참조)
현재로선 적용할 수단이 없습니다. `$MFT`의 `MISMATCH_PAIRS`처럼 물리적
근거가 있는 판별자를 찾은 뒤에 좁혀야 하며, 근거 없이 임계값만 만지면
증거를 놓칩니다.

### 2026-08-24 · 프리패치 버전 30 / 220바이트 레이아웃 (실측)

키오스크 사고 이미지(`evidence/0824test.001`, 60GB VMware 물리 디스크,
볼륨 1)를 04단계로 돌렸더니 **프리패치가 137건 전부 `UnknownLayout`으로
빠졌습니다.** `docs/limitations.md`가 예고한 "새 빌드가 블록 크기를 바꾸면
그 시스템의 프리패치가 통째로 0건"이 실제로 일어난 것입니다. 조용하지는
않았습니다 — `parse_errors`와 로그에 `(버전 30, 파일 정보 220바이트)`가
그대로 찍혔습니다.

**이 이미지는 137건 전부가 `(30, 220)` 하나입니다.** 표에 있던
`(30, 216)`(1903 이상)도 `(30, 224)`(1809 이하)도 아닙니다.

#### 자리를 어떻게 정했나 — 추측이 아니라 대조

블록 크기는 파일이 말합니다(`메트릭 오프셋 - 헤더 84`). 나머지 자리는
137건을 훑어 **값의 성질로** 확정했습니다.

| 자리 | 값 | 무엇으로 확인했나 |
|---|---|---|
| `run_time_offset` | `0x2C` | 그 자리의 QWORD 8개가 FILETIME으로 그럴듯한 유일한 위치 |
| `run_count_offset` | `0x7C` | **유효 시각 개수와 정확히 일치** (아래) |
| `metrics_entry_size` | 32 | `트레이스오프셋 - 메트릭오프셋 = 1232-304 = 928 = 29 × 32` |
| `volume_entry_size` | 96 | v30·v31 공통값. 독립 스캐너 대조가 뒤를 받침 |

`run_count`가 결정적입니다. 유효한 실행 시각이 8개 미만인 파일에서
`0x7C`의 값이 **그 개수와 한 건도 빠짐없이 같았습니다**
(`IPCONFIG` 4/8→4, `BACKGROUNDTASKHOST` 3/8→3, `AUDIODG` 2/8→2 …).
8개가 다 찬 파일에서는 `0x7C`가 10·12·13으로 8을 넘습니다 — 시각 슬롯은
최근 8회만 남는 링버퍼이고 횟수는 계속 센다는 동작과 맞습니다.
후보였던 `0x80`은 개수와 무관하게 흩어졌고, `(30,216)`이 쓰는 `0x74`는
`0` 아니면 `1200000000`이라 둘 다 탈락했습니다.

#### 대조 결과 (`tools/scan_prefetch.py`)

이미지에서 `.pf` 137건을 뽑아 **파서와 다른 길**(메트릭 배열을 걷지 않고
문자열 블록을 널로 쪼개는 경로)로 읽어 맞췄습니다.

```
읽은 파일 137건 / 건너뛴 0건
버전 분포: 30=137
적재 파일 경로 총 10,195건
파일명 해시 불일치 0건 / 헤더 크기 불일치 0건
파서 출력 대조: 불일치 0건
```

#### 곁가지 — 스캐너의 헤더 크기 대조가 늘 틀렸다

처음 돌렸을 때 **헤더 크기 불일치가 137/137**로 나왔습니다. 파서 문제가
아니라 `scan_prefetch.py`가 헤더의 크기(압축을 푼 `.pf`의 크기)를
`path.stat().st_size`(온디스크 **압축** 크기)와 비교했기 때문입니다.
Win10 이후 `.pf`는 전부 `MAM` 압축이라 **이 검사는 구조적으로 항상
실패**했고, 그래서 진짜 크기 어긋남을 가리고 있었습니다. 해제된 바이트
길이와 비교하도록 고쳤습니다(`tools/scan_prefetch.py`).

`$UsnJrnl`의 0바이트 껍데기와 같은 부류입니다 — 검사가 돌고, 답이 나오고,
그 답이 아무것도 말해 주지 않습니다.

### 2026-08-24 · evtx 채널 확장 (Firewall / BITS / NetworkProfile)

키오스크 사고 이미지에서 "외부 서버로 데이터를 보냈는가"에 답할 수 없다는
것이 드러나 카탈로그를 늘렸습니다. **파서는 새로 만들지 않았습니다** —
채널만 다르고 온디스크 형식이 같아 `EvtxParser`를 그대로 씁니다.

#### 대조 — 범위 없이 읽은 히스토그램과 04단계 산출물

같은 파일을 두 번 읽습니다. 한 번은 `Scope()`(제한 없음)로 전량을 읽어
EventID 히스토그램을 만들고, 한 번은 03단계가 준 `event_ids` 범위로
파이프라인을 돌립니다. **범위 밖을 빼먹거나 더 넣으면 두 수가 갈립니다.**

| 아티팩트 | 전량 | 요청 ID 합계 | 04단계 산출물 | 일치 |
|---|---|---|---|---|
| `evtx:Firewall` | 394 | 381 | 381 | ✓ |
| `evtx:BITS` | 118 | 92 | 92 | ✓ |
| `evtx:NetworkProfile` | 30 | — | (Tier 2, 미요청) | — |

함께 확인한 것: 산출물에 **요청 밖 EventID가 한 건도 섞이지 않음**,
`ref` 접두어가 아티팩트별로 일관(`EVTX-FW#` / `EVTX-BITS#`), `ref` 유일.
마지막 둘은 인스턴스를 공유했을 때 깨지는 성질입니다 — 공유하면 한 채널의
레코드가 다른 접두어로 나가고 06단계가 그것을 환각으로 셉니다.

전량 히스토그램 상위:

```
Firewall : 2004=368  2006=8  2010=8  2002=5  2003=5
BITS     : 59=30  3=18  61=16  60=14  4=14  209=8
```

#### 값이 실제로 담기는지

`evtx:BITS` 이벤트 59의 `fields`에 **`url`이 그대로 들어옵니다.**

```
{"transferId": "{da68c0bd-...}", "name": "Font Download",
 "url": "https://fs.microsoft.com/fs/windows/config.json", ...}
```

"어디로 갔는가"가 남는 몇 안 되는 자리이고, 이것이 이 채널을 넣은 이유입니다.

#### EventID는 채널을 가려야 한다

`_flags.yaml`의 새 룰 셋은 기존 evtx 룰과 달리 `evtx:*`가 아니라 **정확한
아티팩트 이름**으로 겁니다. 실제로 겹치기 때문입니다 — NetworkProfile의
`10000`(네트워크 연결)은 `T1200` 매핑이 `evtx:System`에 요청하는 Kernel-PnP
`10000`과 번호가 같습니다. `evtx:*`로 걸면 장치 구성 이벤트에
`network_state_changed`가 붙습니다. `T1200.yaml`에도 같은 이유로 주석을
남기고 NetworkProfile을 Tier 2로 따로 적었습니다.

#### 등록 지점이 넷이 아니라 다섯이었다

`add-parser` 스킬은 등록 지점을 넷으로 적고 있는데, evtx는 하나 더
있습니다 — `parsers/evtx.py`의 `CHANNEL_FALLBACK`입니다.
`EvtxParser.__init__`이 여기 없는 아티팩트를 거부하므로 카탈로그·등록소만
고치면 **import 시점에 죽습니다.** 조용하지는 않지만 어디를 고쳐야 하는지가
드러나지 않아 스킬과 파일 주석 양쪽에 적었습니다.

#### 이 이미지에서 나온 결과

사고 시간창(06:55:09~06:57:38) 안: 방화벽 **0건**, BITS **0건**.
다만 `$MFT`에서 BITS 작업 큐 파일 넷(`qmgr.db`·`edb.log`·`edb.chk`·
`qmgr.jfm`)이 **그 창 안에서 수정**됐습니다. 큐는 만져졌는데 전송 작업
이벤트는 남지 않았다는 뜻이고, BITS 서비스의 정기 정리일 수 있습니다 —
**단정하지 않고 관측만 적습니다.**

**`CurrentVersion`이 6.3인 것이 요점입니다.** Win8.1 이후로 이 값이 굳어
Win10과 Win8.1을 가르지 못합니다. 빌드 번호만 믿는 근거가 이 실측입니다.

### RecentFileCache.bcf — 실물 대조 (같은 날 저녁, Win7 이미지 도착)

`evidence/windows7_testimage.001`(100GB, FTK Imager, VMware 가상 디스크)
볼륨 1 = `Windows 7 Ultimate`, 빌드 7601.

```
ProductName        Windows 7 Ultimate
CurrentVersion     6.1
CurrentBuildNumber 7601
EditionID          Ultimate
InstallationType   Client
```

`UBR`·`ReleaseId`·`DisplayVersion`이 **없습니다**(Win10 이후 값). 빌드
번호만 필수로 두고 나머지를 선택으로 둔 판단이 여기서 확인됐습니다.

#### 헤더는 가정한 대로였다

`Windows/AppCompat/Programs/RecentFileCache.bcf`, 6,742바이트.

```
0000  fe ff ee ff 11 22 00 00 03 00 00 00 01 00 00 00
0010  d1 a0 78 01 27 00 00 00 63 00 3a 00 5c 00 77 00   ....'...c.:.\.w.
0020  69 00 6e 00 64 00 6f 00 77 00 73 00 5c 00 73 00   i.n.d.o.w.s.\.s.
```

- `0x00` 시그니처 `FE FF EE FF` — **가정대로**
- `0x14` 첫 항목의 길이 필드 `0x27` = 39, 이어서 UTF-16LE
  `c:\windows\system32\...` 39자. **길이는 바이트가 아니라 문자 수다**
- 미상 4필드 실측: `0x2211`, `3`, `1`, `0x0178A0D1`. **항목 수(67)와 맞는
  값이 없으므로 개수 필드는 없습니다** — 파일 끝까지 걸어야 합니다

#### 두 경로가 서로를 지지한다

`tools/scan_recentfilecache.py`를 새로 만들었습니다. 프리패치·하이브 때와
같은 방법입니다 — **같은 파일을 다른 길로 읽습니다.** 파서는 길이 필드를
걷고, 스캐너는 길이 필드를 아예 보지 않고 헤더를 뗀 나머지를 통째로
UTF-16LE로 디코딩해 널로 쪼갭니다.

```
파일 크기: 6,742바이트
시그니처: feffeeff (기대 feffeeff)
길이 필드를 걸어서: 67건, 끝나고 남은 바이트 0
널로 쪼개서:       67건
→ 두 해석이 일치합니다.
파서 출력 대조: 일치
```

**남은 바이트 0이 핵심입니다.** 파일 크기는 Windows가 쓴 값이라 우리 해석과
독립인데, 길이 필드를 바이트로 잘못 읽었다면 첫 항목에서 어긋나 67번
연쇄할 수 없습니다. 프리패치에서 헤더 해시·파일 크기를 정답지로 삼은 것과
같은 자리입니다.

레코드 67건 전부 `offset`이 실제 길이 필드를 가리키고, 마지막 항목의 끝이
6,742 = 파일 크기와 같습니다.

| 아티팩트 | 대조 상대 | 상태 |
|---|---|---|
| `recentfilecache` | `tools/scan_recentfilecache.py` (길이 필드를 보지 않는 경로) | **일치 67/67** |
| `recentfilecache` | Windows가 쓴 파일 크기 | **일치** (남은 바이트 0) |
| `recentfilecache` | `RecentFileCacheParser` (Eric Zimmerman) | **미실시** |

셋째 줄이 남았습니다. 앞의 둘은 우리가 만든 두 경로라 **공통 오해가 있으면
같은 방향으로 틀립니다.**

#### 프리패치가 없다 — 그리고 왜 없는지

`Windows/Prefetch`에 `.pf`가 **한 개도 없습니다.** ReadyBoot와 `Ag*.db`
(Superfetch) 뿐입니다. 레지스트리가 이유를 말해 줍니다.

```
SYSTEM\ControlSet001\Control\Session Manager\Memory Management\PrefetchParameters
  EnablePrefetcher  = 2   (부팅 전용 — 애플리케이션 프리패치 꺼짐)
  EnableSuperfetch  = 2
```

`EnablePrefetcher = 2`는 부팅 프리패치만 한다는 뜻이라 애플리케이션 `.pf`가
애초에 만들어지지 않습니다. 04단계는 `artifact_not_found`("증거 없음")로
기록하는데 **그것이 맞습니다** — 버전 때문이 아니라 이 시스템의 설정
때문입니다. 둘을 `osinfo.AVAILABILITY`로 뭉뚱그리지 않은 이유가 이것입니다.

**그래서 프리패치 버전 23(Win7) 실측 재확인은 여전히 못 했습니다.**
예전 `evidence/[root]` 73건 기록만 남아 있고 그 볼륨은 디스크에 없습니다.

### 프리패치 (30, 220)의 이름표가 명세와 어긋난다

위 이미지는 빌드 15063(1703)인데 파일 정보 블록이 **220바이트**입니다.
`FILE_INFORMATION`의 `(30, 224)`에 붙은 [LIBSCCA] 이름표는 "Windows 10
1809 이하"라 1703이면 224여야 합니다.

**파서는 영향받지 않습니다.** 블록 크기를 표에서 가져오지 않고
`메트릭 오프셋 - 헤더 크기`로 파일에서 읽기 때문입니다. 버전 번호만으로
자리를 정하는 구현이었다면 이 이미지의 프리패치 137건이 통째로 어긋났을
자리이고, 그 판단이 옳았음을 실측이 보여 준 사례입니다.

이름표를 고치지는 않았습니다 — 1809 경계가 틀렸는지 빌드마다 더 잘게
갈리는지 확인할 이미지가 하나뿐이라, 아는 것보다 많이 적지 않습니다.
