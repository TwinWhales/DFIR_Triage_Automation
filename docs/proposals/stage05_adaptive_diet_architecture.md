## 1. 문제 — 무엇이 실제로 병목이었나

프로토타입(`feat/stage05-diet-prototype`)이 지목한 것은 셋이었고, 검토에서
**넷째가 하나 더 나왔다.** 넷째가 가장 심각하다.

### 1.1 프롬프트가 크다

Sysmon·Prefetch 레코드마다 `Hashes`·`FileVersion`·`Company`·`LogonGuid`·
`ProcessGuid` 같은 부가 메타데이터가 실린다.

**다만 63KB 는 이미 다이어트된 뒤의 크기다.** `allocation.for_prompt` 가
`fields` 안의 긴 목록을 20개까지 잘라서 내보낸 결과이고(안 자르면
100,068자), 남은 것은 목록이 아니라 **필드**다. 그래서 이번에 줄일 대상은
목록이 아니라 필드다.

### 1.2 VRAM 을 넘겨 CPU 로 흘렀다

6GB VRAM 에서 32,768 창은 KV 캐시만 1.8GB 라 모델이 GPU 에 다 올라가지
않는다. `/api/ps` 실측:

| `num_ctx` | 총 크기 | VRAM | GPU |
|---|---|---|---|
| 4,096 | 4.77GB | 3.90GB | 81% |
| 8,192 | 5.01GB | 3.96GB | 79% |
| 16,384 | 5.41GB | 3.96GB | 73% |
| 32,768 | 6.35GB | 3.91GB | **61%** |

**"100% GPU" 는 창으로 도달하지 못한다.** 이 기계에서 남는 VRAM 이 4GB
대라 천장은 KV 캐시가 아니라 **모델 가중치**다. 그리고 32,768 → 8,192 가
이미 61% → 79% 라, 거기서 4,096 까지 더 내려도 2%p 다.

### 1.3 타임아웃

거대한 컨텍스트 연산 + 문법 제약 디코딩 부하로 05단계가 멈추는 일이 있었다.
`--timeout` 을 넉넉히 두지 않으면 단계가 통째로 실패한다(이미 알려진 것,
`docs/limitations.md`).

### 1.4 **프롬프트가 조용히 잘리고 있었다** (검토에서 발견, 고침)

예산 공식의 `CHARS_PER_TOKEN = 2.5` 가 우리 데이터에 맞지 않았다.
`prompt_eval_count` 로 실측(`qwen2.5:7b`, `K-LIVE-0902-wide`, 난스로 KV
캐시 재사용을 깼다):

```
10건  10,122자 →  4,997토큰   2.03자/토큰
20건  17,744자 →  8,679토큰   2.04
40건  37,863자 → 17,978토큰   2.11
55건  62,713자 → 29,910토큰   2.10
60건  69,875자 → 16,386토큰   4.26   ← 잘림
```

**60건에서 평가된 토큰이 40건보다 적다.** 2.1자/토큰이면 69,875자는 약
33,300토큰이라 32,768 창을 넘고, **넘은 프롬프트를 Ollama 는 거부하지 않고
앞을 잘라서 받는다.** 16,386 은 창의 절반이다.

즉 **기본 설정으로 도는 파이프라인이 증거의 절반만 모델에 보내고 있었고,
오류 없이 끝났다.** 2.5 는 같은 글자를 적은 토큰으로 세므로 예산이 19%
헐거웠다 — 상수 옆에 적혀 있던 "작게 잡으면 자리를 덜 쓸 뿐"이 거꾸로였다.

**고쳤다** (2026-09-03, `fix(05)`). 상수를 2.0 으로 내리고, 백엔드가 실제
평가 토큰 수를 남겨 추정과 나란히 찍게 했다.

## 2. 합의된 구조

원안의 골자 — **"AI 는 가벼운 판단만, 데이터 조립은 파이썬이"** — 를 그대로
가되, 검증의 겨냥을 함께 옮긴다.

```
[04단계 파싱 산출물 (수천~수만 건)]
               │
               ▼
   [입력 다이어트]  ← 9-1
   - 필드 블랙리스트 (실측 24% 압축)
   - 목록 절단은 기존 for_prompt 가 이미 한다
               │
               ▼
   [분기]  ← 9-2
   - 임계값은 allocation.prompt_token_budget() 에서 나온다 (상수 아님)
      ├─ 예산 안: 단일 질의
      └─ 예산 초과: 아티팩트별 Map → 초과하면 시간순 하위 청크
               │
               ▼
   [Map — 객관식 선별 질의]
   - {ref, technique, reason, severity}
               │
               ▼
   [Reduce — 교차 아티팩트 종합 질의 1회]  ← 이것이 있어야 Map-Reduce 다
   - Map 이 고른 단서만 모아 "이것들을 잇는 소견과 타임라인"을 묻는다
               │
               ▼
   [파이썬 결정론적 조립]
   - LLM 이 고른 ref 로 원본에서 claims·timeline 을 1:1 기계 조립
               │
               ▼
   [06 검증 — 겨냥을 옮긴다]
   - value_match 는 이제 항등식이다 (파이썬이 쓴 값을 파이썬이 대조)
   - 대신 technique_supported: 기법과 아티팩트가 매핑에서 만나는가
               │
               ▼
   [07 보고서]
```

## 3. 세부 — 원안에서 바뀐 자리

### 3.1 다이어트는 화이트리스트가 아니라 **블랙리스트**다 (9-1)

**원안**: 필요한 필드만 남기는 화이트리스트, 85% 압축.
**합의**: 불필요한 필드만 빼는 블랙리스트, **실측 24%** 압축.

바꾼 이유가 둘이다.

**(a) 화이트리스트는 아티팩트를 조용히 빈 껍데기로 만든다.** 원안의 공통
보존 필드는 `ref, artifact, event_id, timestamp, flags, path` 였는데:

- `$MFT` 에는 `timestamp` 가 **없다.** `si_*`/`fn_*` 여덟이다
  (`record_filter.activity_times` 가 그래서 두 갈래다). 화이트리스트대로면
  MFT 레코드에서 시간이 통째로 사라지고, 자동 생성될 타임라인도 MFT 를
  못 싣는다.
- `$UsnJrnl` 은 `reason`(FileCreate·DataExtend…)과 `name` 이 판단의 전부다.
  USN 에는 `path` 가 없다. 둘 다 목록에 없어 근거가 0 이 된다.
- registry·SRUM·SQLite·Amcache·RecentFileCache 는 `fields` 목록에 아예 없다.

03단계가 보라고 한 아티팩트가 05 에서 빈손이 되는 것은 `limitations.md`
4-2-1 이 고친 문제의 재발이다. 그리고 `add-parser` 로 새 파서가 붙을 때
목록을 빠뜨려도 **아무 데도 안 남는다.**

**(b) 실측이 85% 를 지지하지 않는다.** 실제로 넣은 목록(`Hashes`,
상관용 GUID 다섯, PE 버전 리소스 다섯, `TerminalSessionId` — 어휘에 근거가
붙어 있다)을 `K-LIVE-0902-wide` 에 재 보면:

| 아티팩트 | 건수 | 전 | 후 | 절감 |
|---|---|---|---|---|
| `evtx:Sysmon` | 9,606 | 1,043자 | 790자 | **25%** |
| `prefetch` | 192 | 1,789자 | 1,789자 | 0% |
| `evtx:Security` | 31 | 774자 | 774자 | 0% |
| 전체 | 9,829 | 1,057자 | 809자 | **24%** |

85% 는 필드를 열 개 남짓만 남겨야 나오는 수이고, 그것이 (a) 의 안이다.

**판단에 쓰는 것은 남겼다.** `UtcTime`·`RuleName`·`IntegrityLevel`·
`LogonId` 까지 빼면 31% 가 되지만, 그 넷은 시각·룰 이름·권한 수준·세션을
가르는 값이라 남겼다. 7%p 와 판단 근거를 맞바꾸지 않는다.

**효과.** 같은 창(32,768)에서 전달 레코드가 **54건 → 58건**이 됐다.

**목록은 코드가 아니라 어휘에 둔다** — `mappings/_flags.yaml`. 선례가 둘
있다(`privileged_groups`, `prompt_keep_paths`). 그리고 **뺐다는 사실을
프롬프트가 말한다**(`_trim_notice`) — 말하지 않으면 모델이 "해시 정보가
없다"를 근거로 쓰고, 그것은 우리가 유발한 환각이다.

### 3.2 분기 임계값은 상수가 아니라 **유도된 값**이다 (9-2)

**원안**: 임계 6,000 토큰, 하위 청크 4,000 토큰, 창 4,096.
**합의**: `allocation.prompt_token_budget(num_ctx, reserve_output_tokens)`.

원안의 세 수는 서로 맞지 않았다. 4,096 창에 6,000 토큰은 들어가지 않고,
그 구간은 **조용히 잘리는 구간**이다(1.4 와 같은 모양). 그리고 당시
`RESERVE_OUTPUT_TOKENS` 가 4,096 이라 `--num-ctx 4096` 을 그대로 넣으면
예산이 0 이 되어 레코드가 한 건도 안 나간다 — 프로토타입이 `allocation` 을
우회해서 안 터졌다.

**출력 예약은 질의마다 다르다.** 객관식 선별은 ref 와 한 줄 사유를 낼
뿐이고, 문장·타임라인을 쓰는 질의는 그 몇 배다(실측 소견 4건 + 타임라인이
약 1,800토큰). 상수 하나로 두면 큰 쪽에 맞춰야 하고, 창이 좁을수록 그
낭비가 곧 레코드 수다. 그래서 이름을 `RESERVE_FINDINGS_TOKENS` 로 바꿔
질의를 박아 뒀다(2026-09-03 완료).

**청크 실패는 조용히 넘어가지 않는다.** 다섯 중 하나가 타임아웃인데 넷으로
완주하면 그것이 폴백이다. `errors.jsonl` 에 남기고, 부분 결과로 갈 거면
그 사실이 07 보고서까지 나가야 한다.

**Reduce 입력도 예산 판정을 받는다.** 단서가 `{ref, technique, reason}`
한 줄로 120자쯤인데 수십 건이면 그것만으로 창을 넘는다.

### 3.3 Map 질의 — 객관식

```json
{
  "type": "object",
  "properties": {
    "suspicious_records": {
      "type": "array",
      "items": {
        "type": "object",
        "properties": {
          "ref": {"type": "string"},
          "technique": {"type": ["string", "null"]},
          "reason": {"type": "string"},
          "severity": {"type": "string", "enum": ["high", "medium", "low", "info"]}
        },
        "required": ["ref", "reason"]
      }
    }
  },
  "required": ["suspicious_records"]
}
```

**`ref` 와 `technique` 에 enum 을 걸어야 한다.** 지금
`llm_client.constrained_schema()` 가 하는 일이다 — `$defs.ref` 를 이번에
실어 보낸 레코드 목록으로, `technique` 을 시나리오의 기법 목록으로 갈아
끼운다. 위 스키마처럼 자유 문자열로 두면 `T1200.001`(형식은 맞고 실재하지
않는 하위기법)이 그대로 돌아온다(`limitations.md` ⑤).

### 3.4 파이썬 조립 — 그리고 **검증의 겨냥을 옮긴다**

`ref` 로 원본을 찾아 `path`·`fields.CommandLine`·`fields.TargetFilename`·
`fields.TargetUserName` 등을 1:1 로 `claims` 에 넣고, `timestamp` 기준으로
`timeline` 을 정렬한다. 여기까지는 원안 그대로다.

**"환각률 0%" 를 성과로 적으면 안 된다.** 파이썬이 원본에서 복사한 값을 06
이 원본과 대조하면 항등식이라, 통과율 100% 는 구조상 보장된다. `ref` 는
이미 문법 enum 으로 막혀 있으니(3.3) 06 이 잡던 유일한 환각이 값 불일치
였고, 이 변경이 그것을 없앤다. **없어지는 것은 오류가 아니라 측정이다.**

환각의 유형별 상태는 이렇다(`docs/limitations.md` 에 표로 있다).

| 유형 | 무엇이 막나 | 상태 |
|---|---|:---:|
| 입력에 없는 `ref` 인용 | 출력 문법 enum | 예방 |
| 값을 잘못 옮겨 적음 | (파이썬 조립) | **예방으로 바뀜** |
| 볼 것이 아닌 레코드를 고름 | — | 못 잼 |
| 증거가 뒷받침 않는 기법을 붙임 | — | **채울 수 있다** |
| `statement` 문장 자체 | — | 못 잼 |

**넷째 줄을 채운다.** `mappings/windows/T*.yaml` 의 `artifacts:` 가 "이
기법은 이 아티팩트로 말한다"를 적어 두었고, `src/common/refs.py` 의
`PREFIX_ARTIFACT` 가 `ref` 접두어를 아티팩트로 되돌린다. 소견의
`technique` 과 `refs` 가 매핑에서 만나지 않으면 기각하는 검사기 하나면
된다. 결정론적이라 04·06 규약을 깨지 않는다.

**지표 이름도 바꾼다.** `benchmark/collect.py` 와 `benchmark/README.md` 의
"환각률" 정의를 `technique_supported` 기준으로 옮긴다. 안 바꾸면 숫자는
맞는데 이름이 거짓말이 된다.

### 3.5 질의 내역 저장

`cases/<case_id>/05_llm_queries/` 에 질의 전문과 응답 원문을 남긴다.
원안 그대로 가되 하나 더 — **질의별 `ref` 목록**을 함께 남긴다.
`input_refs` 가 청크들의 합집합이 되면 `ref_in_input` 검사가 헐거워지기
때문이다(청크 A 의 ref 를 B 소견이 인용해도 합집합으로는 통과한다).

## 4. 창 축소는 마지막이다 (9-3)

원안은 창 4,096 을 전제로 시작했다. **순서를 뒤로 옮겼다.**

예산 공식이 `(창 − 출력 예약) × 자/토큰 − 프롬프트 고정분` 이고,
`K-LIVE-0902-wide` 의 레코드는 평균 1,057자다.

| 창 | 출력 예약 | 실을 수 있는 레코드 |
|---|---|---|
| 32,768 | 4,096 | **54건** |
| 16,384 | 2,560 | 약 25건 |
| 8,192 | 2,560 | 약 9건 |
| 4,096 | 1,024 | 약 4건 |

**창만 따로 내리면 GPU 20%p 를 얻고 레코드 50건을 잃는다.** 4-3 이 미해결로
둔 "Tier 1 아티팩트당 4건" 을 더 나쁘게 만든다. 좁은 창은 **여러 번 묻는
구조와 함께여야** 이득이고, 그래서 9-2 뒤다.

그래서 `stage05_interpret/llm_client.py` 가 `DEFAULT_NUM_CTX` 를 자기 것으로
갖되(02단계와 함께 움직이지 않게) 값은 32,768 그대로 두었다.

## 5. 실측 성능 — 무엇이 검증됐고 무엇이 아직인가

프로토타입이 낸 16.3초는 **단일 질의 경로**의 값이다. Map-Reduce 와 서브
청킹은 그 실행에서 돌지 않았다(프롬프트가 임계값 아래였다).

| 지표 | 프로토타입 주장 | 검토 결과 |
|---|---|---|
| 프롬프트 63KB → 9KB (85%) | 화이트리스트 기준 | 블랙리스트로는 **24%** (1,057자 → 809자) |
| 창 4,096, GPU 100% | 다른 장비 기준 | 이 기계는 창으로 100% 도달 불가(천장이 가중치). 32,768 → 8,192 가 61% → 79% |
| 05 소요 1,800초 → 16.3초 | 단일 질의 | 창 축소분과 다이어트분이 분리되지 않았다. 대조군(현 코드 + 낮춘 창)을 재야 한다 |
| 06 환각률 0.0% | passed 4 / rejected 0 | 파이썬 조립이면 항등식이라 **구조상 100%** 다. 3.4 참조 |
| "1~11단계 관통" | — | 이 파이프라인은 01→07 이다 |

**대조군을 남겨 둔다.** 110배가 창에서 왔는지 다이어트에서 왔는지 분리하지
않으면, 나중에 블랙리스트가 증거를 지운 것이 드러났을 때 되돌릴 근거가
없다.
