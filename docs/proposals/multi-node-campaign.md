# 멀티 노드 상관분석과 캠페인 통합 보고서 — 설계

> `work.md` 2번의 상세입니다. **무엇을 할 차례인가**는 `work.md` 에 있고,
> 여기에는 다음 세션이 바로 집을 수 있게 적어 둔 배선이 있습니다.
> 합의된 것은 아래 "A안을 택하지 않은 이유" 하나이고, 나머지는 제안입니다.

키오스크 한 대로 끝나는 사고는 없습니다. 내부망 전파를 따라가려면 노드 여럿의
증거를 한 사건으로 묶어야 하는데, 지금 파이프라인은 **한 실행이 한 볼륨**을
전제로 서 있습니다. 그 전제를 어디서 깰 것인가가 이 문서의 주제입니다.

---

## 1. A안을 택하지 않은 이유

노드가 셋이면 `MFT#12345` 가 키오스크·POS·관리서버에 모두 존재합니다. `ref` 는
전 단계를 관통하는 유일한 증거 식별자이므로(`src/common/refs.py`), 이대로 한
케이스에 섞으면 어느 노드의 레코드인지 알 수 없습니다.

**A안 — `ref` 에 노드를 넣는다.** `<노드>/<접두어>#<번호>` 로 바꾸는 길입니다.
검토했고, 택하지 않았습니다.

- `ref` 정규식이 **동결 스키마 두 곳에 하드코딩**되어 있습니다
  (`schemas/parsed_record.schema.json`, `schemas/findings.schema.json`).
  `CLAUDE.md` 가 전체 공지 대상으로 지정한 변경입니다.
- 기존 케이스 산출물과 `benchmark/golden/` 이 전부 무효가 됩니다.
- 05 프롬프트의 `ref` enum 이 노드 수만큼 커집니다. 창 예산은 이미 좁습니다
  (`docs/limitations.md` 3-2).
- **가장 큰 문제**: 모델이 노드를 넘나들며 소견을 쓸 수 있게 됩니다. 그러면
  "키오스크의 이 파일이 POS 로 갔다" 를 **모델이 주장**하고, 06 은 그 주장을
  값 대조로만 봅니다. 노드를 잇는 판단이 검증되지 않은 채 보고서에 오릅니다.

**B안 — 캠페인 레이어를 위에 얹는다.** 노드마다 지금 구조 그대로 01~07 을
완주시키고, 그 위에서 **파이썬이 결정론으로** 노드를 잇습니다. 동결 스키마를
건드리지 않고, 골든과 테스트가 그대로 살아 있으며, **노드를 잇는 연결고리를
LLM 이 지어낼 자리가 없습니다.** 04·06·07 을 결정론 구간으로 둔 판단과 같은
결입니다.

이 문서는 B안의 배선입니다.

## 2. 배치 — 노드는 그냥 케이스다

```
cases/
  KIOSK-0910-kiosk/     01_input.json … 07_report.md      ← 평범한 케이스
  KIOSK-0910-pos/       01_input.json … 07_report.md
  KIOSK-0910-server/    01_input.json … 07_report.md

campaigns/
  KIOSK-0910/
    campaign.json       입력 — 어느 케이스들이 한 사건인가
    08_campaign.json    상관분석 결과
    08_campaign.md      캠페인 통합 보고서
```

**노드 케이스는 특별하지 않습니다.** `case_id` 규칙(`^[A-Za-z0-9][A-Za-z0-9_-]*$`)을
그대로 지키고, 각각 단독으로도 완결된 보고서를 냅니다. 캠페인이 실패해도 노드
보고서는 유효합니다.

`campaigns/` 는 `cases/`·`evidence/` 와 같은 부류라 gitignore 대상입니다.

### `campaign.json` (사람이 쓰거나 GUI 가 만든다)

```json
{
  "campaign_id": "KIOSK-0910",
  "nodes": [
    {"node": "kiosk",  "case_id": "KIOSK-0910-kiosk",  "role": "endpoint"},
    {"node": "pos",    "case_id": "KIOSK-0910-pos",    "role": "endpoint"},
    {"node": "server", "case_id": "KIOSK-0910-server", "role": "server"}
  ]
}
```

`node` 는 캠페인 안에서 유일한 짧은 이름입니다. 보고서와 `08_campaign.json` 이
`(node, ref)` 쌍으로 증거를 가리키므로, 이 이름이 A안의 `ref` 접두어 역할을
**캠페인 레이어에서만** 합니다.

## 3. 08단계 — 무엇을 읽고 무엇을 내는가

**읽는 것** (노드마다):

| 파일 | 쓰임 |
|---|---|
| `04_parsed/` | 상관 축의 값을 뽑는다 |
| `06_verified.json` | 어느 소견이 통과·주의·기각인가 |
| `05_findings.json` | 소견의 문장과 인용 `ref` |
| `02_scenario.json` | 노드의 분석 기간·호스트 이름 |

**내는 것**: `08_campaign.json` + `08_campaign.md`.

**LLM 을 부르지 않습니다.** 07 과 같은 이유입니다 — 마지막에 모델이 문장을
다시 쓰면 앞의 검증이 전부 무의미해집니다. 08 은 Jinja2 템플릿입니다.

### 스키마

`schemas/campaign.schema.json` 을 **새로 추가**합니다. 동결된 6개는 각각
`"stage": {"const": ...}` 라 새 단계는 파일 추가지 기존 파일 변경이 아닙니다.
그래도 `schemas/` 가 공용이므로 추가 자체는 공지 대상으로 봅니다.

## 4. 상관 축 넷 — 무엇으로 노드를 잇는가

**새 어휘를 만들지 않습니다.** 04단계의 `canonical` 오버레이가 이미
아티팩트 중립 필드를 냅니다(`src/stage04_parse/canonical.py`) —
`subject_path`·`event_time`·`process_image`·`parent_image`·`command_line`·
`hashes`·`user`. 노드 안에서 `same_path`·`same_hash` 를 잇는 기계도 이미
있습니다(`src/stage05_interpret/incident_packet.py`). 08 은 **같은 정규화를
노드 사이로 넓힐 뿐**입니다.

| 축 | 값의 출처 | 정규화 |
|---|---|---|
| **해시** | `canonical.hashes` | `incident_packet._hash_keys` 그대로 — 접두어 제거·소문자 |
| **경로·파일명** | `canonical.subject_path` | `io.normalize_path` 그대로. 노드마다 드라이브 문자가 다를 수 있어 **basename 도 함께** 색인한다 |
| **계정** | `canonical.user` | 도메인 분리 후 소문자. `SYSTEM`·`LOCAL SERVICE` 등은 제외 어휘 |
| **네트워크** | Sysmon EID 3 의 `fields.DestinationIp`·`DestinationPort`, 그리고 `command_line` 에서 뽑은 IPv4·URL 호스트 | 문자열 그대로. **사설 대역을 빼지 않는다** — 내부망 횡적 이동이 바로 그 대역이다 |

네트워크 축만 `canonical` 에 자리가 없습니다. `canonical.py` 에
`remote_ip`·`remote_port` 를 **더합니다** — 오버레이는 파서 출력을 덮지 않는
추가 계층이라 파서도 스키마도 건드리지 않습니다.

### 링크가 되는 조건

같은 정규화 값이 **서로 다른 노드 둘 이상**에서 관측되면 링크 후보입니다.
후보는 다음을 갖춥니다.

```json
{
  "axis": "hash",
  "value": "e3b0c44298fc1c14…",
  "observations": [
    {"node": "kiosk",  "ref": "SYSMON#22236", "at": "2026-09-10T13:37:04Z", "verdict": "passed"},
    {"node": "pos",    "ref": "MFT#88120",    "at": "2026-09-10T13:45:11Z", "verdict": "passed"}
  ],
  "span_seconds": 487
}
```

`observations` 는 노드마다 **가장 이른 관측 하나**만 싣습니다. 같은 값이 한
노드에서 수백 번 나와도 링크는 하나입니다 — 안 그러면 표가 반복으로 덮입니다.

### 체인

링크들을 `observations` 의 가장 이른 시각으로 정렬하면 캠페인 타임라인이
됩니다. 노드가 바뀌는 지점이 곧 횡적 이동 후보입니다.

```
13:37  kiosk           certutil 다운로드          SYSMON#22236
13:45  kiosk → pos     같은 해시가 POS 에 생성      MFT#88120     [hash]
13:52  pos → server    같은 계정으로 작업 등록      EVTX-SEC#5109 [account]
```

## 5. 신호등을 그대로 잇는다

캠페인 보고서도 노드 보고서와 같은 삼색을 씁니다. 링크의 등급은 **양끝 관측의
등급 중 낮은 쪽**입니다.

| 양끝 | 링크 |
|---|---|
| 둘 다 `passed` 소견이 인용한 `ref` | 🟢 |
| 하나라도 `unverifiable` | 🟡 (분석가 확인 권장) |
| 하나라도 `rejected` 소견에만 실린 `ref` | **링크를 만들지 않는다** |
| 어느 소견도 인용하지 않은 `ref` | ⚪ 참고 — 별도 절에 싣고 본문 체인에는 넣지 않는다 |

마지막 줄이 중요합니다. **04 에는 있지만 05 가 고르지 않은 레코드**로도 링크는
만들어집니다. 그것을 본문에 섞으면 "검증된 것"과 구별되지 않으므로, 절을
나눠 싣고 개수를 밝힙니다.

## 6. 이 설계가 주장하지 않는 것

**적어 두는 이유** — 캠페인 보고서는 화면에서 가장 그럴듯해 보이는 산출물이라,
무엇을 말하지 않는지 함께 인쇄하지 않으면 과대 해석됩니다.

- **인과를 말하지 않습니다.** 링크는 "같은 값이 두 노드에 있었다"까지입니다.
  "A 가 B 를 감염시켰다" 는 사람이 판단합니다. 시간 순서는 방향의 근거가
  되지만 증명은 아닙니다 — 시계가 노드마다 어긋날 수 있고, 시간대 가정은
  지금 KST 하나입니다(`docs/limitations.md` 3-4).
- **정상 공통값을 가리지 못합니다.** 세 노드에 다 있는 계정·경로·해시는
  대개 배경입니다(같은 이미지로 배포된 단말이면 특히). 지금은 **모든 노드에
  나타난 값의 신호를 낮추는 것**밖에 할 수 없고, 진짜 해법은 베이스라인입니다
  — 노드 보고서에서 "정상 항목을 정확하게 인용한 오탐" 을 못 거르는 것과
  **같은 자리**입니다.
- **노드가 빠진 것은 모릅니다.** 수집되지 않은 단말은 캠페인에 없고, 없다는
  사실도 보고서에 나타나지 않습니다. `campaign.json` 에 적힌 노드가 전부라는
  가정 위에 섭니다. 03단계가 선별하지 않은 아티팩트를 보고서가 모르는 것과
  같은 성질입니다 — 카탈로그(`mappings/_artifacts.yaml`)에 없는 것은 "확인하지
  못한 아티팩트" 에도 오르지 않습니다.
- **노드 하나가 실패하면 그 노드는 통째로 빠집니다.** 캠페인은 계속 진행하되
  **어느 노드가 왜 빠졌는지 보고서 첫 화면에 싣습니다.** 조용히 두 노드짜리
  캠페인이 되면 안 됩니다.

이 넷은 구현이 끝나면 `docs/limitations.md` 에 캠페인 절로 옮깁니다 — 아직
없는 절이므로, 옮길 때 만듭니다.

## 7. 구현 순서 — 관문마다 멈춰 볼 것

1. **`canonical.py` 에 `remote_ip`·`remote_port` 추가.**
   관문: 기존 테스트가 그대로 통과하는가(오버레이는 덮지 않는다).
2. **`schemas/campaign.schema.json` + `src/stage08_campaign/`.**
   먼저 `campaign.json` 을 읽어 노드 케이스를 여는 것까지만.
   관문: 노드 하나가 없거나 07 을 못 냈을 때 **멈추지 않고 사유를 싣는가.**
3. **축 색인과 링크 생성** (`correlate.py`).
   관문: 같은 값이 한 노드에서만 나오면 링크가 없어야 한다.
   관문: 한 노드 안의 반복이 링크를 부풀리지 않아야 한다.
4. **신호등 등급 부여.**
   관문: `rejected` 소견만 인용한 `ref` 로는 링크가 서지 않는가.
5. **`08_campaign.md` 템플릿.**
   관문: 링크 0건일 때 "연결 없음" 과 "노드가 하나뿐" 이 구별되는가.
6. **픽스처로 관통.** 노드 셋짜리 합성 케이스를 `benchmark/fixtures/` 에 만든다.
   실물 증거가 아직 없으므로 **여기까지가 합성으로 잴 수 있는 끝**이다.

**실물이 필요한 자리는 6번 다음입니다.** POS·관리서버 증거가 없고, 키오스크
축 다섯 채널도 아직 미검증입니다(`docs/limitations.md` 2-7). 합성으로 배선을
세워 두고, 증거가 들어오면 그때 잽니다 — 그 순서를 뒤집으면 배선과 실측이
동시에 틀렸을 때 어느 쪽인지 못 가립니다.
