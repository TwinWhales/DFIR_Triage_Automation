# 알려진 한계

**이 도구가 지금 못 하는 것과, 그것이 결과에 어떤 영향을 주는지** 적는
문서입니다. 보고서의 "분석 범위 한계"는 자동 생성되지만, 그 자동 생성이
잡아내지 못하는 층위의 한계가 여기 모입니다.

한계를 아는 것과 모르는 것의 차이가 이 프로젝트의 핵심입니다. 못 본 것을
못 봤다고 말할 수 없으면, "봤는데 없었다"와 구분되지 않습니다.

## 1. 증거 입력

### 디스크 이미지를 직접 열 수 있다 (**부분 해결**)

`evidence.py`의 `VolumeSource`가 이제 `dissect.target` 기반으로
구현돼 있습니다. `--evidence`에 추출된 폴더 대신 raw 이미지 **파일**을
주면 `open_source()`가 자동으로 이쪽으로 갑니다.

**실측(`evidence/test_image.001`, 60GB raw NTFS 볼륨)** — 파티션 테이블
없이 NTFS 볼륨 하나만 담은 형태로, 카탈로그의 7개 아티팩트
전부($MFT·$UsnJrnl·evtx 2종·registry 3종, Amcache 포함)를 04단계
파이프라인 전체로 관통시켜 575,992건을 확인했습니다. `dissect.util
.stream.RunlistStream`이 `seekable() == True`이고 재읽기 값이 원본과
일치함도 실측으로 확인했습니다(`mft.py`의 두 번 순회 패턴과 호환).

**아직 검증 못 한 것**:
- **파티션 테이블이 있는 전체 디스크 이미지**(MBR/GPT, EFI·복구
  파티션이 섞인 형태)도 이제 엽니다(**2026-08-24 해결**). `--volume N`으로
  **사람이 고릅니다.** 도구는 크기나 순서로 추측하지 않습니다 — 복구
  파티션과 시스템 볼륨이 둘 다 NTFS라 자동 판별이 그럴듯하게 틀릴 수
  있고, 잘못 고르면 "아티팩트가 없다"가 아니라 **다른 볼륨의 결과가
  조용히 나옵니다.** 지정하지 않으면 후보를 크기·이름과 함께 보여 주고
  멈춥니다.

  실측(`evidence/0824test.001`, 60GB VMware 물리 디스크): NTFS 2개
  (0.4GiB 복구 + 59.4GiB 시스템)가 나왔고 `--volume 1`로 카탈로그
  8종 전부를 찾았습니다. **일반적인 Win10/11 물리 디스크는 복구
  파티션도 NTFS라 거의 항상 이 분기를 탑니다** — 논리 드라이브만
  뜬 이미지가 예외입니다.
- **폴더 아티팩트(프리패치)도 볼륨에서 읽습니다**(**2026-08-24 해결**).
  그전까지 `VolumeSource.open_all`·`locate_all`이 `NotImplementedError`
  였습니다 — 이미지에서 돌리면 `$MFT`·하이브·evtx는 나오는데 **프리패치만
  통째로 빠졌습니다.** `FileSource._collect`와 같은 규약(이름순 고정,
  0바이트 제외)을 씁니다. 실측 이미지에서 `.pf` 137건을 잡았습니다.
- **E01**은 검증하지 않았습니다. `Target.open`이 `dissect.evidence`로
  같은 경로를 태운다고 문서화돼 있으나 실물 E01로 확인한 적은 없습니다.
- `$UsnJrnl`은 추출 폴더용 이름 후보(`FILE_LAYOUT`)와 별개로
  `evidence.py`의 `VOLUME_PATH_OVERRIDES`에 원본 ADS 경로
  (`$Extend/$UsnJrnl:$J`, 콜론 포함)를 따로 둡니다 — 추출 도구가
  콜론을 못 쓰는 것과 원본 볼륨이 콜론을 그대로 갖는 것의 차이입니다.

E01/dd 이미지를 추출된 파일 단위로 다루려면 여전히 FTK Imager 등으로
**먼저 뽑아 둘 수도 있습니다** — `FileSource`도 그대로 유지됩니다.
`evidence/[root]/` 형태가 그 결과물입니다.

**영향** — 단일 NTFS 볼륨 raw 이미지는 추출 단계 없이 바로 돌릴 수
있습니다. 파티션 테이블이 있는 전체 디스크나 E01은 여전히 사전 추출이
안전합니다.

### 한 실행은 한 볼륨

`$MFT`에는 드라이브 문자가 없어 증거 경로에서 유추합니다. 볼륨이
여럿이면 케이스를 나눠 각각 돌립니다(`C-001-C`, `C-001-D`).

**영향** — 볼륨을 넘나드는 흔적은 사람이 이어 붙여야 합니다.

### Windows 버전 — 어디까지 갈라 보는가 (2026-08-25)

04단계가 SOFTWARE 하이브의 `Microsoft\Windows NT\CurrentVersion`에서
빌드 번호를 읽어 매니페스트의 `windows`에 싣습니다
(`src/stage04_parse/osinfo.py`). 03단계는 증거를 열지 않아 버전을 알 수
없으므로 판정은 증거를 처음 여는 04단계의 몫입니다.

**빌드 번호만 믿습니다.** `ProductName`은 Win11 초기 빌드가 "Windows 10
Pro"라고 적혀 있고, `CurrentVersion`은 Win8.1 이후 전부 "6.3"으로 굳어
변별력이 없습니다.

| 판정 | 빌드 | 확인 상태 |
|---|---|---|
| `win7` | 7600–7601 | **실측** — `evidence/windows7_testimage.001`, 빌드 7601 / Ultimate / Client |
| `win8` | 9200 | **미확인** |
| `win81` | 9600 | **미확인** |
| `win10` | 10240–21999 | **실측** — `evidence/0824test.001`, 빌드 15063 / 1703 / Client |
| `win11` | 22000 이상 | **미확인** |

Win7 실물에서 `CurrentVersion`이 `6.1`이고 `UBR`·`ReleaseId`·`DisplayVersion`이
**없습니다.** 빌드 번호 하나만 필수로 두고 나머지를 선택으로 둔 판단이
여기서 확인됐습니다 — 이 값들을 요구했다면 Win7에서 판정이 통째로 실패합니다.

`family`는 제품명이 아니라 **온디스크 구조 세대**입니다. 서버판은
클라이언트와 빌드를 공유하므로(2008 R2 = 7601, 2012 = 9200, 2016 = 14393)
`win10`이 클라이언트라는 뜻이 아닙니다. 제품 구분은
`windows.installation_type`(Client/Server)이 따로 싣습니다.

#### 버전에 따라 존재하지 않는 아티팩트

`Amcache.hve`(Win8 이상)와 `RecentFileCache.bcf`(Win7)는 **배타적인
짝**입니다. 매핑은 둘 다 요청하고(03단계는 버전을 모릅니다) 04단계가
해당 없는 쪽을 `version_not_applicable`로 뺍니다.

가르기 전에는 Win7 이미지의 Amcache가 `artifact_not_found` — 즉 **"수집
누락"** 으로 기록됐습니다. 보고서를 읽은 분석가는 있지도 않은 파일을
다시 뽑으러 갑니다. 07단계가 이제 두 사유를 다른 문장으로 싣습니다.

**판정에 실패하면 아무것도 거르지 않습니다.** 잘못 거르면 있는 증거를 안
읽지만, 안 거르면 최악이 지금과 같기 때문입니다. 사유는 stderr와
매니페스트 `windows.reason`에 남되 `errors.jsonl`에는 남기지 않습니다 —
저 로그는 아티팩트 단위 실패의 집계이고 버전 판정은 아티팩트가 아닙니다.

#### 아직 버전을 가르지 않는 곳

**이벤트 ID에 버전 조건이 없습니다.** 매핑의 `event_ids`는 전부 Vista 이후
번호(4xxx·7045 등)이고, 일부는 하위 버전에 존재하지 않습니다(`T1053.005`의
4698 등). 구버전 이미지에서 0건이 나와도 "그 버전엔 그 이벤트가 없다"와
"탐지 실패"가 구별되지 않습니다. 아티팩트 단위 가용성만 있고 **이벤트
단위 가용성은 없습니다.**

**XP/2003은 대상이 아닙니다.** `.evt`(evtx 이전 포맷)를 읽지 못하고,
채널 경로가 `Windows/System32/winevt/Logs`로 고정돼 있습니다. 프리패치
버전 17의 자리는 표에 있지만 그것만으로 XP를 지원한다고 할 수 없습니다.

**레지스트리 값 안의 버전별 구조를 해석하지 않습니다.** `AppCompatCache`
(Shimcache — XP/7/8/8.1/10이 전부 다름)·`UserAssist`·`BAM`·`SRUM`은
값이 바이너리 블롭이고 버전마다 포맷이 갈리는데, 파서는 키/값 일반
순회만 합니다. 애초에 매핑에도 없어 미착수 범위입니다.

**섹터 크기가 512로 박혀 있습니다.** `structs/mft_record.py`의
`SECTOR_SIZE`. `apply_fixups`가 인자로 받게 돼 있지만 부트섹터에서 읽어
넘기는 호출자가 없습니다. 4Kn 디스크에서 픽스업이 어긋납니다. Windows
버전 차이는 아니지만 같은 부류의 미완입니다.

### RecentFileCache — 실물 1건으로 확인했다 (2026-08-25)

`evidence/windows7_testimage.001`(Windows 7 Ultimate, 빌드 7601)의 실제
파일 6,742바이트 / 67항목으로 대조했습니다. 명세만 보고 쓴 구조가 그대로
맞았습니다.

| 확인한 것 | 결과 |
|---|---|
| 시그니처 `FE FF EE FF` | 일치 |
| 길이 필드가 **문자 수** | 67항목을 연쇄해 걸었을 때 마지막 항목 끝이 파일 크기와 **정확히 일치**(남은 바이트 0) |
| 독립 경로 대조 | `tools/scan_recentfilecache.py` — 길이 필드를 보지 않고 널로 쪼갠 결과 67건 전부 일치 |
| 04단계 관통 | 67건, `parse_errors` 0 |

**남은 바이트 0이 가장 강한 신호입니다.** 파일 크기는 Windows가 쓴 값이라
우리 해석과 독립인데, 길이 필드의 단위를 바이트로 잘못 잡았다면 첫 항목에서
어긋나 끝까지 갈 수 없습니다.

**아직 남은 것 둘.**

- **외부 도구 대조를 안 했습니다.** 위 둘은 우리가 만든 두 경로라 공통
  오해가 있으면 같은 방향으로 틀립니다. `RecentFileCacheParser`(Eric
  Zimmerman)와 맞춰 보는 것이 남았습니다.
- **이미지가 하나입니다.** 다른 빌드·언어·SP 조합에서 헤더가 다를 수
  있습니다. 헤더의 미상 4필드는 실측값을 구조체 docstring에 적어 뒀고,
  **항목 수(67)와 맞는 값이 없어 개수 필드는 없다**고 판단했습니다.

어긋났을 때 거부하는 검사들은 그대로 둡니다 — 시그니처 불일치는 파일
전체 거부(실제로 본 4바이트를 메시지에 담습니다), 길이 단위 오류는 종결자
검사, 중간 파손은 거기까지 유지하고 남은 바이트 집계.

### 프리패치에서 확인되지 않은 것

**버전 23(Windows 7)만 실물로 확인했습니다.** `evidence/[root]` 73건이
전부 그 버전입니다. 나머지는 아래와 같습니다.

| | 상태 |
|---|---|
| 버전 23 | 실측 73건 — 적재 경로 10,187건 독립 대조 일치. **다만 그 볼륨(`evidence/[root]`)은 지금 디스크에 없어 재확인 불가** |
| **버전 30 / 220바이트** | **실측 137건** — 적재 경로 10,195건 독립 대조 일치 (2026-08-24) |
| 버전 17 / 26 / 31, 버전 30의 216·224 | **명세만.** 실물로 확인한 적 없음 |
| `MAM` 압축 해제 | **실물 137건 해제 성공**(2026-08-24). `RtlCompressBuffer` 왕복 83건 일치 |

`(30, 220)`은 표에 없어서 **한 이미지의 프리패치가 통째로 0건이 됐던**
조합입니다. 아래 2번이 실제로 일어난 사례이고, 자리를 어떻게 확정했는지는
`docs/artifact-notes.md` "2026-08-24 · 프리패치 버전 30 / 220바이트" 참고.

**표의 Windows 이름표를 그대로 믿지 마십시오.** `(30, 224)`에 붙은
"Windows 10 (1809 이하)"와 `(30, 216)`의 "1903 이상"은 [LIBSCCA]를 옮긴
것인데, 실측한 `evidence/0824test.001`은 **빌드 15063(1703)인데 220바이트**
입니다. 1703은 1809 이하이므로 명세대로라면 224여야 합니다. 이름표가
틀렸는지 빌드마다 더 잘게 갈리는지는 확인하지 못했습니다.

**동작은 이 불일치에 영향받지 않습니다.** 파서가 블록 크기를 표에서
가져오지 않고 `메트릭 오프셋 - 헤더 크기`로 파일에서 읽기 때문입니다
(`read_file_information`). 버전 번호만으로 자리를 정했다면 이 이미지의
프리패치가 통째로 어긋났을 자리입니다.

버전별 자리는 `tests/test_prefetch_parser.py`가 합성 파일로 왕복 검증합니다
(17·23·26·30의 세 크기·31). **명세가 맞다는 증명은 아닙니다** — 테스트가
모듈의 표를 가져다 쓰지 않고 명세 값을 따로 적어 대조하므로, 고정되는 것은
"표를 말없이 바꾸지 못한다"입니다.

세 가지가 남습니다.

**1. Win10/11 실물을 읽어 본 적이 없습니다.** 압축 해제는 Windows 자신의
압축기와 왕복이 맞지만 압축기와 복호기가 같은 구현 계열이라 **공통 오해는
잡지 못합니다.** 실물 증거가 들어오면 다시 대조해야 합니다
(`artifact-notes.md` 2026-08-21).

**2. 모르는 레이아웃은 건너뜁니다.** `(버전, 파일 정보 블록 크기)`가 표에
없으면 그 파일만 건너뛰고 `parse_errors`로 셉니다. 새 Windows 빌드가 블록
크기를 바꾸면 **그 시스템의 프리패치가 통째로 0건**이 됩니다. 조용하지는
않습니다 — 매니페스트의 `parse_errors`와 로그에 버전·크기가 함께 남고,
표에 한 줄 추가하면 되는 일임이 메시지에 적혀 있습니다.

**3. 적재 파일의 MFT 참조를 버립니다.** 메트릭 원소마다 파일 참조(엔트리
번호 + 시퀀스)가 있어 `$MFT` 레코드와 상호 참조할 수 있는데, 지금은
`fields.loaded_files`를 **문자열 리스트**로 냅니다. 06단계 `compare`가
리스트를 "원소 중 하나라도 일치"로 보므로 경로를 지목한 문장이 그대로
검증되기 때문입니다. 객체 리스트로 바꾸면 그 성질이 사라집니다.

**영향** — "이 DLL이 그때 그 파일이었는가"는 사람이 이어 붙여야 합니다.

### 레지스트리 — 라이브러리를 우회한 곳 (**해결됨**)

기록으로 남깁니다. **독립 디코더 대조로만 드러난 것들**이라, 대조를 하지
않았으면 그대로 갔습니다. 셋 다 조용히 틀리는 종류입니다.

대조 방법은 `nk`/`vk` 레코드를 명세대로 직접 디코딩해 파서 출력과
맞춰 본 것입니다. 결과(`SYSTEM\CurrentControlSet\Services` 1,754키 +
`SOFTWARE\...\CurrentVersion` 44,393키):

| | 고치기 전 | 고친 뒤 |
|---|---|---|
| 키 이름 | 46,147 / 46,147 | 46,147 / 46,147 |
| LastWrite | **565 / 1,754** (SYSTEM) | **46,147 / 46,147** |
| 값 전체 | 21,473 / 46,147 | **46,142 / 46,147** |

남은 5건은 big data(`db`) 레코드로, 값이 16,344바이트를 넘어 여러 셀로
쪼개진 것입니다(222KB·56KB 등). **python-registry가 맞고 대조 도구가
구현하지 않은 것**이라 파서 문제가 아닙니다.

#### ① 한글 문자열이 잘렸다

python-registry의 `decode_utf16le`가 종결자를 `s.index(b"\x00\x00")`로
찾습니다. **바이트 검색이라 문자 경계를 보지 않습니다.**

```
'볼륨 관리자 드라이버'
 fc bc │ 68 b9 │ 20 00 │ 00 ad │ ...
  볼      륨    공백    관
                └─ 00 00 ─┘   ← 오프셋 5(홀수)에서 끊긴다

라이브러리 : '볼륨 '
실제       : '볼륨 관리자 드라이버'
```

공백(`U+0020`, 고위 바이트 `0x00`) 다음에 `U+XX00` 형태 문자가 오면 두
문자에 걸쳐 `00 00`이 만들어집니다. **한글에 흔한 배치입니다** —
`U+AC00`(가), `U+AD00`(관)처럼 하위 바이트가 `0x00`인 음절이 많습니다.

실측 SYSTEM 하이브에서 **문자열 값 42,578건 중 56건(0.13%)** 이
잘렸습니다. 전부 한글이고, 서비스 표시명과 드라이버 설명이 주로
걸렸습니다.

**이 프로젝트는 한국어 환경이 대상입니다.** 비율은 작지만 걸리는 자리가
보고서에 그대로 실리는 필드입니다. 예외도 경고도 없고 잘린 문자열은 그
자체로 그럴듯해 보입니다.

**조치** — 문자열 타입은 `value.value()`를 쓰지 않고 `raw_data()`를 직접
UTF-16LE로 디코딩합니다. 정렬을 지키므로 가짜 종결자에 걸리지 않습니다.

#### ② `MULTI_SZ` 종결자가 값으로 남았다

`MULTI_SZ`는 각 문자열이 널로 끝나고 목록 전체가 널 하나로 더 끝납니다.
라이브러리가 널 기준으로 그냥 쪼개므로 빈 항목이 둘 남습니다.

```
raw_data : b'r\x00p\x00c\x00s\x00s\x00\x00\x00\x00\x00'
라이브러리 : ['rpcss', '', '']
실제 내용  : ['rpcss']
```

`Services` 1,754개 키 중 **249개**가 이 형태였습니다.

**06단계에 실제 영향이 있습니다.** `compare`가 리스트를 "원소 중 하나라도
일치"로 보므로, 빈 문자열이 남아 있으면 모델이 지어낸 `value: ""` 주장이
**검증을 통과합니다.** 환각 탐지에 구멍이 생깁니다.

**조치** — 끝의 빈 문자열을 뗍니다. 가운데 것은 건드리지 않습니다 —
구조적으로 있을 수 있고 위치가 의미를 가집니다.

#### ③ 타임스탬프가 반올림됐다

python-registry가 100ns를 마이크로초로 줄이면서 `ROUND_HALF_EVEN`으로
**반올림**합니다. 이 프로젝트의 나머지 파서는 전부 `filetime_to_datetime`
으로 **절삭**합니다.

```
raw FILETIME   128920208934228618   (끝자리 8)
라이브러리      .422862   ← 반올림
정수 절삭       .422861
```

1µs 차이라 허용 오차 안이지만, 문제는 값이 아니라 **표기가 사실과
달라지는 것**입니다. 우리 형식은 끝에 `0`을 붙여 7자리를 만듭니다 —
"100ns 자릿수는 버렸다"는 뜻인데, 반올림하면 그 자리가 6번째 자리에
섞여 들어가고 표기는 여전히 버렸다고 말합니다.

evtx가 python-evtx의 `timestamp()`를 우회한 것과 같은 결론입니다
(`artifact-notes.md`). 저쪽은 float 오차였고 이쪽은 반올림이라 원인은
다릅니다.

**조치** — `_nkrecord.unpack_qword(0x04)`로 raw FILETIME을 읽어
`filetime_to_datetime`에 넘깁니다.

회귀 테스트는 `tests/test_registry_parser.py`에 있습니다(한글 잘림,
`MULTI_SZ` 종결자, 가운데 빈 항목 보존, 홀수 길이).

#### `registry:Amcache` — 실물 하이브 구조는 확인, 값 의미는 대조 안 함 (**부분 해결**)

`Amcache.hve`도 regf 포맷이라 `RegistryParser`를 그대로 재사용했습니다
(`HIVE_OF`에 `"registry:Amcache": "Amcache"` 추가).
셀 구조 자체의 정확성은 위 세 가지 우회(한글 잘림·`MULTI_SZ` 종결자·
타임스탬프 반올림)와 `docs/artifact-notes.md`의 `scan_hive_cells.py`
대조가 이미 검증한 것을 그대로 물려받습니다 — SYSTEM/SOFTWARE와 셀
디코딩 경로가 완전히 같기 때문입니다.

**실물 이미지(`evidence/test_image.001`)로 1,140건을 뽑아 구조를
확인했습니다.** `Amcache\Root\Programs\...`, `Amcache\Root
\InventoryApplicationFile\...` 서브키가 예상대로 나오고,
`InventoryApplicationFile` 레코드의 `fields`에 `LowerCaseLongPath`
(전체 경로)·`FileId`(`0000`+SHA1로 보이는 41자리 값)·`BinFileVersion`·
`BinaryType`·`Size`·`ProgramId`가 실제로 담겨 있음을 확인했습니다 —
파서 확충 때 기대한 "실행 파일 경로·SHA1·타임스탬프"가 맞습니다.

**다만 두 가지는 여전히 안 됐습니다.**
- **필드 이름의 의미를 우리가 해석하지 않습니다** — 그럴 필요가
  없습니다. `registry.py`의 설계(가치가 경로·값 이름에 있지 레코드
  자체에 있지 않음, `docs/limitations.md` 6-7)를 그대로 따라 원시
  값만 냅니다. `Programs` 서브키의 필드는 `"0"`·`"1"`·`"17"` 같은
  숫자 이름이라("13": 0, "a": 1787353733 등) 사람이 읽으려면 외부
  문서 대조가 필요한데, 그건 05단계 해석의 몫입니다.
- **매핑(`T1547.001.yaml`)의 `path_prefix`를 아직 안 정했습니다** —
  구조는 확인했지만 "어느 서브키가 조사에 실제로 유용한가"(예:
  `InventoryApplicationFile`만 볼지, `Programs`도 볼지)는 검증하지
  않았습니다. 범위를 좁히면 놓칠 위험이 있어 보류합니다.
- **외부 도구(AmcacheParser 등) 대조는 하지 않았습니다.** 지금까지의
  확인은 "구조가 그럴듯하다"이지 "필드값이 정확하다"의 바이트 단위
  대조가 아닙니다. `docs/artifact-notes.md`에 대조 기록을 남기려면
  이 절차가 남아 있습니다.

### 레지스트리에서 못 보는 것

#### 값에는 타임스탬프가 없다

**이것이 이 아티팩트의 가장 큰 제약입니다.** 타임스탬프는 키(nk)에만
있고 그 키 아래 **모든 값이 하나를 공유합니다.** python-registry도 값에
시각을 물으면 거부합니다 — `ValueError: value does not have a timestamp`.

```
Dnscache LastWrite = 2009-07-14T04:54:53Z
  ├ ImagePath    시각 없음
  ├ Start        시각 없음
  └ ObjectName   시각 없음
```

**영향** — "ImagePath가 이 시각에 설정되었다"는 문장은 **원리적으로 검증할
수 없습니다.** 키 타임스탬프는 "그 키 아래 무언가가 바뀌었다"까지만
말합니다. 06단계 `value_match`는 통과시킵니다(키 타임스탬프와 대조하므로).
**즉 근거가 되지 않는 문장이 통과합니다.** `$MFT`·evtx는 레코드 하나에
시각 하나가 대응하는데 레지스트리만 N:1입니다.

07단계 타임라인도 같은 영향을 받습니다. 키 하나가 값 몇 개를 담고 있든
타임라인에는 한 점으로 찍힙니다.

#### 트랜잭션 로그를 재생하지 않는다

`.LOG1`/`.LOG2`를 읽지 않습니다. 더티 하이브(기본 블록의 시퀀스 번호 두
개가 다름)는 **정상적으로 열리고 정상적으로 파싱되는데 값이 낡았습니다.**
최신 내용이 로그에 있기 때문입니다.

`$UsnJrnl`의 0바이트 껍데기(4-0)와 같은 유형입니다 — 파일이 있고, 파서가
성공하고, 답이 틀립니다. 그래서 조용히 넘어가지 않고 경고를 찍고
`stats.dirty_hive`에 남깁니다.

**다만 매니페스트까지 가지 않습니다.** `parse.py`가 파서 `stats`에서
`parse_errors`와 `unreadable_bytes`만 옮기기 때문입니다. evtx의
`recovered_chunks`도 같은 처지입니다. 콘솔 경고를 놓치면 보고서만 보고는
더티 하이브였는지 알 수 없습니다.

실측(`evidence/[root]`)에서는 SYSTEM·SOFTWARE 둘 다 clean이었습니다.

#### 삭제된 키를 복구하지 않는다

미할당 셀에 남은 `nk`를 읽지 않습니다. python-registry가 할당된 트리만
걷기 때문입니다. 삭제된 Run 키나 서비스가 포렌식적으로 가치가 큰데
보지 못합니다.

`tools/scan_hive_cells.py`가 **개수는 셉니다.** 실측에서 SYSTEM 7건,
SOFTWARE 2건이었습니다. 이 값이 크면 그 증거에서는 복구가 의미 있다는
신호입니다.

#### SAM·SECURITY·NTUSER를 읽지 않는다

SYSTEM·SOFTWARE 둘뿐입니다. `T1136.001`(로컬 계정 생성)의 1차 아티팩트는
SAM 하이브인데 지원하지 않습니다. 사용자별 흔적(NTUSER.DAT의 `Run`,
`RecentDocs`, `TypedPaths`)도 전부 범위 밖입니다.

파서는 그대로 쓸 수 있습니다 — 하이브 형식이 같습니다. `refs.py`의
접두어와 `FILE_LAYOUT` 항목, 카탈로그 등재가 필요합니다.

#### CurrentControlSet은 해석하지만 경로는 실제 이름으로 나간다

`scope`의 `CurrentControlSet`은 `Select\Current`를 읽어 `ControlSet001`로
바꿉니다. 다만 **산출물의 `path`에는 실제 이름이 들어갑니다.**

**영향** — 모델이 `SYSTEM\CurrentControlSet\Services\...`라고 인용하면
06단계가 `ControlSet001`과 대조해 **기각합니다.** 문장은 맞는데
표기가 다른 경우이고, `comparators`가 흡수하지 못하는 종류입니다.
04단계 산출물이 원본에 충실해야 한다는 것과 충돌하므로 06단계에서
풀어야 할 문제로 남깁니다.

#### 장치 속성의 DEVPROP 타입을 못 읽는다 (2026-08-26 실측)

`K-ALERT` 실행에서 04단계가 경고 **90건**을 냈고, 90건 전부 같은 자리였습니다.

```
SYSTEM\ControlSet001\Enum\USB\...\Properties\{GUID}\NNNN
  → Unknown Type Exception (Unknown VK Record type 0x12)
```

`0x12`는 `DEVPROP_TYPE_STRING`입니다. 장치 속성 저장소는 표준 레지스트리
값 타입(`REG_SZ` 등)이 아니라 **DEVPROP 타입 체계**를 쓰는데,
python-registry가 이것을 모릅니다.

**Stage 1(USB 삽입) 증거에는 손실이 없습니다.** 정작 중요한 타임스탬프는
멀쩡히 나옵니다.

```
Properties\{83da6326-97a6-4088-9453-a1923f573b29}\0064  InstallDate       2022-10-24T15:29:48.8920000Z
                                                 \0065  FirstInstallDate  2022-10-24T15:29:48.8920000Z
                                                 \0066  LastArrivalDate   2022-10-24T15:45:41.6995900Z
```

못 읽는 90건은 문자열형 속성(장치 설명·제조사 등)이고, 같은 사실이
`DeviceDesc`·`Mfg`·`HardwareID`·`ContainerID` 같은 평범한 값으로 **이미
따로 들어옵니다.** 그래서 우선순위를 낮게 둡니다 — 다만 경고 90줄이
04단계 출력을 덮어 다른 경고를 가릴 수 있습니다.

### evtx에서 못 보는 것

- **메시지 문자열을 만들지 않습니다.** 이벤트 로그 뷰어가 보여 주는 문장은
  제공자 매니페스트(DLL 리소스)와 `<Data>` 값을 합성한 결과입니다. 우리는
  원시 값만 냅니다. `fields`에 재료가 다 들어 있어 해석은 되지만, 보고서에
  뷰어와 같은 문장이 실리지는 않습니다.
- **`EventID`만으로 이벤트를 특정하지 않습니다.** ID는 제공자 안에서만
  유일합니다. `fields.Provider`에 제공자를 함께 실어 두었으나,
  03단계의 `event_ids` 선별은 제공자를 구분하지 않습니다. 다른 제공자가
  같은 번호를 쓰면 함께 딸려 옵니다.

  **채널을 늘리면서 이 위험이 현실이 됐습니다**(2026-08-24). NetworkProfile의
  `10000`(네트워크 연결)은 `T1200` 매핑이 `evtx:System`에 요청하는 Kernel-PnP
  `10000`과 번호가 같습니다. 새 플래그 룰(`firewall_config_changed`·
  `bits_transfer`·`network_state_changed`)은 그래서 기존 룰과 달리
  `evtx:*`가 아니라 **정확한 아티팩트 이름**으로 겁니다.

  **기존 룰들은 아직 `evtx:*`입니다.** 지금 카탈로그에서는 번호가 겹치지
  않아 문제가 없지만, 채널을 더 늘리면 다시 확인해야 합니다 — 조용히
  틀리는 쪽입니다.

### 네트워크 흔적 — 절반만 볼 수 있다 (2026-08-24)

키오스크 사고에서 "외부 서버로 데이터를 보냈는가"를 물었더니 **카탈로그에
네트워크 아티팩트가 하나도 없었습니다.** 그래서 보고서의 "확인하지 못한
아티팩트"에도 나타나지 않았습니다 — 안 본 것을 안 봤다고 말하지도
못하는 상태였습니다.

**붙인 것** — `evtx:Firewall`·`evtx:BITS`·`evtx:NetworkProfile`. 파서는
새로 만들지 않았습니다(채널만 다르고 형식이 같습니다). 대조 기록은
`docs/artifact-notes.md` "2026-08-24 · evtx 채널 확장". 기법은 `T1562.004`
(방화벽 무력화)와 `T1197`(BITS Jobs)을 `KNOWN_TECHNIQUES`에 더하고 매핑을
새로 썼습니다.

**여전히 못 보는 것** — 여기가 중요합니다.

| 아티팩트 | 무엇을 담나 | 왜 못 읽나 |
|---|---|---|
| SRUM (`SRUDB.dat`) | **앱별 송수신 바이트** | ESE 포맷. 신규 라이브러리 필요 |
| WebCache | 브라우저 방문·다운로드 | ESE 포맷 |
| `qmgr.db` | BITS 작업 큐 원본 | ESE 포맷 |
| NTUSER.DAT | 사용자별 흔적 | 사용자 프로필마다 하나 (다중 매칭 미지원) |
| DNS 클라이언트 로그 | 조회한 도메인 | 기본적으로 비활성 |

**SRUM이 가장 아픕니다.** "어느 프로그램이 얼마를 보냈나"에 직접 답하는
유일한 아티팩트인데 못 읽습니다. 실측 이미지에서 640KB로 존재하고,
`dissect.database`의 `ESE`로 열리는 것까지는 확인했습니다 — 즉 트랙 B
후보 중 가장 값이 큰 자리입니다.

#### 그리고 증거 자체에 없는 것

도구를 고쳐도 안 되는 층이 있습니다. 실측 이미지 기준:

```
Security.evtx 912건 중
  5156 (연결 허용/WFP)  0건   ← 연결 감사가 꺼져 있었다
  5158 (바인드)          0건
  4688 (프로세스 생성)  41건 — 사고 시간창 안 0건
```

**연결 단위 기록이 아예 없습니다.** 방화벽 로그(WFP)는 연결이 아니라
**규칙 변경**만 남기므로 이것을 대신하지 못합니다. 어떤 도구를 붙여도
"어느 IP로 얼마를 보냈다"는 이 증거에서 나오지 않습니다.

**영향** — 네트워크 관련 결론은 두 가지를 나눠 적어야 합니다. "우리가 안
본 것"(SRUM 등)과 "아무도 못 보는 것"(연결 감사 미설정). 섞으면 도구의
한계가 증거의 한계로 둔갑하거나 그 반대가 됩니다.
- **손상 구간의 레코드 수를 모릅니다.** 라이브러리가 청크를 조기 종료하면
  못 읽은 바이트 수는 알아도 그 안에 몇 건이 있었는지는 알 수 없어,
  `parse_errors`에 "구간 1건"으로 셉니다. 실제 유실 건수는 그보다 많습니다.

### $MFT만으로는 알 수 없는 것

`[LIBFSNTFS]`가 "$MFT metadata file only parsing"으로 정리한 것과 같습니다.

- 속성 목록(`$ATTRIBUTE_LIST`)이 `$MFT` 밖에 저장된 경우
- `$I30` 인덱스가 `$MFT` 밖에 있는 경우
- 부모 MFT 엔트리가 재사용됐으면 경로 재구성이 어긋남

**영향** — 고아 레코드는 만들 수 있는 만큼만 경로를 냅니다. 경로가
없다고 레코드를 버리지는 않습니다(삭제 흔적을 놓치므로).

### $UsnJrnl에는 경로가 없다

USN 레코드는 파일 **이름**만 담습니다. 전체 경로를 얻으려면
`parent_entry`로 `$MFT`를 되짚어야 하는데, 파서가 그것을 하지 않습니다 —
한 아티팩트를 읽는 동안 다른 아티팩트에 의존하면 "무엇을 읽어 무엇이
나왔는가"가 흐려지기 때문입니다.

**영향** — `scope`의 `path_prefix`를 **적용할 수 없습니다.**
`extensions`만 이름에 적용됩니다. 03단계가 경로로 좁혀 달라고 해도
넓게 나옵니다. 좁히다 증거를 놓치는 것보다 낫다는 판단이지만, 아래
4-2의 원인이기도 합니다.

### K-001 설계서 대응 — 무엇을 열었고 무엇이 여전히 안 되나 (2026-08-25)

「K-001 공격 시나리오 설계서」의 Stage 1~7이 요구하는 아티팩트를 카탈로그와
대조하고, 열 수 있는 것을 열었습니다. **먼저 결론**: Tier 1 아티팩트 36개
중 24개가 이제 됩니다(이전 15개).

#### 연 것 — evtx 채널 아홉

전부 evtx 파서 재사용이라 새 파서가 없습니다.

| 아티팩트 | 채널 | Stage |
|---|---|---|

랩에 설치돼 있어야 하고, 없으면 `artifact_not_found` 로 빠집니다.

#### 검증하지 않은 채 채운 값

**이벤트 ID를 전부 추정으로 넣었습니다.** 공개 DFIR 자료와 설계서 §2의
서술에서 골랐고 실제 증거로 대조한 적이 없습니다. 신뢰도가 낮은 순:

- **`evtx:AssignedAccess` 세 채널의 이벤트 ID를 모릅니다.** 그래서
  `kiosk_restriction_event` 플래그가 `event_id` 로 좁히지 않고 **전
  레코드에 붙습니다.** "전 레코드에 붙는 플래그는 필터 역할을 못 한다"는
  원칙의 의도적 예외이고, 근거는 "세 채널 다 로그가 작다"입니다.
  **그 전제를 실측으로 확인하지 않았습니다** — 키오스크가 이 채널을 수만
  건 남기면 05단계 쿼터를 혼자 태웁니다.
- **`device_connected` 의 ID 목록**(DriverFrameworks 2003·2100·2102 계열,
  Kernel-PnP 400·410 계열) — 위 `T1200` 20001/10000 과 같은 부류입니다.
- **`remote_session` 의 ID 목록**(1149, 21·22·24·25) — RDP 관련 ID는
  공개 자료가 비교적 일치하지만 우리 증거로 확인하지는 않았습니다.
- **`shell_spawned` 의 실행 파일 목록** — 설계서가 든 cmd/explorer/taskmgr
  에 관례적으로 함께 보는 것들을 더했습니다. **키오스크 실물에서 정상
  운영 중 이 목록이 얼마나 뜨는지 모릅니다.**
- **`unexpected_parent_process` 가 `explorer.exe` 를 이상 징후로 봅니다** —
  잠긴 키오스크에서 셸이 주문 UI 로 대체된다는 전제입니다. 설계서 §1.3 의
  M1(현실 오구성)에서는 서드파티 키오스크 SW 가 explorer 위에서 도는 경우가
  있어 **정상 부모가 될 수 있습니다.** 그러면 이 룰이 전량을 잡습니다.
  랩 구성이 정해지면 다시 봐야 합니다.
- **`execution_from_unusual_path` 가 `C:\ProgramData` 를 뺐습니다** — Mock
  POS 가 거기 놓일 예정이라 넣으면 정상 POS 실행이 전량 걸립니다. POS 설치
  경로가 정해지면 다시 판단합니다. 같은 이유로 `pos_db_root`·`data_root`
  기본값도 임시입니다(아래).
- **`{pos_db_root}`·`{data_root}`·`{staging_root}` 기본값** — Mock POS 앱이
  개발되지 않아 거래 DB 위치를 모릅니다(설계서 §9 D1). 이 변수들은 시나리오
  `entities` 에서 채워지는 다섯에 없어 **항상 기본값이 쓰입니다.** 틀리면
  `T1565.001`·`T1005`·`T1657` 의 Tier 1 `$MFT` 요청이 0건을 내는데, 경로를
  잘못 짚은 것인지 흔적이 없는 것인지 산출물만 보고는 구별되지 않습니다.

#### 게이트 4를 자동으로 검사하게 했다 (2026-08-25, 자체 점검에서 발견)

매핑에 `event_ids` 를 적어도 **그것을 받는 flag 가 없으면 05단계에 한 건도

K-001 매핑을 쓰면서 이 구멍을 **13개 만들었습니다.** Sysmon 11·22 와
Security 4634·4647·4722·4724·4735·4737·4738·4778·4779 입니다. 같은 검사가

`tests/test_flag_rules.py` 의 `test_every_mapped_event_id_has_a_flag_that_
receives_it` 가 이제 이것을 막습니다. 예외는 두 목록에만 적을 수 있고,
둘 다 **매핑에 실제로 남아 있는 조합인지** 함께 검사합니다.

#### flag 의 사정거리가 채널을 늘릴 때마다 넓어지고 있었다 (2026-08-25, 코드 리뷰)

`account_created`·`privileged_group_add`·`logon_success`·`logon_failed`·
`service_config_changed`·`service_installed` 여섯이 `artifact: evtx:*` 로
걸려 있었습니다. **채널이 5개에서 14개가 되면서 같은 룰이 새 채널 전부에
걸리게 됐고, 그 재확인을 하지 않았습니다.**

EventID 는 **제공자 안에서만** 유일합니다. 채널은 그 근사치입니다 — 실측하면
`System.evtx` 하나에 제공자가 22개입니다(Win7 7601). 다만 **같은 채널 안에서
두 제공자가 같은 ID 를 쓴 경우는 0건**이었고, 진짜 위험은 채널 사이입니다.

| | Win7 7601 실측 |
|---|---|
| `evtx:System` | 1,468건 / 제공자 **22개** / 채널 내 ID 충돌 0건 |
| `evtx:Security` | 8,013건 / 제공자 2개 / 채널 내 ID 충돌 0건 |

**실제로 뚫려 있던 통로는 AssignedAccess 세 채널입니다.** `T1059.003` 이
`scope_template: {}` 로 요청해 event_id 필터 없이 전량 파싱되는데, 그 채널의
ID 를 우리가 모르는 채로 여섯 룰에 노출돼 있었습니다. 4624·4720·7045·4732
중 하나라도 쓰면 그 레코드에 로그온·계정 생성·서비스 설치 플래그가 붙습니다.

여섯을 정확한 채널명으로 좁혔습니다. **각 룰의 `artifacts:` 선언은 처음부터
맞는 채널을 적고 있었습니다** — 룰이 그 선언을 안 지키고 있었을 뿐입니다.

#### `evtx:Firewall` 이 안 가진 것을 요청하고 있었다

`T1041`·`T1048` 이 `evtx:Firewall` 을 Tier 1 로 걸고 rationale 에 "아웃바운드
연결의 허용·차단 기록"이라고 적었는데, **그 채널에는 그런 기록이 없습니다.**
`Windows Firewall With Advanced Security/Firewall` 이 담는 것은 방화벽 규칙·
프로필의 **구성 변경**입니다(그쪽은 `T1562.004` 가 봅니다).

연결 단위 허용/차단 감사는 Security 의 5152·5156·5157(필터링 플랫폼)에
있습니다. **걸지 않았습니다** — 기본 감사가 꺼져 있어 대개 안 남고, 켜면
정상 트래픽으로 로그가 가득 차 05단계 쿼터를 혼자 태웁니다. 외부 통신의
근거는 Sysmon 3·22 가 Tier 1 로 들고 있습니다.

그 결과 K-001 에서 `evtx:Firewall` 은 **제외**로 나갑니다. 이 시나리오의
기법 중 그 채널을 요구하는 것이 없기 때문이고, 그것이 사실입니다.

`tests/test_flag_rules.py`. 넷 다 **일부러 되돌려 실제로 잡는 것을 확인**
했습니다 — 통과만 보고 믿으면 가드가 죽어도 모릅니다.

| `test_a_whole_channel_request_has_a_flag_that_can_receive_it` | 채널 전체를 요구했는데 받을 절이 없다 |
| `test_the_known_gap_list_does_not_rot` | 예외 목록이 실제 매핑과 어긋난 채 남는다 |

**세 번째 검사가 아는 것은 기계적 증상뿐입니다.** "받아 줄 절이 없다"까지고,
rationale 이 틀렸는지는 사람이 채널 내용을 확인해야 나옵니다. 위 Firewall 건도
그 순서로 드러났습니다 — 가드가 걸림 → 왜지 → 채널 내용 확인 → rationale 이
틀렸음. 여기서 걸리면 "고쳐라"가 아니라 **"왜 그런지 보라"** 는 신호입니다.

커버리지 계산에서 전역 표식(`artifact: "*"` + `match` 없음)을 제외하는 것도
**이름이 아니라 성질로** 바꿨습니다. 예전에는 `outside_time_range` 라는 이름을
박아 두었는데, 그러면 전역 표식이 하나 더 생기는 순간 모든 조합이 "덮였다"로
계산돼 검사가 조용히 죽습니다. 실패하지 않으므로 죽었다는 사실도 안 드러납니다.

#### Sysmon EID 1 을 이름이 아니라 맥락으로 가른다 (2026-08-25)

처음에는 `shell_spawned` 하나였습니다 — `fields.Image` 가 셸·시스템
유틸리티인 것만 잡는 룰입니다. **그것만으로는 K-001 Stage 2 를 못 잡습니다.**
그 단계가 겨냥하는 것은 USB 안의 비승인 실행파일이고, **공격자가 무엇을
실행할지는 우리가 알 수 없습니다.**

이름 대신 **맥락**으로 거는 룰 둘을 더했습니다. 셋이 겹치지 않는 사실을 봅니다.

| flag | 무엇을 보나 | 겨냥하는 단계 |
|---|---|---|
| `shell_spawned` | **무엇이** 실행됐나 (`fields.Image` 가 셸) | Stage 3 (키오스크 이탈) |
| `execution_from_unusual_path` | **어디에** 있나 (비시스템 볼륨·쓰기 가능 경로) | Stage 2 |
| `unexpected_parent_process` | **누가** 실행시켰나 (`fields.ParentImage`) | Stage 2·3 |

실제로 갈리는지 확인했습니다.

```
USB 에서 직접 실행 (E:\banker.exe)   execution_from_unusual_path
Temp 로 복사 후 실행                 execution_from_unusual_path
explorer 가 띄운 것                  unexpected_parent_process
셸 획득 (cmd.exe)                    shell_spawned
정상 POS 앱 / svchost                (없음)   ← 걸러진다
```

**부정으로 쓰지 않은 것이 핵심입니다.** "`C:` 로 시작하지 않으면"이 한 줄로
끝나는데, 그렇게 쓰면 형식 가정이 틀렸을 때 **전량이 걸립니다** — Sysmon
설정에 따라 `Image` 가 `\Device\HarddiskVolume2\...` 로 올 수 있고 그러면
정상 프로세스 생성이 모두 신호가 되어 05단계 쿼터를 통째로 태웁니다.
긍정으로 열거하면 형식이 다를 때 아무것도 안 걸립니다 — 그것도 문제지만
조용히 넘어가는 쪽이지 필터를 죽이지는 않습니다.

**실물 Sysmon 로그를 한 번도 파싱해 본 적이 없어서 내린 판단입니다.**
두 이미지 다 Sysmon 이 설치돼 있지 않습니다(기본 탑재가 아닙니다).

#### 넣지 않은 것 — 화이트리스트 역탐지

가장 확실한 방법은 **"알려진 정상 프로세스 목록을 제외한 전부"** 입니다.
키오스크는 도는 프로세스가 극도로 제한적이라 이 방식이 잘 듣습니다.
넣지 않은 이유가 둘입니다.

**① 목록이 환경마다 다릅니다.** `_flags.yaml` 은 **전역 어휘**이고, 어느
키오스크에 무엇이 설치돼 있는지는 그 이미지의 사실입니다. 여기에 특정 랩의
프로세스 목록을 박으면 다른 환경에서 전량이 걸립니다. `privileged_groups`
처럼 런타임에 읽는 자리를 두는 선례가 있지만, 그 목록 자체를 어디서 받을지가
정해져 있지 않습니다.

**② 그 목록은 Stage 0 베이스라인에서 나옵니다.** 설계서가 "베이스라인 없이는
이상을 판단할 수 없다"며 D3 에서 먼저 수집하기로 한 데이터인데, **아직
수집되지 않았습니다.** 지금 목록을 지어내면 그것이 검증되지 않은 가정으로
파이프라인 한가운데 박힙니다.

**베이스라인이 들어오면 이것이 가장 강한 필터가 됩니다.** 그때 필요한 것은
부정 매처 하나와 목록을 04단계에 넘길 통로이고, 둘 다 지금 없습니다.

#### 남겨 둔 구멍 하나 — `evtx:System` 7034·7036

`T1543.003` 이 요청하는데 받을 flag 가 없습니다. **일부러 남겼습니다.**

7036(서비스 상태 변경)은 정상 부팅에서만 수백 건이 나옵니다. flag 를
만들면 필터가 죽고, 안 만들면 이 요청이 모델에 닿지 않습니다. 어느 쪽이
나은지는 **실제 키오스크 로그의 분포를 봐야** 정해지고 지금 그 데이터가
없습니다. 7034(비정상 종료)는 드물지만 같은 채널·같은 판단이라 함께 뒀습니다.

`_KNOWN_GAPS` 에 사유와 함께 적혀 있어, 목록에서 지우면 테스트가 막습니다.

#### 상하위 기법이 남남이다

설계서가 Stage 2에 `T1059`(상위), Stage 3에 `T1059.003`(하위)를 쓰고,
Stage 4에 `T1078`(상위)을 쓰는데 우리에겐 `T1078.003`(하위)도 있습니다.
**`attack.py` 에 상하위 관계를 아는 코드가 없어 둘은 완전히 다른
문자열입니다.** 매핑을 양쪽 다 써 두어 어느 쪽이 와도 선별되게 했지만,
02단계가 어느 쪽을 내느냐에 따라 **선별되는 아티팩트 집합이 달라집니다.**
정답 데이터의 `expected_techniques` 와 02단계 출력이 어긋나면 기법 식별
재현율이 실제보다 낮게 집계됩니다. D1에서 못 박아야 할 항목입니다.

### 매핑 — 검증되지 않은 채 채운 항목 (키오스크 시나리오, 2026-08-23)

키오스크 침해사고 시나리오([[kiosk-scenario-goal]] 참고 — 웹셸은 벤치마크
케이스일 뿐 목표가 아니다)가 05단계에 도달하지 못해 막혀 있던 세 지점을
메꾸려고 `T1091`·`T1200`·`T1547.001` 매핑을 새로 채웠습니다. **실제
증거 이미지로 대조하지 않은 "임의 채움"이며, 아래는 신뢰도가 낮은 순으로
적습니다.**

- **`T1200.yaml`의 이벤트 ID(20001, 10000)** — 공개 DFIR 자료에서 흔히
  인용되는 UserPnp/Kernel-PnP 이벤트 ID를 추정으로 넣었습니다. 이
  프로젝트의 실제 이미지로 대조한 적이 없습니다. 실증거에서 걸리지
  않으면 매핑이 아니라 모델 문제로 잘못 집계될 수 있습니다.
- **`T1547.001.yaml`이 HKLM Run/RunOnce만 봅니다** — HKCU 쪽(사용자별
  자동실행)은 `NTUSER.DAT`가 필요한데 지금 카탈로그는 볼륨 공용 하이브
  (`SYSTEM`·`SOFTWARE`)만 지원합니다 — 사용자별 하이브 다중 매칭이
  아직 없습니다. 단일 로컬 계정으로 상시 로그인되는 키오스크에서는 영향이
  작을 것으로 보고 우선 이렇게 두었으나 검증하지 않은 가정입니다.
- **`T1091.yaml`의 `$UsnJrnl` 요청에 `path_prefix`가 없습니다** — 이동식
  매체에서 옮겨진 파일이 어느 경로에 놓일지 미리 알 수 없어 확장자만
  걸었습니다. 바쁜 볼륨에서는 `file_created` 플래그가 붙는 레코드가
  많아질 수 있고, 05단계 `record_filter`의 `DEFAULT_LIMIT`(60건) 안에
  더 급한 신호가 밀릴 위험이 있습니다.

**영향** — 세 매핑 다 "선별이 이 아티팩트를 보게는 한다"는 배선 확인
수준입니다. 재현율·정확도는 실제 키오스크 증거로 돌려 보기 전까지
모릅니다. 대조하면 이 절을 갱신하십시오(`work-guide.md` 3.2와 같은
의무 — 다만 이번 건은 매핑 도메인 지식이라 파서처럼 자동화된 대조
도구는 없고, 사람이 직접 아티팩트를 열어 확인해야 합니다).

#### 2차 추가분 5종 (같은 날, `mapping_table_version` 0.7)

`T1547.004`·`T1546.008`·`T1078.003`·`T1112`·`T1562.001`을 더 채웠습니다.
**같은 성격의 임의 채움이며**, 신뢰도가 낮은 순으로 적습니다.

- **`T1112.yaml`의 `AssignedAccessConfiguration` 경로** — 다중 앱 키오스크
  설정이 이 키에 남는다는 것은 공개 자료 기준 추정입니다. 단일 앱 키오스크는
  다른 자리(LogonUI 계열)를 쓴다고 알려져 있는데 확인하지 않았습니다.
- **`T1112`는 기법 전체가 아니라 "정책·잠금 설정 변조"로 좁혀져 있습니다.**
  `path_prefix` 없이 SOFTWARE를 요청하면 156,716건이 나와 선별이 의미를
  잃기 때문입니다(`_artifacts.yaml` 주석). 랜섬웨어의 복구 설정 변조 같은
  다른 T1112 용례는 이 매핑으로 잡히지 않습니다. 매핑 이름과 실제 범위가
  어긋나 있다는 뜻이므로, 다른 시나리오를 붙일 때 반드시 넓혀야 합니다.
- **`T1546.008`의 접근성 프로그램 7종 목록** — `sethc`·`utilman`은 확실하나
  `AtBroker`·`DisplaySwitch`는 Windows 버전에 따라 존재하지 않을 수 있습니다.
  없는 경로를 걸면 조용히 0건이 되고, 그것이 "흔적 없음"과 구별되지 않습니다.
- **`T1562.001`의 서비스 이름 5종** — `WinDefend`·`wscsvc`·`EventLog`는
  표준이지만 `Sense`·`WdNisSvc`는 Defender ATP 구성에 따라 없을 수 있습니다.

**영향** — 위와 같습니다. 다만 이번 5종은 앞의 3종과 달리 **evtx·$MFT 경로가
섞여 있어 일부는 실제로 05단계까지 도달합니다.** 아래 절에 가른 결과가 있습니다.

#### 새 매핑이 05단계에 도달하는지 (실측)

관문 4를 기법별로 확인한 결과입니다. 대표 레코드를 만들어
`flagging.apply_all` → `allocation.allocate_records`(카탈로그의 실제
`signal_source`를 준 상태)를 태웠습니다.

| 기법 | Tier 1 아티팩트 | 플래그 | 05단계 전달 |
|---|---|---|---|
| T1078.003 | evtx:Security (4624·4625·4672) | 5/5 | **5/5** (`logon_success`/`logon_failed` 신설) |
| T1562.001 | evtx:System (7040·7045) | 5/5 | **5/5** (`service_config_changed` 신설) |
| T1546.008 | $MFT (접근성 바이너리) | 5/5 | **5/5** (`timestamp_mismatch`) |
| T1546.008 | registry:SOFTWARE (IFEO) | 0/5 | **5/5** (`signal_source: scope`) |
| T1547.004 | registry:SOFTWARE (Winlogon) | 0/5 | **5/5** (`signal_source: scope`) |
| T1112 | registry:SOFTWARE·SYSTEM | 0/6 | **6/6** (`signal_source: scope`) |
| T1547.001 | registry:Amcache | 0/5 | **5/5** (`signal_source: scope`) |

**레지스트리 쪽 플래그가 0인 것은 그대로입니다.** 달라진 것은 그것이
탈락 사유가 아니게 된 점입니다 — 05단계 배분이 아티팩트별로 자리를
나누므로 질문이 "신호냐"에서 "몇 자리를 줄 것이냐"로 바뀌었습니다(6-7).

이 매핑들을 처음 쓸 때는 `T1112`가 Tier 1이 레지스트리뿐이라 **매핑은
있으나 사실상 작동하지 않는 유일한 기법**이었습니다. `T1547.004`도
레지스트리가 본체이고 `$MFT`는 Tier 2(루프백 없음)라 같은 상태였습니다.
둘 다 배분이 들어오면서 풀렸습니다.

`flagging.py`에 "Winlogon 하위면 신호" 같은 룰을 넣어 때우지 않은 것은
잘한 선택으로 남았습니다. 그렇게 했으면 지금 배분이 들어온 뒤 룰을 도로
걷어내야 했을 것이고, 그 사이 나온 수치는 플래그가 부풀려진 값이었을
것입니다.

## 3. 파이프라인 구조

### Tier 2 루프백이 없다

03단계는 아티팩트를 Tier 1(즉시 읽음)과 Tier 2(조건부 유예)로 나누지만,
**그 조건을 평가하는 루프가 구현돼 있지 않습니다.** `deferred` 항목은
전부 미발동으로 처리됩니다.

**영향** — 예전에는 보고서에 `Tier 2 조건 미충족`이라고 적혔는데, 실제로는
**조건을 평가한 적이 없습니다.** C-100-C에서 `$MFT`가 `deleted` 69건을
냈는데도 `$UsnJrnl`이 "조건 미충족"으로 기록된 것이 그 예입니다 —
평가했는데 안 걸린 것처럼 읽혀 사실과 달랐습니다.

**표기는 고쳤습니다.** 이제 `Tier 2 루프백 미구현으로 미평가 (조건: …)`로
적힙니다. `trigger` 문장은 그대로 실으므로, 읽는 사람이 "무엇을 보면
이걸 봤어야 하는가"를 알 수 있습니다.

**루프백 자체는 여전히 미구현이며 명시적 비목표입니다**(`work-guide.md`
1.4). 표기가 사실과 맞아진 것이지 기능이 생긴 것은 아닙니다.

### 07단계는 LLM을 쓰지 않는다

스펙은 sLLM으로 적었으나 의도적으로 템플릿 렌더링만 합니다. 검증을
통과한 문장을 모델이 다시 쓰게 하면 마지막 단계에서 환각이 재유입되고,
앞의 모든 검증이 무의미해집니다.

**영향** — 한계가 아니라 설계 결정입니다. 다만 스펙과 다릅니다.

## 4. 결과 해석에 영향을 주는 것 — 미해결

### 4-1. 04단계의 스킵이 보고서에 도달하지 않았다 (**해결됨**)

기록으로 남깁니다. 고치기 전 보고서는 이랬습니다.

```markdown
## 분석 범위 한계

카탈로그의 모든 아티팩트를 확인했습니다.
```

같은 실행에서 04단계는 3개 중 1개만 읽었습니다. **누락이 아니라 거짓
진술이었습니다.** 침해사고 보고서에서 "보안 이벤트 로그까지 봤는데
깨끗하다"와 "보안 이벤트 로그를 못 구했다"는 완전히 다른 문서입니다.

원인은 `_limits()`가 `03_selection.json`의 `excluded`·`deferred`만 본 것
입니다. `selected`에 들어간 뒤 04단계에서 스킵된 것을 볼 경로가 없었고,
스킵은 `errors.jsonl`에만 남았습니다.

**조치 — 네 가지.**

1. **04가 스킵을 매니페스트에 남깁니다.** `_manifest.json`의 `skipped`에
   아티팩트·사유코드·메시지가 들어갑니다. 매니페스트는 04가 자기 일을
   적는 곳이므로 "안 한 일"도 여기가 맞습니다. `errors.jsonl`은 전 단계가
   공유하는 집계용이라 07이 그것을 파싱하면 에러 로그 형식에 묶입니다.
2. **07이 차집합으로 검산합니다.** `selected` − (`files` ∪ `skipped`)에
   남는 것이 있으면 04가 기록을 빠뜨린 것이므로 "사유를 남기지 않았습니다"
   로 표에 올립니다. 새 실패 유형이 생겨도 조용히 사라지지 않습니다.
3. **무엇을 봤는지도 적습니다.** "안 본 것"만 적으면 범위가 반쪽입니다.
   `### 확인한 아티팩트`에 레코드 수와 부분 판독 여부가 실립니다.
4. **"모든 아티팩트를 확인했습니다"를 없앴습니다.** 선별 자체가 놓친 것은
   이 도구가 알 수 없으므로 단정할 수 없습니다. 대신 선별 범위 안에서의
   진술임을 명시합니다.

부수적으로, 읽은 아티팩트가 `deferred`에도 있으면 "확인함"과 "확인 못 함"
양쪽에 실리던 문제도 막았습니다. 산출물이 있다는 사실을 더 강한 증거로
봅니다.

사유는 **분석가가 할 일이 다르므로** 나눠 적습니다.

| 사유 코드 | 보고서 문구 | 분석가의 조치 |
|---|---|---|
| `artifact_not_found` | 증거에 없음 (수집 누락) | 다시 수집 |
| `empty_artifact` | 파일이 0바이트 (추출 확인 필요) | 다시 추출 |
| `parser_missing` | 본 버전 미지원 (파서 없음) | 다른 도구로 확인 |

회귀 테스트는 `tests/test_report.py`("04가 읽지 못한 것이 보고서에
실리는가")에 있습니다.

### 4-1-1. 남은 것 — 선별이 놓친 것은 여전히 알 수 없다 (미해결)

4-1이 닫은 것은 **"선별했는데 못 읽은 것"**입니다. 그보다 한 겹 위는
그대로입니다 — **03단계가 애초에 선별하지 않은 것**은 보고서에 나타나지
않습니다.

`_artifacts.yaml` 카탈로그에 있는 아티팩트는 `excluded`로 실리지만,
**카탈로그에 없는 것은 존재하지 않는 것과 같습니다**(`mapping-guide.md`).
지금 카탈로그는 `$MFT`·`$UsnJrnl`·evtx 2종·registry 2종·`prefetch`·
`$LogFile`뿐입니다. ShimCache·Amcache·Jump List·브라우저 이력, 그리고
레지스트리 중에서도 SAM·SECURITY·NTUSER는 목록에 없으므로 "확인하지 못한
아티팩트"에도 오르지 않습니다.

**영향** — 보고서의 "확인하지 못한 아티팩트" 표는 **이 도구가 아는 범위
안에서만 완전합니다.** 그래서 템플릿이 "선별된 아티팩트를 모두 확인했습니다"
라고만 쓰고 "카탈로그의 모든 아티팩트"라고 쓰지 않습니다. 문구를 좁힌
것이지 문제를 푼 것은 아닙니다.

이것은 선별 방식 자체의 리스크이며 **재현율로 측정할 대상**입니다
(`work-guide.md` 1.2). 매핑을 채워 나가면서 재현율이 어떻게 변하는지
`mapping_table_version`으로 추적합니다.

### 4-0. 0바이트 껍데기가 진짜 저널을 가렸다 (**해결됨**)

기록으로 남깁니다. **증거가 있는데도 0건을 보고하던 문제**입니다.

실측(`evidence/[root]`, Windows 7 시스템 볼륨):

| | 고치기 전 | 고친 뒤 |
|---|---|---|
| 읽은 파일 | `$Extend\$UsnJrnl` (0바이트) | **`$J` (34,406,400바이트)** |
| `record_count` | **0** | **306,857** |

원인은 두 가지가 겹친 것이었습니다.

**① 탐색이 껍데기를 먼저 잡았다.** `_probe`가 `relative_paths`를 순서대로
훑다가 `$Extend/$UsnJrnl`에서 멈췄습니다. 파일이 **존재하되 0바이트**인데
존재만 보고 채택했고, `filenames`에 등록된 `$J`에는 도달하지 못했습니다.

`$UsnJrnl:$J`는 콜론이 파일명에 못 들어가 도구마다 다르게 저장되는데,
**추출본이 껍데기(이름 없는 `$DATA`)와 알맹이(`$J`)를 둘 다 내놓는 경우**가
이 조합입니다.

**② `$UsnJrnl` 파서가 빈 스트림에 침묵했다.** evtx는 같은 상황에서
`ValueError`로 중단하고 `$MFT`는 시그니처로 걸리는데 이것만 조용했습니다.

**조치** — 셋 다 했습니다.

1. `_probe`·`_search`가 **0바이트 후보를 건너뜁니다.** 크기 0은 내용이
   다른 스트림에 있다는 신호이므로 다음 후보로 넘어갑니다.
2. 건너뛴 껍데기를 **버리지 않고 남깁니다.** `Located.empty_candidates`에
   담겨 매니페스트의 `source_empty_skipped`로 나가고, 콘솔에 경고가
   찍힙니다. **추출이 잘못됐다는 진단이므로 조용히 넘어가면 안 됩니다.**
3. 후보가 **전부 0바이트면** `EmptyArtifact`로 중단합니다. `ArtifactNotFound`를
   상속해 04단계 처리는 같지만 메시지가 다릅니다 — "수집 안 됨"과
   "수집됐는데 알맹이가 없음"은 분석가가 취할 조치가 다르기 때문입니다.
   `$UsnJrnl` 파서에도 같은 취지의 빈 스트림 가드를 뒀습니다.

회귀 테스트는 `tests/test_parse_scaffold.py`("0바이트 껍데기")와
`tests/test_usn_parser.py`에 있습니다.

### 4-0-1. `parse_errors`가 스캔 횟수를 셌다 (**해결됨**)

기록으로 남깁니다. 같은 실측에서 `parse_errors: 62,969`가 나왔습니다.
숫자만 보면 저널이 심하게 깨진 것 같지만 실제로는 이랬습니다.

- 정상 레코드 **306,857건 / 스키마 위반 0**
- USN 증가분과 오프셋 증가분이 정확히 일치 (33,901,024 = 33,901,024)
- 재동기화 62,969회는 **전부 한 덩어리** — `@0x2055000`부터 503,752바이트

그 구간은 저널이 아니라 **phpMyAdmin 언어 파일 텍스트**입니다(이 볼륨의
`APM_Setup` 잔재). `$J`는 스파스 파일이라 추출 도구가 유효 데이터 끝
너머 클러스터까지 담았고, 거기 남아 있던 삭제 파일 내용이 딸려온 것입니다.

파서 동작 자체는 정확했습니다 — 가짜 레코드를 만들지 않고 8바이트씩
재동기화하며 지나갔습니다. 틀린 것은 **집계 단위**였습니다.
`503,752 / 8 = 62,969`로 나머지 없이 딱 떨어지는 것이, 저 숫자가
"오류 건수"가 아니라 **"걸어간 횟수"**라는 증거입니다.

**조치** — 연속된 실패를 한 구간으로 묶고 규모를 바이트로 분리했습니다.

| | 고치기 전 | 고친 뒤 |
|---|---|---|
| `parse_errors` | 62,969 | **1** |
| `unreadable_bytes` | — | **503,752** |
| 로그 | `재동기화 62969회` | `@0x2055000 부터 503752바이트를 읽지 못했습니다` |

evtx 파서가 이미 쓰던 방식과 같습니다. 구간 수만으로는 8바이트가 깨진
것과 500KB가 통째로 저널이 아닌 것을 구별할 수 없으므로 **둘을 함께**
냅니다. 저널 중간에 진짜 손상이 여러 군데 생기면 구간 수가 실제로 여러
개로 나옵니다 — 그게 원래 알고 싶었던 값입니다.

회귀 테스트는 `tests/test_usn_parser.py`에 있습니다(구간 1곳이 1건으로,
떨어진 손상 둘은 2건으로, 규모는 `unreadable_bytes`로).

### 4-0-2. 시각 없는 신호가 05단계를 멈춰 세웠다 (**해결됨**)

기록으로 남깁니다. **타임스탬프가 조작된 증거에서 도구가 죽는** 문제였습니다.

`record_filter.select_records`가 시각을 못 읽은 신호 레코드에 tz-naive
`datetime.max`를 정렬 자리로 주고, 시각이 있는 신호(tz-aware)와 같은
리스트에서 정렬했습니다.

```
TypeError: can't compare offset-naive and offset-aware datetimes
```

**드문 경우가 아닙니다.** `$SI` 타임스탬프가 전부 0이면
`filetime_to_datetime`이 `None`을 주고 04단계가 `zero_timestamp`를
붙입니다 — 즉 **시각이 없다는 사실 자체가 그 레코드를 신호로 만듭니다.**
안티포렌식 흔적을 찾는 필터가 바로 그 흔적에서 멈추는 구조였습니다.
목업 데이터에는 타임스탬프가 전부 정상이라 드러나지 않았습니다.

**조치** — 정렬 자리를 `NO_TIME`(tz-aware `datetime.max`)로 상수화하고,
"앵커가 되지 못한다"는 판정을 `tzinfo` 검사가 아니라 그 상수와의 동일성
비교로 바꿨습니다. 시각 없는 신호는 **전달되되 주변 창은 열지 않습니다** —
"그 시각 주변"이라고 할 시각이 없기 때문입니다.

회귀 테스트는 `tests/test_interpret.py`에 있습니다(시각 없는 신호가
버려지지 않고 맨 뒤로 정렬되는지, 창을 열지 않는지).

### 4-3. 아티팩트가 19종이 되면서 아티팩트당 자리가 얇아졌다 (2026-08-25)

`DEFAULT_LIMIT`(60건)은 웹셸 케이스에서 정해진 값입니다. 그때는 선별되는
아티팩트가 대여섯이라 하나당 8~12건이 갔습니다.

K-001 은 **19종**이 선별됩니다. 같은 60건을 나누면 이렇게 됩니다(측정).

| priority | 아티팩트당 |
|---|---|
| 1 | **4건** |
| 2 | 2건 |
| 3 | 1건 |

**굶는 아티팩트는 없습니다** — 배분이 공평하게 작동하고, `priority` 도
의도대로 갈립니다. 문제는 절대량입니다. Tier 1 아티팩트 하나당 4건으로
7단계 침해 체인을 재구성해야 합니다.

**고치지 않았습니다.** 올릴지 말지는 모델의 컨텍스트 한계(qwen2.5-7b)와
맞물린 판단이고, 그 데이터가 없습니다. 후보는 셋입니다.

1. `--limit` 을 올린다 — 컨텍스트가 감당하는지 재 봐야 한다
2. 매핑의 `priority` 를 더 정교하게 매긴다 — 지금은 대부분 1 이라 변별력이 낮다
3. 아티팩트를 줄인다 — 시나리오가 요구하는 것이라 줄일 수 없다

실제 K-001 증거가 나오면 1번을 먼저 재 보는 것이 순서로 보입니다.

### 4-2. 신호 플래그가 필터 역할을 못 한다 (**배분으로 완화됨**)

**`$UsnJrnl`만의 문제가 아닙니다.** 시스템 볼륨을 처음 돌려 보니
`$MFT`도 같은 상태였습니다.

| 아티팩트 | 볼륨 | 신호 비율 |
|---|---|---|
| `$UsnJrnl` `deleted` | 개발 장비 저널 | 355,850건 중 37% |
| `$MFT` `timestamp_mismatch` | `evidence/test` (데이터) | 154건 중 **0%** |
| `$MFT` `timestamp_mismatch` | `evidence/[root]` (시스템) | 2,034건 중 **81%** |

`$MFT` 쪽 원인은 **OS 설치**입니다. Windows Setup이 `$SI`를 설치 미디어의
빌드 시각으로 보존하고 `$FN`은 설치 시각으로 쓰기 때문에
`si_btime < fn_btime`이 OS 파일 전체에서 정상적으로 성립합니다. 측정과
근거는 `artifact-notes.md`("시스템 볼륨에서는 좁힌 룰도 81%가 걸린다").

**즉 데이터 볼륨에서 0%였던 룰이 시스템 볼륨에서 81%입니다.** 실제 사고
조사 대상은 시스템 볼륨입니다.

측정치는 `artifact-notes.md`("USN 신호 플래그는 $MFT보다 훨씬 많이
걸린다")도 참조.

`evidence/$J` 355,850건 중 `deleted` 37%, `file_created` 23%.
확장자와 20분 시간창으로 좁혀도 2,042건 중 **1,281건(63%)이 신호**로
남습니다. `record_filter.DEFAULT_LIMIT`은 60입니다.

**룰이 틀린 것이 아닙니다.** 플래그는 정확합니다. 이름은 같지만
카디널리티가 다릅니다.

- `$MFT`의 `deleted` = **상태**("지금 미할당"). 볼륨 크기에 묶임
- `$UsnJrnl`의 `deleted` = **사건**("지워졌다"). 시간에 비례해 무한정 쌓임

**영향이 조용해서 위험합니다.** 신호 1,281건 중 60건만 05단계로
넘어가고 나머지는 모델이 아예 보지 못합니다. 그런데 **06단계가 이것을
잡지 못합니다** — 환각이 아니기 때문입니다. 모델이 없는 것을 지어낸
것이 아니라, 있는 것을 못 받은 것입니다. 결과는 "sLLM이 탐지에
실패했다"로 집계되는데 실제 원인은 필터가 증거를 안 넘긴 것입니다.

> **벤치마크 수치를 내기 전에 반드시 정해야 합니다.** 정하지 않고 돌리면
> 나온 환각률·재현율이 모델 성능이 아니라 필터 설정을 재게 됩니다.

검토 중인 방향 셋:

1. 04단계에서 `file_entry` → `$MFT` 상호 참조로 경로 복원 —
   가장 효과적이나 아티팩트 간 의존이 생김
2. 05단계 `record_filter`에서 상호 참조 — 04단계 순수성 유지
3. 이진 선택에서 순위 매기기로 — 고볼륨 아티팩트 일반의 문제로 다룸
   (**채택·구현됨**, 6장)

임계값만 조정하는 것은 답이 아닙니다. `$MFT`의 `MISMATCH_PAIRS`처럼
**물리적 근거가 있는 판별자**를 찾은 뒤에 좁혀야 합니다.

3번을 4-2-1과 함께 설계·구현한 결과가 **6장**입니다. 아티팩트별 쿼터가
생겼으므로 시끄러운 아티팩트가 조용한 아티팩트를 굶기는 일은 없어졌습니다.
**남은 것은 쿼터 안의 문제입니다** — `$UsnJrnl` 신호 1,281건 중 배분받은
자리만큼을 무엇으로 채울지는 여전히 시간창 근접성에 기댑니다(6-6).

### 4-2-1. 넘길 60건을 고르는 것이 파일명 순서였다 (**해결됨**)

4-2가 "1,281건 중 60건"이라고 쓴 그 60건이 **어떻게 뽑히는지**는 따로
봐야 했습니다. 예전 `select_records`는 신호를 정렬하지 않고 `[:limit]`으로
잘랐습니다. 그 순서는 `io.read_parsed_records`가 읽은 순서, 즉
`sorted(glob("*.jsonl"))`입니다.

```
evtx_security → evtx_system → mft → usnjrnl
```

**알파벳순입니다.** 앞의 파일이 60자리를 채우면 뒤의 아티팩트는 신호가
몇 건이든 모델에 한 건도 도달하지 않습니다. 4-2의 실측 규모(신호
1,281건)에서는 `$UsnJrnl`이 통째로 잘립니다 — 저널이 가장 많은 신호를
내는 아티팩트인데도 그렇습니다.

4-2와 원인이 다릅니다. 4-2는 **몇 건을 넘길지**의 문제이고 이것은
**어느 것을 넘길지**의 문제입니다. 상한을 올려도 순서 편향은 남습니다.

**영향** — 4-2와 같았습니다. 06단계가 못 잡고 "sLLM 탐지 실패"로
집계됩니다. 다만 이쪽은 **아티팩트 단위로 통째로** 빠지므로, 아티팩트별
재현율을 내면 값이 파일명 알파벳순과 상관됐습니다.

**해결** — 6장의 배분이 아티팩트마다 자리를 먼저 나누므로 앞 파일이 뒤
아티팩트를 통째로 굶기는 경로가 없어졌습니다. 파일을 읽는 순서는 그대로지만
배분 결과가 그 순서에 의존하지 않습니다(`test_allocation.py`의
`test_the_allocation_does_not_depend_on_insertion_order`).

### 실제 모델로 처음 돌렸다 (2026-08-24, `qwen2.5:7b`)

그전까지 케이스 산출물은 전부 `StubBackend` 리플레이였습니다. 키오스크

#### 고친 것

**① `findings.schema.json`의 `ref` 패턴에 `PF`가 없었다.**
`refs.py`와 `parsed_record.schema.json`에는 있는데 여기만 빠져 있었습니다
(프리패치 파서를 붙이며 한 군데를 놓친 것). `input_refs`는 **모델이 아니라
우리 코드가** 배분 결과에서 만드는 값이라, 프리패치가 05단계에 닿는 케이스는
모델이 무엇을 내든 **원리적으로 통과할 수 없었습니다.** 더 나쁜 것은 그
실패가 `schema_violation`으로 기록돼 **모델의 환각으로 집계된다**는
점입니다. 동결 대상 스키마를 고쳤으므로 전체 공지 대상입니다.
`tests/test_schemas.py`가 이제 `refs.py`의 접두어와 스키마 패턴을 양방향으로
대조합니다 — 이 결함이 테스트를 통과했던 이유가 두 스키마의 `ref`가 서로
다른 자리(`$defs` vs `properties`)에 적혀 있어서였습니다.

**② 05단계 배분이 실물 규모에서 멈췄다.** 앵커마다 거리를 재는 구현이라
연산량이 `비신호 레코드 × 앵커 시각`이었습니다. 이 이미지에서
`12,470 × 8 × 337,264 ≈ 3.4 × 10¹⁰`회, 약 **56분**입니다. 목업은 레코드가
수십 건이라 드러날 수 없었습니다. 정렬 + 이분 탐색(`AnchorIndex`)으로
바꿨고, **무차별 대입과 비트 단위로 같은 값**임을 표본 1,200건으로
확인했습니다. 처음 `timestamp()` float로 짰을 때는 1,200건 중 750건이
갈렸습니다 — 2020년대 epoch 초에서 마이크로초 자리가 float 유효숫자
한계에 걸립니다. 정수 마이크로초로 재고 마지막에 한 번만 나눕니다.

**③ 타임아웃을 올릴 방법이 없었다.** 120초 고정이라 05단계가 네 번 연속
`timeout`으로 죽었습니다. 02·05에 `--timeout`을 노출했습니다
(`src/common/llm.py`의 `DEFAULT_TIMEOUT`). 이 장비에서 05단계 한 번 호출이
120초를 넘습니다.

#### 남은 것

**④ `entities`에 없는 값이 들어오는데 스키마가 못 잡는다.** 프롬프트가
"입력에 명시된 것만 넣으십시오. 추측하지 마십시오"라고 적어 두었는데도
두 번 다 지어냈습니다 — `C:\Windows\System32`(K-001),
`C:\Program Files\BankingApp\`(K-002). 둘 다 입력 서술에 없는 경로입니다.
**`entities.paths`의 첫 항목은 03단계가 기준 경로로 씁니다.** 지어낸 경로가
선별 범위를 정하는 자리까지 갑니다. 06단계는 `findings`의 `claims`만
검증하므로 이 층은 아무도 안 봅니다.

**⑤ 재시도가 `temperature 0`에서 무의미하다.** 오류를 프롬프트에 되먹이는
구조는 있는데, 결정론적이라 모델이 같은 답을 반복합니다. K-001에서
`T1200.001`(존재하지 않는 하위기법)을 **다섯 번 연속** 냈습니다.

`num_ctx`를 지정하지 않아 모델이 4,096 토큰 창으로 떴습니다(`/api/ps`의
`context_length`로 확인). `qwen2.5:7b` 자체는 32,768을 지원합니다.
05단계는 레코드 60건을 실어 보내므로 **프롬프트가 조용히 잘렸습니다** —
모델이 못 본 레코드에 대해 "흔적 없음"을 말해도 06단계는 검증할 수단이
없습니다. `DEFAULT_NUM_CTX = 32768`로 명시하고 `--num-ctx`로 노출했습니다.

**이것이 findings 0건의 원인이 맞았습니다.** 같은 입력으로 다시 돌리자

### 06단계가 표기 오류를 환각으로 셌다 (**해결됨**, 2026-08-24 실측)

`K-003`의 유일한 findings가 기각돼 **환각률 100%**로 집계됐습니다.
그런데 내용을 보면 모델이 맞았습니다.

```
모델 주장 : REG-SW#9604700 / DisableRealtimeMonitoring / "1"
실제 레코드: SOFTWARE\Microsoft\Windows Defender\Real-Time Protection
            fields = {"DisableRealtimeMonitoring": 1, ...}
기각 사유 : field_not_found
```

**ref도 필드명도 값도 맞습니다.** 틀린 것은 `fields.` 접두어 하나입니다 —
`get_field`가 점 표기를 요구하는데 모델이 맨 이름을 썼습니다. 프롬프트가
점 표기를 명시했으니 모델의 잘못이 맞지만, **이것을 환각으로 세면
환각률이 표기 오류를 세게 됩니다.**

`CurrentControlSet` 표기 문제(2장)와 같은 부류입니다 — 문장은 맞는데
표기가 달라 `comparators`가 흡수하지 못합니다.

**`benchmark/validator_check.py`는 이것을 못 잡습니다.** 33건 전부 통과로
나옵니다. 사례에 점 표기를 쓰는 것이 4건 있으나, **맨 이름이 `fields` 아래
있는 경우**는 하나도 없습니다. 과엄격 감시에 이 부류가 비어 있습니다.

#### 조치 — `comparators`의 네 번째 관대함으로 흡수한다

`comparators.py`는 이미 셋을 관대하게 보고 있었습니다. 타임스탬프 절삭,
경로 대소문자, 타입(`4821` 대 `"4821"`). 전부 **"주장하는 사실은 같은데
표기가 다른"** 경우이고, `fields.` 접두어는 그 네 번째입니다. 그래서
새 예외 처리를 만들지 않고 `get_field`가 흡수합니다. **양방향입니다** —
맨 이름을 `fields` 아래에서 찾고, 반대로 `fields.path`를 최상위에서도
찾습니다(`$MFT`는 `path`가 최상위입니다).

**검증이 무르지 않는 이유**가 핵심입니다.

- 이 함수가 하는 일은 **모델이 가리킨 필드를 찾아 주는 것까지**입니다.
  찾은 뒤에 값을 그대로 대조하므로, 값이 틀리면 `value_mismatch`로
  기각됩니다. 없는 필드를 지어낸 경우는 대안 표기로도 못 찾으므로
  `field_not_found` 그대로입니다.
- **모호해질 수 없습니다.** 원래 표기를 먼저 시도하고 성공하면 대안을
  보지 않으므로, 최상위와 `fields`에 같은 이름이 있어도 최상위가 이깁니다.
- 기각될 때 **끊긴 지점은 모델이 쓴 표기 기준**으로 남깁니다. 대안 표기의
  끊긴 지점을 보고하면 사유가 모델이 쓰지도 않은 경로를 가리킵니다.

`tests/test_verify_checkers.py`가 이 성질들을 각각 고정합니다 — 특히
"지어낸 필드는 두 표기 모두에서 여전히 못 찾는다"와 "표기를 흡수해도
값이 틀리면 `value_mismatch`".

**과엄격 감시의 구멍도 메웠습니다.** `benchmark/validator_cases.json`에
V34(맨 이름)·V35(반대 방향)를 더해 33건 → 35건입니다. 이 부류가 통째로
비어 있어서 감시가 100% 통과를 보고하고 있었습니다.

**결과** — `K-003`을 다시 검증하니 환각률 **100% → 0%**, 보고서에 첫
"확인된 사항"이 실렸습니다(Defender 실시간 보호 비활성화, 06:48:31,
`REG-SW#9604700`).

#### 같은 부류인데 아직 남은 것

**`CurrentControlSet` 표기**(2장)는 그대로입니다. 04단계가 `ControlSet001`로
풀어 쓰고 모델은 `CurrentControlSet`이라고 인용하므로 기각됩니다. 이번
것과 달리 **필드를 찾는 문제가 아니라 값 문자열이 다른 문제**라
`get_field`가 아니라 `compare`/`normalize_path` 쪽에서 풀어야 합니다.
레지스트리 경로에만 적용되는 치환이라 경로 비교 규칙 전체를 건드리게
되고, 그만큼 오탐 위험이 커서 따로 둡니다.

**영향** — "소형 모델의 환각을 검증 계층으로 잡는다"는 논지는 이제
**한 건이지만 실물 수치가 있습니다**(통과 1 / 기각 0). 다만 표본이
findings 1건이라 비율로 말할 수 없고, `priority`가 비어 있는 동안의
배분으로 얻은 결과라는 점도 그대로입니다(6-5).

### 검증기가 경로 표기 차이를 환각으로 센다 (**부분 해결**, 2026-08-26 실측)

**같은 일이 다른 표기 부류로 또 일어났습니다.** 위 절이 `fields.` 접두어를
메꾸고 감시 사례를 35건으로 늘린 지 이틀 만입니다.

`K-ALERT`(실물 이미지 + 알럿 입력, 기법 8개)에서 06단계가 소견 4건을
**전부 기각해 환각률 100%**를 냈습니다. 열어 보니 셋이 오탐입니다.

| | 모델 주장 | 실제 레코드 | 판정 |
|---|---|---|---|
| F4 | `C:\WINDOWS\SYSTEM32\sppsvc.exe` | `c:\windows\system32\sppsvc.exe` | 대소문자만 다름 — **오탐** |
| F2 | `C:\WINDOWS\SYSTEM32\SVCHOST.EXE` | `\VOLUME{01d8e7bd02796420-a202ae01}\WINDOWS\...` | 볼륨 GUID 표기 — **오탐** |
| F3 | `C:\WINDOWS\SYSTEM32\WERMGR.EXE` | 같음 | **오탐** |
| F1 | `SubjectUserName` = `MINWINPC$` | `-` (레코드에 그 문자열 없음) | **진짜 환각** |

**실제 환각률은 100%가 아니라 25%입니다.**

#### 원인 — 경로 비교 규칙이 필드 **이름**으로 켜진다

```python
# comparators.py:48
PATH_FIELDS = frozenset({"path", "target_path", "source_path", "image_path"})
```

`is_path_field()`가 이 넷(과 `*_path`)일 때만 `normalize_path`를 태웁니다.
그 밖의 이름은 `_scalar_equal`의 정확 문자열 비교로 갑니다. 실측:

```
compare("15",   'C:\WINDOWS\...\sppsvc.exe', 'c:\windows\...\sppsvc.exe')  →  False
compare("path", 같은 값)                                                    →  True
```

F4의 필드명이 `"15"`인 것은 Amcache 값 이름이 숫자 문자열이기 때문입니다.

**K-001 랩에서 이것이 훨씬 크게 터집니다.** Sysmon 이 실린 순간
Stage 2·3 이 통째로 기대는 필드들이 전부 경로로 인식되지 않습니다.

```
is_path_field('Image')          = False   ← Sysmon EID 1
is_path_field('ParentImage')    = False   ← Stage 3 의 결정적 근거
is_path_field('TargetFilename') = False   ← Sysmon EID 11
```

F2·F3 은 별개 원인입니다 — 프리패치의 `_to_drive()` 가
`\DEVICE\HARDDISKVOLUME*` 만 드라이브 문자로 바꾸고, 실물에서 나온
`\VOLUME{serial-serial}` 형태는 그대로 둡니다("바꿀 수 없으면 그대로
둔다"는 주석대로의 동작). **04단계에서 풀 문제이지 06단계가 흡수할
것이 아닙니다.**

#### 과엄격 감시가 또 못 잡았다

같은 시점에 `benchmark/validator_check.py` 는 **35건 중 35건 통과,
"오탐 없음"**을 보고했습니다. 볼륨 GUID 표기도 숫자 필드명도 사례에
없는 부류입니다.

**위 절이 예고한 그대로입니다** — 감시는 사례에 있는 부류만 봅니다.
새 표기 부류가 생기면 100% 통과를 보고하면서 정상 문장을 기각합니다.
**`PATH_FIELDS` 를 손대기 전에 사례부터 추가해야 합니다.**

#### 영향

**이 상태에서 나온 환각률 수치는 쓸 수 없습니다.** 발표 수치가 모델의
환각이 아니라 우리 비교기의 이름 화이트리스트를 재고 있습니다. 위 절이
"실물 수치가 있습니다(통과 1 / 기각 0)"라고 적은 것도 findings 1건짜리
표본이라 이 오탐 부류를 만날 기회가 없었을 뿐입니다.

#### 조치 — 이름 목록을 넓혔다. 셋 중 하나만 풀렸다

**순서를 지켰습니다** — `benchmark/validator_cases.json` 에 사례 V36~V39 를
먼저 넣어 넷 다 기각되는 것을 확인하고, 그다음 `PATH_FIELDS` 를 고쳤습니다.
사례 없이 비교기만 고치면 감시가 계속 "오탐 없음"을 보고합니다.

사례용 레코드는 `benchmark/validator_records/` 에 따로 뒀습니다. C-001
목업은 웹셸 벤치마크의 입력이라, 표기 시험용 레코드를 섞으면 파싱 건수와
05단계 배분이 함께 흔들립니다.

| | 상태 |
|---|---|
| Sysmon `Image`·`ParentImage`·`TargetFilename`·`ImageLoaded` | **해결** — `PATH_FIELDS` 에 추가 |
| Security `ProcessName`·`NewProcessName`·`ParentProcessName` | **해결** — 같음 |
| `filename` 으로 끝나는 새 이름 | **해결** — `PATH_FIELD_SUFFIXES` 가 받음 |
| Amcache 숫자 값 이름 (`"15"`) | **미해결** — 아래 |
| 프리패치 볼륨 GUID 경로 | **미해결** — 06단계 문제가 아니라 04단계 `_to_drive()` 몫 |

**`CommandLine` 은 일부러 넣지 않았습니다.** 앞머리는 경로지만 뒤는
인자입니다. 경로 규칙으로 대소문자를 지우면 인자의 실제 차이까지 같이
지워져 검증이 물러집니다.

#### 남은 것 — Amcache 숫자 값 이름은 04단계 몫이다

`"15"` 는 전체 경로지만 **이름이 아무 뜻도 담고 있지 않습니다.**
`PATH_FIELDS` 에 `"15"` 를 넣으면 다른 서브키의 `15` 까지 경로로 봅니다.
값의 생김새로 판단하는 것은 이 모듈이 처음부터 거부한 방식입니다.

**04단계가 Amcache 값 이름을 해석해 내보내면 풀립니다.** `V36` 에
`expect: "rejected"` 와 `gap` 을 달아 두었고, 고쳐지면
`test_known_gaps_carry_a_reason_and_are_still_broken` 이 **"이제 통과하니
expect 를 되돌리라"**고 알립니다 — 목록이 낡은 채 남아 진짜 회귀를 덮는
것을 막습니다.

#### 이 조치로 K-ALERT 수치는 움직이지 않았습니다

**중요합니다.** 다시 검증해도 환각률은 100% 그대로입니다.

```
F1  value_mismatch  SubjectUserName   ← 진짜 환각 (올바른 기각)
F2  value_mismatch  path              ← 프리패치 볼륨 GUID (04단계 몫)
F3  value_mismatch  path              ← 같음
F4  value_mismatch  "15"              ← Amcache (아는 구멍)
```

그 이미지에 Sysmon 이 없어 이번에 고친 필드들이 등장하지 않기 때문입니다.
**이번 조치는 K-001 랩에서 터질 것을 미리 막은 것이지, 이 케이스의 수치를
고친 것이 아닙니다.** 수치가 정상으로 돌아오려면 위 표의 미해결 둘이
남아 있습니다.

### 05단계 프롬프트가 컨텍스트 창을 넘는다 (**미해결**, 2026-08-26 실측)

`K-ALERT`(기법 8개 → 아티팩트 10종 1,693건)에서 05단계가 **3회 재시도
끝에 중단**됐습니다. 약 25분 소모, 소견 0건.

```
attempt 1  malformed_output   응답에서 JSON 객체를 찾지 못함
attempt 2  timeout            qwen2.5:7b: 900.0초 내 응답 없음
attempt 3  malformed_output   응답에서 JSON 객체를 찾지 못함
           abort              → SystemExit(1)
```

프롬프트를 그대로 재현해 재 봤습니다.

| | |
|---|---|
| 전달 레코드 60건의 JSON | 71,476자 (**추정 28,600 토큰** — 글자수÷2.5, 토크나이저를 돌린 값이 아님) |
| 시스템 프롬프트 | 3,002자 |
| `--num-ctx` 기본값 | 32,768 |
| `qwen2.5:7b` 의 `context_length` | 32,768 (**모델 상한이라 더 열 수 없음**) |

출력에 쓸 자리가 2천 토큰도 남지 않습니다.

**`--limit 15` 로 낮추니 첫 시도에 통과했습니다**(소견 4건, 재시도 0회,
`errors.jsonl` 0건). 원인이 프롬프트 크기임이 확인됐고, attempt 2의
타임아웃도 같은 원인입니다 — 3만 토큰 프롬프트의 처리 시간입니다.

**5장이 "넘는지는 아무도 검사하지 않습니다"라고 적어 둔 자리이고,
이번이 실제로 넘긴 첫 실측입니다.** 웹셸 목업은 레코드가 5건이라 닿을
수 없던 지점입니다.

#### 왜 60건이 이렇게 커졌나

4-3이 적은 것과 같은 구조입니다 — 아티팩트가 늘면 자리를 나눠 갖지만
**총량 60건은 그대로**라, 레코드 하나당 평균 1,190자가 그대로 실립니다.

```
evtx:Security  후보 482 → 9자리     registry:Amcache  후보 392 → 8자리
evtx:KernelPnP 후보 385 → 9자리     registry:SYSTEM   후보 258 → 8자리
prefetch       후보 137 → 9자리     evtx:RDPSession   후보  12 → 9자리
```

`--limit` 기본값 60은 카탈로그가 11종이던 시절 값입니다.

#### 조치하지 않은 것

**실패한 모델 원문을 남기지 않습니다.** 그래서 위 진단이 "프롬프트가
잘렸다"까지 확인한 것이 아니라 **크기를 재고 `--limit` 를 낮춰 재현한
것**입니다. 프롬프트가 실제로 어디서 잘렸는지, 모델이 무엇을 뱉었는지는
보지 못했습니다. `malformed_output` 일 때 응답 원문을 남기면 다음부터는
추측 없이 판단합니다.

### 외부 도구 대조가 부분적이다

| 아티팩트 | 대조 상대 | 상태 |
|---|---|---|
| `$MFT` | MFTECmd | **미실시** — 추출 파일 크기 대조로 대신함 |
| `$UsnJrnl` | MFTECmd (`-f $J`) | **미실시** — 독립 순회 코드로 대신함 |
| `evtx` | `wevtutil` | **실시** — 8,257건 전량 일치 |
| `registry` (커버리지) | 원시 셀 스캔 | **실시** — SYSTEM 34,855 / SOFTWARE 156,716건 일치 |
| `registry` (값) | 독립 `nk`/`vk` 디코더 | **실시** — 46,147키 중 46,142건 일치 (나머지는 대조 도구의 big data 미구현) |
| `registry` (값) | `reg load` | **미실시** |

레지스트리는 대조를 둘로 나눴습니다. 위험의 성격이 `$MFT`와 다르기
때문입니다 — 값을 틀리게 읽는 것이 아니라 **서브트리를 통째로 못 보고
지나가는 것**이 위험합니다. python-registry는 서브키 목록(`lf`/`lh`/`li`/
`ri`)을 따라 내려가는데, 그 목록 하나가 손상되면 아래 전부가 예외도
경고도 없이 사라집니다.

`tools/scan_hive_cells.py`가 **서브키 목록을 전혀 따라가지 않고** hbin의
셀을 직접 걸어 `nk`를 셉니다. 트리 구조와 무관하므로 커버리지 정답지가
됩니다. 두 하이브 모두 정확히 일치했습니다.

**값 대조는 독립 디코더로 한 번 했습니다.** `nk`/`vk`를 명세대로 직접
읽어 파서 출력과 맞춰 본 것이며, **이 대조에서만 드러난 버그가 셋**
있었습니다(위 「라이브러리를 우회한 곳」). 다만 같은 사람이 명세를 읽고
짠 두 구현이라 공통 오해는 잡지 못합니다.

**그래서 `reg load` 대조는 여전히 필요합니다** — 모든 Windows에
들어 있고 마이크로소프트 자신의 구현이라 `wevtutil`과 같은 조건입니다.
관리자 권한이 필요하고 원본이 아닌 복사본에 걸어야 합니다(마운트가
하이브를 더티로 만들 수 있음). 절차는 `tools/scan_hive_cells.py`
docstring에 있습니다.

`regipy`나 `python-registry`로 대조하면 의미가 줄어듭니다. 아래
`evtx_dump.py` 함정과 같습니다.

독립 순회 정답지는 같은 사람이 짠 두 구현이라 **공통 오해는 잡지
못합니다.** 순회 로직 버그는 잡히지만 명세 이해가 틀렸다면 둘 다 같이
틀립니다. `$MFT`·`$UsnJrnl`은 외부 도구 대조가 남아 있습니다.

evtx만 실시된 이유는 준비물 때문입니다. `wevtutil`은 모든 Windows에 들어
있어 받을 것이 없고, 마이크로소프트 자신의 구현이라 공통 오해가 생기지
않습니다. `$MFT`·`$UsnJrnl`은 MFTECmd를 따로 받아야 합니다. 기록은
`artifact-notes.md`에 있습니다.

**`evtx_dump.py`(python-evtx 동봉)로 대조하면 의미가 없습니다.** 우리가 쓰는
바로 그 라이브러리라 자기 대조입니다. 위의 "공통 오해" 함정과 같습니다.

## 6. 05단계 레코드 배분 (**구현됨**)

4-2("몇 건을 넘길지")와 4-2-1("어느 것을 넘길지")을 함께 푸는 설계입니다.
구현은 `src/stage05_interpret/allocation.py`이고, 아래는 설계 논의와 그
근거를 그대로 둔 것입니다. **채우지 않은 것이 하나 남아 있습니다** —
6-5의 `priority` 값입니다.

### 6-1. 왜 정해야 했는가

예전에는 `record_filter`가 신호를 이진 판정한 뒤 앞에서 60개를 잘랐습니다.
자르는 기준이 파일명 알파벳순이라 **어느 증거가 모델에 도달하는지가
파일 이름 철자에 달려 있었습니다.**

파이프라인 전체에서 **05단계의 자르기만 시나리오의 영향을 받지 않았습니다.**
03단계가 "이 기법 때문에 이 아티팩트를 본다"고 정해 놓은 것을 05단계가
통째로 무시했습니다. 이 도구의 논지가 "시나리오 기반 선별"인데 마지막
관문이 시나리오와 무관했습니다.

### 6-2. 채택한 구조 — 2단 배분

```
매핑 priority   →  이 케이스에서 어느 아티팩트가 중요한가   [가중치]
신호 수 정규화  →  어느 아티팩트가 시끄러운가              [보정]
                          ↓
                아티팩트별 자릿수 배분 (쿼터)
                          ↓
                쿼터 안에서 레코드 선택 (시간창 중심성)
```

가중치만 있으면 시끄러운 아티팩트가 자리를 쓸어가고, 보정만 있으면 모든
아티팩트를 똑같이 취급합니다. 둘 다 있어야 "웹셸 케이스에서 `$MFT`를
우선하되, `$UsnJrnl`이 30만 건이라고 `$MFT`를 밀어내지는 못한다"가 됩니다.

**가중치는 (기법, 아티팩트) 쌍의 속성입니다.** 기법의 속성이 아닙니다.
같은 `$MFT`라도 `T1070.006`(Timestomp)에서는 판정의 근거 그 자체이고
`T1053.005`(Scheduled Task)에서는 이벤트 로그를 보조하는 자리입니다.

매핑 YAML이 이미 그 모양이라 스키마도 코드도 바꿀 것이 없습니다.

```yaml
artifacts:
  - name: $MFT
    tier: 1
    priority: 1        # ← 이 한 줄
    scope_template: {}
    rationale: $SI와 $FN 타임스탬프 불일치
```

`work-guide.md` 5.1의 "`mappings/`는 코드가 아닌 데이터" 원칙에 맞습니다 —
여러 명이 동시에 채우고, 개수를 세고, 파이썬을 몰라도 씁니다.

**보정값은 아티팩트별 후보 수입니다.** 배분이 어차피 전 레코드를 훑으며
`is_signal()`을 부르므로 새 입력 없이 셀 수 있습니다.

구현에서 정한 것 둘을 함께 적습니다.

- **눈금은 셋입니다**(1·2·3, 작을수록 강함 — `tier`와 같은 방향). 가중치는
  4·2·1로 한 눈금마다 두 배입니다. 배수를 더 키우지 않은 것은 약한
  아티팩트가 굶으면 안 되기 때문입니다 — 자리를 적게 받는 것과 한 건도 못
  받는 것은 보고서에서 전혀 다른 결과입니다.
- **후보가 있는 아티팩트는 최소 한 자리를 받습니다.** 03단계가 보라고 한
  아티팩트가 보고서에서 통째로 사라지지 않는다는 보장이며, 6-7이 여기서
  풀립니다.

남은 자리는 동트(D'Hondt)식으로 하나씩 나눕니다. 매번 `가중치 / (이미 받은
자리 + 1)`이 가장 큰 아티팩트가 다음 자리를 가져갑니다. 최대잔여법과 달리
소수점 잔여를 들고 다니지 않아 **자리마다 누가 왜 가져갔는지 손으로 따라갈
수 있습니다.** 동점은 이름순으로 가릅니다 — 근거가 있어서가 아니라 같은
입력에 같은 배분이 나와야 재현율이 모델 성능의 지표가 되기 때문입니다.

### 6-3. 배선

05단계에 `--selection`이 생겼습니다. `priority`는 03단계가 매핑에서 읽어
`selected[].priority`로 산출물에 실어 보내고, 05단계는 그것만 읽습니다.
05단계가 `mappings/`를 다시 읽지 않는 이유는 **그 사이 매핑이 바뀌면
보고서와 대조가 되지 않기 때문입니다** — "왜 이 60건입니까"에 답할 근거가
케이스 산출물 안에 남아 있어야 합니다.

`signal_source`는 반대로 카탈로그에서 읽습니다(`--mappings`, 기본
`mappings`). 케이스마다 달라지는 판단이 아니라 아티팩트의 고정된
성질이기 때문입니다.

한 아티팩트를 여러 기법이 요청할 수 있습니다(04단계가 `scope`를 합치는
이유와 같음). 아티팩트 가중치는 **요청한 기법들 중 최대값**으로 봅니다 —
합치면 여러 기법이 스치듯 요청한 아티팩트가 한 기법이 강하게 요청한
아티팩트를 이깁니다.

### 6-4. 검토했으나 채택하지 않은 것

기록으로 남깁니다. 셋 다 그럴듯해 보이는데 근거가 없습니다.

**① ATT&CK 기법 번호순** — 번호는 **카탈로그 등재 순서**입니다. 심각도도
킬체인 순서도 아니며, 하위 번호(`.001`)도 부모 기법 안에서의 등재
순번입니다. 매핑 6건을 ID순으로 세우면 이렇게 됩니다.

```
T1053.005  Scheduled Task
T1070.004  File Deletion
T1070.006  Timestomp
T1136.001  Create Account
T1505.003  Web Shell          ← 5번째
T1543.003  Windows Service
```

대표 데이터셋이 `C-001-webshell`인데 **웹셸이 5번째**입니다. `1505 > 1053`
이라는 이유뿐입니다. 킬체인으로 봐도 거꾸로입니다 — Web Shell(초기 침투)이
File Deletion(사후 방어 회피)보다 뒤에 옵니다.

알파벳순을 번호순으로 바꾸는 것이라 근거 없기는 같은데, **겉보기에
원칙이 있어 보여서 더 위험합니다.** "왜 이 60건입니까"에 "ATT&CK
번호순입니다"라고 답하면 되묻는 사람이 없습니다.

**② 파일 크기 반비례 배분** — 볼륨 편차를 보정한다는 방향은 맞지만,
파일 크기는 증거의 양이 아니라 **그릇의 크기**를 잽니다. `evidence/[root]`
실측:

| 아티팩트 | 파일 크기 | 실제 레코드 | 바이트/레코드 |
|---|---|---|---|
| `$MFT` | **103.5 MB** | 101,120 슬롯 (대부분 미사용) | 1,024 |
| `$J` | 34.4 MB | **306,857** | 112 |
| `Application.evtx` | 1.1 MB | 8,257 | 135 |
| `HardwareEvents.evtx` | 68 KB | **0** | — |

**크기 순서가 레코드 수 순서와 정반대입니다.**

- `$MFT`가 가장 큰데(103MB) 가장 적게 받습니다. 그런데 범위를 좁히면
  실제로 154건(C-100-C)~2,034건뿐입니다. 넘칠 걱정이 제일 적은 것이
  제일 깎입니다.
- `$J`는 `$MFT`의 3분의 1 크기인데 레코드는 3배입니다. 4-2가 지적한
  "무한정 쌓이는" 바로 그 아티팩트가 오히려 후하게 받습니다.
- `HardwareEvents.evtx`는 68KB에 레코드 0건입니다. 작다는 이유로
  빈 로그에 자리가 배분됩니다.

셋의 그릇 성격이 달라서입니다 — `$MFT`는 안 쓰는 슬롯도 1,024바이트를
차지하는 고정 테이블, evtx는 채널마다 상한이 있는 링 버퍼, `$J`는
스파스 파일입니다. 특히 `$J`는 34MB 중 503,752바이트가 저널이 아니라
phpMyAdmin 텍스트입니다(4-0-1). 즉 파일 크기는 **추출 도구의 동작**을
재고 있습니다.

**③ `scenario.techniques[].confidence`** — 이미 스키마에 있는 0.0–1.0
값이라 쓰고 싶어지지만, 쓰면 순환이 생깁니다. **LLM이 매긴 확신도가 그
LLM이 볼 증거의 양을 정하게** 됩니다. 02단계가 맞는 기법을 낮은
확신도로 뽑으면 05단계가 바로 그 기법의 증거를 굶기고, 결과는 "sLLM
탐지 실패"로 집계됩니다 — 4-2가 경고한 조용한 실패를 우리가 직접
만드는 것입니다.

`work-guide.md` 2.2 원칙 1("LLM 구간과 결정론적 구간을 번갈아 배치")에도
어긋납니다. 03·05의 결정론적 구간에 LLM 판단을 되돌려 넣는 셈입니다.

### 6-5. 남는 수작업 (**미완 — 팀이 나중에 채우기로 함, 2026-08-24**)

**배분 기계는 돌아가지만 아직 아무 매핑도 `priority`를 적지 않았습니다.**
전부 중립(2)이라 지금 배분을 가르는 것은 후보 수뿐입니다. 시나리오가
자릿수에 반영되려면 이 값이 채워져야 합니다.

> **누락이 아니라 미룬 것입니다.** 배분을 구현하면서 함께 정하지 않고
> 나중에 채우기로 했습니다. 그때까지 나오는 배분 수치는 **가중치가 빠진
> 상태의 값**이므로, 벤치마크에 쓰기 전에 이 절을 먼저 확인하십시오.

매핑 9건의 아티팩트 항목 약 22개에 `priority`를 사람이 채워야 합니다.
**이 값은 어떤 자동 규칙에서도 나오지 않습니다.** 기법 번호에서도, 파일
크기에서도, 모델 출력에서도 나오지 않습니다. 분석가가 판단해 적고 다른
사람이 검토해야 나옵니다 — 그래서 코드가 아니라 `mappings/`에 둡니다.

일부러 채우지 않고 두었습니다. 자동으로 채울 수 있었다면 애초에 코드에
두었을 것이고, 그럴듯한 값을 넣어 두면 **검토되지 않은 값이 검토된 값처럼
보입니다.** 매핑 도메인 지식은 파서처럼 자동 대조 도구가 없어 사람이 직접
아티팩트를 열어 확인해야 합니다(2장 "매핑 — 검증되지 않은 채 채운 항목"과
같은 이유).

논의 중 `T1070.006`(Timestomp)에 이벤트 로그를 우선하자는 안이 나왔는데,
실제 매핑에는 이벤트 로그가 아예 없습니다. 타임스톰핑은 이벤트 로그에
기록되지 않고 `$SI`/`$FN` 불일치로만 잡히기 때문입니다. **6개 기법 중
가장 `$MFT` 의존적인 기법입니다.** 값 하나하나가 이 정도의 도메인 판단을
요구한다는 예로 남깁니다.

### 6-6. 이것으로 풀리지 않는 것

기법 우선순위는 **아티팩트 단위**입니다. `$MFT` 신호 1,648건 중 어느
60건이냐는 여전히 쿼터 안의 문제로 남습니다. 지금 설계는 시간창
중심성으로 채우기로 했으나 근거가 약합니다 — `MISMATCH_PAIRS`처럼
**물리적 근거가 있는 판별자**를 찾기 전까지는 임시입니다(4-2 말미).

### 6-7. 레지스트리가 05단계에 도달하지 못했다 (**해결됨**)

파서를 붙이면서 드러난 것이라 6장에 함께 적습니다. **04단계까지는
정상인데 모델에 한 건도 가지 않았습니다.**

`registry:Amcache`도 같은 클래스(`RegistryParser`)를 쓰므로 이 절이
그대로 적용됩니다 — Amcache 레코드도 `flags`가 붙지 않습니다. 카탈로그에
세 하이브 모두 `signal_source: scope`를 적어 두었습니다.

실측(`evidence/[root]`, `SYSTEM\CurrentControlSet\Services`):

```
registry:SYSTEM: 1754건 (플래그 0건) → registry_system.jsonl
```

`flagged_count`가 **0**입니다. 오류가 아니라 구조입니다.

기존 파서 셋은 **"전부 훑고 재미있는 것에 플래그"** 모델입니다.
레지스트리는 반대로 **가치가 레코드가 아니라 경로에 있습니다.**
`$MFT` 레코드 12345는 맥락 없이도 의미가 있지만
`Services\XYZ\ImagePath`는 그 경로가 무엇을 뜻하는지 알아야 의미가
생깁니다. 그래서 신호가 `flagging.py`가 아니라 **선별에서** 나옵니다.

그런데 05단계는 `is_signal()`로 `flags`가 빈 레코드를 버렸습니다. 결과적으로 **선별이 정확히 골라 온 1,754건이 전부 탈락합니다.**

임계값 문제가 아니라 필터 모델이 이 아티팩트에 맞지 않는 것입니다.
`flagging.py`에 억지로 룰을 넣는 것은 답이 아닙니다 — "Services 하위면
신호"라고 쓰면 선별이 이미 한 일을 한 번 더 하는 것이고, 그러면 플래그가
"볼 만하다"는 뜻이기를 그만둡니다.

6-2의 2단 배분에서 함께 풀렸습니다. 쿼터가 아티팩트별로 자리를 배분하므로
**"신호냐"가 아니라 "몇 자리를 줄 것이냐"가 질문이 되고**, 플래그 없는
아티팩트도 자기 몫을 받습니다.

**고친 방법.** 카탈로그에 `signal_source`를 두었습니다. 기존 셋은
`flags`(기본값)이고 레지스트리 두 하이브가 `scope`입니다. `scope`
아티팩트에서는 모든 레코드가 후보이며, 시간창으로 다시 거르지 않습니다 —
`Services` 하위 키의 LastWrite는 대개 OS 설치 시각이라 사건 시간창에
걸리지 않기 때문입니다. 쿼터 안에서는 사건 앵커에 가까운 키부터 들어갑니다.

이 예외를 `flagging.py`의 룰로 넣지 않은 이유는 그대로입니다. "Services
하위면 신호"라고 쓰면 선별이 이미 한 일을 한 번 더 하는 것이고, 그러면
플래그가 "볼 만하다"는 뜻이기를 그만둡니다. 카탈로그에 두면 **그 아티팩트의
신호가 어디서 나오는가**라는 사실 하나만 적는 것으로 끝납니다.

**앵커는 아티팩트를 가리지 않습니다.** evtx의 로그온 시각이 레지스트리
키를 끌어올 수 있습니다. 증거가 여러 계층에 흩어지는 사건에서 이 교차가
상관분석의 실질입니다.

재현 시나리오(1,754건 전부 플래그 0, `$UsnJrnl` 신호 500건, 상한 60):

| 배분 | `registry:SYSTEM` | `$UsnJrnl` | `evtx:Security` |
|---|---|---|---|
| 예전(플래그로 거름) | **0~3** | 55 | 2 |
| `signal_source: scope`, 중립 | **29** | 29 | 2 |
| 매핑이 레지스트리를 `priority: 1`로 지목 | **47** | 11 | 2 |

세 번째 줄은 아직 **가정입니다.** 6-5대로 `priority`가 비어 있어 실제
매핑으로는 두 번째 줄이 나옵니다.

### 6-8. 프리패치도 같은 자리에 있었다 (**해결됨**)

파서를 붙이면서 같은 일이 반복됐습니다. 실측(`evidence/[root]`):

```
prefetch: 73건 (플래그 0건) → prefetch.jsonl
```

레지스트리와 원인이 같습니다 — **가치가 레코드가 아니라 그 안의 경로에
있습니다.** "CMD.EXE가 5회 실행됐다"는 그 자체로 신호가 아니고,
`C:\inetpub\wwwroot\shell.aspx`를 적재했다는 사실이 신호입니다. 그 판단은
선별(`path_prefix`)이 이미 했으므로 `flagging.py`가 더 할 일이 없습니다.

`program_executed` 같은 플래그를 새로 만드는 안을 검토했다가 **접었습니다.**
프리패치 레코드는 전부 "무언가 실행됐다"이므로 모든 레코드에 붙고, 그러면
플래그가 "볼 만하다"는 뜻이기를 그만둡니다. 레지스트리에 "Services 하위면
신호"를 넣지 않은 것과 같은 이유입니다.

`outside_time_range`는 붙습니다(실측: 1시간 범위로 좁히면 73건 중 47건).
다만 `record_filter.NON_SIGNAL_FLAGS`에 들어 있어 신호로 치지 않으므로,
**결론도 같았습니다 — 프리패치도 05단계에 도달하지 못했습니다.**

**해결도 레지스트리와 같습니다.** 카탈로그에 `signal_source: scope`를
적었습니다. 배분이 그것을 보고 프리패치에도 자리를 줍니다.

재현(프리패치 73건 전부 플래그 0, 최근 실행 시각은 몇 주에 걸쳐 흩어져
있고 사건 근처는 2건, 상한 60):

| | 후보 | 전달 |
|---|---|---|
| `flags`로 볼 때 | **2건** (다른 아티팩트 신호의 시간창에 걸린 것만) | 2건 |
| `signal_source: scope` | **73건** (선별이 골라 온 전부) | 59건 |

두 경우 다 사건 근처 2건은 들어갑니다. 달라지는 것은 **나머지 71건을
후보로 볼 것이냐**입니다 — 프리패치에서는 그 71건이 "사건 시각에 실행되지
않았다"가 아니라 "그 프로그램이 이 시스템에서 실행된 적이 있다"이므로,
경로를 보고 판단할 거리가 남아 있습니다.
