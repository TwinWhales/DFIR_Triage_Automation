# 알려진 한계 (Limitations)

**이 도구가 지금 못 하는 것과, 그것이 결과에 어떤 영향을 미치는지**를 기록하는 문서입니다.  
보고서의 "분석 범위 한계"는 파이프라인에서 자동 생성되지만, 자동 생성이 포착하지 못하는 시스템 및 파서 층위의 구조적 한계가 여기에 모입니다.

한계를 정확히 아는 것은 포렌식 자동화의 핵심입니다. 못 본 것을 못 봤다고 정직하게 밝히지 못하면, "철저히 조사했으나 악성 행위가 없었다"와 "도구가 확인하지 못했다"를 구분할 수 없습니다.

> **문서 관리 원칙**:

## 1. 증거 입력 (Evidence Input)

### 1-1. 전체 물리 디스크 이미지의 파티션 수동 지정 필요
- MBR/GPT 파티션 테이블이 있는 전체 디스크 이미지(raw / dd)를 직접 파싱할 수 있으나, 시스템 볼륨을 도구가 임의로 추측하여 열지 않습니다.
- 일반적인 Windows 10/11 물리 디스크는 복구 파티션과 메인 OS 볼륨이 둘 다 NTFS 포맷입니다. 도구가 크기나 순서로 자동 판별할 경우 복구 파티션을 시스템 볼륨으로 오인하여 "증거가 조용히 누락되는 치명적 오류"가 발생할 수 있습니다.
- 따라서 분석관이 `--volume N` 옵션으로 대상 볼륨 번호를 명시해야 하며, 지정하지 않으면 파티션 목록(크기, 타입)을 출력하고 안전하게 실행을 멈춥니다.

### 1-2. E01 / VMDK 포맷의 미완전 실물 검증
- **E01 (Expert Witness Format)**: `dissect.target`을 통해 E01 컨테이너 헤더 디코딩 및 파티션 해석까지는 확인되었으나, 실제 대용량 Windows NTFS E01 이미지 상에서 04단계 전체 아티팩트를 관통 추출하는 실물 검증은 미완료 상태입니다. 급한 실무 사건에서는 FTK Imager 등을 통해 사전에 폴더 형태로 추출(`FileSource`)하여 투입하는 것이 안전합니다.
- **VMDK (Virtual Machine Disk)**: `.venv`에 `dissect.hypervisor`가 포함되어 단일 flat vmdk 구동은 가능할 것으로 기대되나, 스냅샷 델타(`-000001.vmdk`)나 분할 vmdk 환경에서의 실물 관통 검증은 수행된 적이 없습니다.

### 1-3. 단일 실행당 단일 볼륨 전용
- 본 파이프라인의 단일 실행은 1개의 대상 볼륨(예: `C:` 드라이브)을 기준으로 동작합니다.
- 침해 사고 시스템에 여러 드라이브(`C:`, `D:` 등)가 존재하는 경우, 케이스 ID를 분리하여(`CASE-001-C`, `CASE-001-D`) 각각 독립 실행해야 합니다.

### 1-4. 4Kn 디스크 실물 검증 부재
- MFT 파서에서 섹터 크기를 512바이트로 고정하던 로직을 레코드 기반 가변 처리로 수정했으나, 실제 4096바이트 네이티브(4Kn) 실물 디스크 이미지 기반의 04단계 관통 검증은 수행되지 않았습니다.

### 1-5. 라이브 호스트 직접 수집 미지원
- `\\.\C:`와 같은 활성 윈도우 호스트의 원시 볼륨 직접 접근 수집 기능은 포함되어 있지 않습니다. 사전에 KAPE, CyLR, FTK Imager 등으로 획득된 타겟 아티팩트 폴더 또는 디스크 이미지를 입력으로 받습니다.

## 2. 아티팩트 파서 (Artifact Parsers)

### 2-1. `$UsnJrnl` v4 미지원
- `$UsnJrnl` 파서는 v2 및 v3 포맷을 파싱할 수 있으나, Windows 11 대용량 볼륨 등에서 드물게 발견되는 v4 포맷은 지원하지 않으며 발견 시 스킵 처리됩니다.
- `$UsnJrnl` 레코드 자체에는 전체 절대 경로가 포함되어 있지 않으므로, 부모 디렉터리 레코드 번호(FRN)를 `$MFT` 트리와 결합하여 경로를 복원하는 과정에서 일부 유실(삭제된 부모 디렉터리 등)이 발생할 수 있습니다.

### 2-2. SRUM 트랜잭션 로그 미재생 및 시간 해상도
- SRUM ESE 데이터베이스(`SRUDB.dat`) 파서가 커밋되지 않은 트랜잭션 로그(`.log`)를 롤포워드 재생하지 않습니다. 비정상 강제 종료 시스템의 경우 종료 직전 최대 1시간 분량의 네트워크 및 리소스 사용 흔적이 누락될 수 있습니다.
- SRUM 데이터는 시간 해상도가 1시간 단위(Hourly aggregate)이므로 초/분 단위의 실시간 프로세스 생성/네트워크 연결 타임라인과 직접 1:1 결합하기 어렵습니다.

### 2-3. Amcache 문자열 시각 한계 및 `Root\File` 외부 미검증
- Amcache 파서는 스키마에 사전에 정의된 타임스탬프 필드명(예: `InstallDate`, `LinkDate`)만 파싱합니다. 임의의 벤더가 비표준 문자열 필드로 기록한 시간값은 흡수하지 못합니다.
- `Root\File` 키 파싱 로직은 실물 기반으로 구현되었으나, Eric Zimmerman의 `AmcacheParser` 등 표준 외부 도구 출력과의 대규모 교차 대조 검증이 완결되지 않았습니다.

### 2-4. SQLite 내장 엔진의 구조적 제약
- 순수 Python 기반 SQLite 파서(`sqlite_page.py`)는 B-tree 직접 파싱 방식을 사용하며 다음과 같은 제약이 존재합니다:
  1. `WITHOUT ROWID` 최적화 테이블을 읽지 못합니다.
  2. WAL(Write-Ahead Log) 파일을 병합 재생하지 않아 최근 트랜잭션이 누락될 수 있습니다.
  3. 삭제된 비할당 레코드의 카빙 복구를 수행하지 않습니다.
  4. 다중 윈도우 사용자 프로필 환경(`Users\*\...`)에서 가장 최근 또는 단일 사용자 프로필 경로만 탐색합니다.

### 2-5. 네트워크 단독 증거 파서 부재
- 시스템 내에 pcap 패킷 파서나 활성 소켓 테이블 카빙 엔진이 없습니다. 외부 C2 통신 흔적은 Sysmon EID 3(Network Connect), SRUM 네트워크 사용량, 브라우저 다운로드 히스토리 등 시스템 로그성 아티팩트에 전적으로 의존합니다.

### 2-6. Wazuh 알럿 연동 범위의 한계
- 현재 Wazuh 연동은 Windows 기반 Agent 알럿 JSON의 평탄화(`flatten_wazuh`)만 지원합니다. Linux Auditd/Syslog 기반 알럿은 평탄화 룰이 없으며, 알럿 발생 시 즉각적인 원격 증거 수집을 트리거하는 Active-Response 래퍼는 미구현 상태입니다.

## 3. 파이프라인 구조 및 LLM 해석 (Pipeline & LLM)

### 3-1. Tier 2 아티팩트 루프백 미구현 (명시적 비목표)
- 03단계(선별)는 아티팩트를 Tier 1(즉시 수집)과 Tier 2(조건부 유예)로 분류하지만, 04단계 수집 결과를 바탕으로 조건을 재평가하여 추가 파싱하는 피드백 루프백 엔진이 없습니다.
- 현재 Tier 2 항목은 전량 `Tier 2 루프백 미구현으로 미평가 (조건: ...)`로 투명하게 기록되며, 아키텍처의 단순성을 유지하기 위해 루프백 자동화는 명시적 비목표로 둡니다.

### 3-2. 05단계 레코드 배분: 시그널당 대표 1건 배분 (보장 레인)
- LLM의 컨텍스트 윈도우 한계와 생성 토큰 상한(1,024~2,048 토큰)으로 인해, 05단계 해석 모델에 전달되는 레코드는 최대 120건으로 제한됩니다.
- 동일한 attention 시그널(예: 고위험 LOLBin 실행, 암호화폐 지갑 접근 등)이 수십 개 발생하더라도 모델에는 해당 시그널의 **대표 레코드 1건**만 우선 전달됩니다. 이로 인해 동일 공격 루프의 반복 변종이 서사에서 축약될 수 있습니다.

### 3-3. Sysmon 프로세스 종료(EID 5) 플래그의 프롬프트 점유
- 프로세스 실행 수명(duration) 측정을 위해 로드된 Sysmon EID 5 이벤트 전건에 `process_lifecycle_closed` 플래그가 부여됩니다. 이로 인해 정상 종료된 일반 프로세스의 EID 5 레코드가 프롬프트 토큰을 일부 소모하는 오버헤드가 존재합니다.

### 3-4. 단일 타임존(KST/UTC+9) 가정
- 시나리오와 아티팩트 타임스탬프 결합 시 대한민국 표준시(KST) 및 명시적 UTC 오프셋을 기준으로 파싱합니다. 다국적 엔드포인트나 복수 타임존이 혼재된 케이스에서는 분석관의 타임존 사전 정규화가 요구됩니다.

### 3-5. 정답 데이터(Ground Truth) 부재 및 환각률 착시 현상
- 실제 침해사고 증거에는 전지적 100% 정답 라벨이 존재하지 않아, 프레임워크 평가는 합성 시나리오 및 K-LIVE 재현 환경에 의존합니다.
- 모델이 공격 서사 작성을 완전히 회피하여 생성된 문장이 0개일 경우, 통계상 기각된 문장이 없어 환각률이 0%로 계산되는 왜곡 현상이 발생할 수 있습니다.

## 4. 검증 및 보고서 해석 — 신호등 체계 (Verification & Reporting)

### 4-1. 검증기(Stage 06)의 과도한 엄격성으로 인한 연쇄 문장 증발 문제
- **문제점**: 종전 06단계 검증기는 증거와의 대조 시 대소문자, 파일 확장자, 공백 및 구분자 표기 차이(예: `nodejs` vs `Node.js`, 백슬래시 vs 슬래시)까지 엄격한 문자열 불일치로 처리하여 문장을 기각했습니다.
- **결과적 왜곡**: 분석 모델이 증거에 기반하여 정확한 공격 행위(C2 다운로드, 악성 스크립트 실행 등)를 서술했음에도 불구하고, 사소한 단어 표기 차이 하나 때문에 유효한 서사 문장 10여 개가 연쇄 삭제되는 치명적인 정보 유실이 발생했습니다.
- **신호등 검증 체계 (Traffic Light System) 도입**:
  - 🟢 **초록불 (`passed`)**: 원본 아티팩트 증거와 100% 엄격 일치하는 **확정 사실 (Confirmed Facts)** $\rightarrow$ 최종 보고서 본문의 핵심 사실로 기재.
  - 🟡 **노란불 (`unverifiable` / 부분 일치)**: 공격의 실체와 행위는 증거와 부합하나 단순 표기 차이나 맥락상 추가 검증이 요구되는 사실 $\rightarrow$ 문장을 삭제하지 않고 **"⚠️ 분석관 확인 필요 (Analyst Review Required)"** 고지와 함께 보고서에 보존.
  - 🔴 **빨간불 (`rejected`)**: 명백한 환각, 증거와 상충하는 거짓 진술 $\rightarrow$ 보고서 본문에서 완전히 배제하고 기각 통계에만 반영.

### 4-2. `must_review` 증거의 서사 누락 시 사건 개요 공백 현상
- 05단계 Reduce 과정에서 필수 검토 레코드(`must_review`)가 `incident_story` 문장에 명시적으로 인용되지 않으면, 검증기가 이를 기각하고 최대 재시도 횟수까지 모델에 재질의합니다.
- 모델이 끝내 해당 증거를 서사에 매끄럽게 편입시키지 못할 경우, 보고서의 "사건 개요 서사" 전체가 공백으로 출력되는 현상이 발생할 수 있습니다.

### 4-3. 07단계 보고서의 결정론적 템플릿 렌더링 (LLM 미사용)
- 최종 07단계 보고서는 환각 유입을 100% 차단하기 위해 LLM을 일절 사용하지 않고, 검증 완료된 JSON 데이터만을 Python 코드로 조립하는 결정론적(Deterministic) 템플릿 방식으로 렌더링됩니다.
- 따라서 사람 분석관이 작성하는 것과 같은 유려한 종합 분석 소견이나 창의적인 추론 문장은 제공되지 않으며, 오직 검증을 통과한 객관적 사실들의 목록과 타임라인으로만 구성됩니다.
